# ADR-0001 采用 Tauri 2 单一技术栈承载三平台桌面应用

| 字段 | 内容 |
|---|---|
| 01 标识 | ADR-0001 |
| 状态 | **Accepted**（决策已接受，2026-11-23） |
| 决策者 | 人类维护者（本项目唯一有权接受者） |
| 实施状态 | 实现中（feat/impl：core 已存在；Tauri 壳与 UI 未实现）（详见 `06-acceptance.md`） |
| 负责人 | 技术负责人 |
| 适用范围 | 全仓库；`apps/desktop`、`crates/core`、`crates/platform` |

## 02 决策问题与范围边界

用什么技术构建一个能在 macOS / Windows / Linux 同时交付的桌面应用，且需要：全局热键、多显示器截图、透明穿透覆盖窗、键鼠注入、麦克风采集、系统 TTS、自动更新、三平台安装包？**不涉及**模型选择、UI 设计语言、后端（本项目无服务端）。

## 03 背景、约束、假设与证据

- 单维护者 + 多 Agent 并行开发 → 语言数量越少越好（C-1）。
- 核心体验（覆盖窗 + 采集 + 注入）都在系统层，纯 Web 方案（PWA）做不到。
- 假设 H-1…H-4：`xcap`/`enigo`/`cpal`/Tauri 透明窗在三平台可用（待 CI 与冒烟验证）。
- 证据强度：**中等**。依据是各库官方文档与历史使用，未在本仓库实测。

## 04 决策驱动因素（按优先级）

1. 三平台同一代码基，可维护性
2. 系统级能力（采集/注入/热键）可达
3. 可离线单测的核心逻辑
4. 打包与更新成熟
5. 安装包体积与内存
6. 前端开发速度

## 05 候选方案

| 方案 | 说明 |
|---|---|
| A. Tauri 2 + Rust 核心 + 无框架 TS | 壳 WebView，业务在 Rust |
| B. Electron + Node 原生模块 | 全 JS，原生部分靠 addon |
| C. 纯原生三份（Swift / C# / C++） | 每平台独立 |
| D. Flutter Desktop | Dart + 平台通道 |
| E. Python + Qt | PySide6 |

## 06 方案比较与证据强度

| 维度 | A | B | C | D | E |
|---|---|---|---|---|---|
| 单代码基 | 强 | 强 | 弱 | 中 | 强 |
| 系统能力 | 强（Rust 直接调） | 中（原生 addon 维护痛苦） | 强 | 中（通道） | 中 |
| 核心可离线单测 | 强（纯 Rust crate） | 中 | 弱 | 中 | 中 |
| 安装包体积 | 中（~15MB） | 大（~120MB） | 小 | 中 | 大 |
| 打包/更新 | 强（内置 updater+打包器） | 强 | 弱 | 中 | 弱 |
| 团队匹配（单人会 Rust） | 强 | 中 | 弱 | 弱 | 中 |

证据强度：A 与 B 判断为**中等**（基于文档）；C/D/E 判断为**弱**（未验证）。

## 07 决策结论

采用 **A**：

- `crates/core`：纯 Rust，**无 GUI / HTTP 客户端 / 子进程**依赖；允许 SQLite 文件读写（ADR-0008）与内存中的定时/解析逻辑，全部业务规则与状态机，可 `cargo test` 离线跑。
- `crates/platform`：`cfg(target_os)` 分平台实现 ports。
- `apps/desktop`：Tauri 2 薄壳，只做窗口、命令桥、线程调度。
- `apps/desktop/ui`：TypeScript + Vite，无前端框架；渲染用 Canvas + DOM。

## 08 选择理由与关键取舍

理由：把"难测又关键"的逻辑放进纯 Rust；把"必须碰系统"的部分限制在一个 crate；把 UI 做成可替换的薄层。

取舍：放弃 Electron 的生态红利与熟悉度，换取体积、启动与系统能力；接受 WebView 在三平台的渲染差异（用最保守的 CSS/Canvas 子集）。

## 09 后果与剩余风险

中性变化：职责与接口按本决定重新分配，团队/Agent 的工作方式随之调整；既有习惯做法需要迁移。

正面：一处修 bug 三平台生效；核心逻辑覆盖率可到 80%+；无 async 运行时（同步 HTTP + 线程）使测试确定。

负面：Rust 开发速度慢于 TS；WebView 版本差异（尤其 Linux WebKitGTK）；Tauri 生态变更风险。

剩余风险：H-1…H-4 未验证；Linux 需 `webkit2gtk-4.1`，部分发行版要额外安装。

## 10 实施约束与落实确认

- 禁止在 `core` 引入 `std::process`、`reqwest`、`tauri`（CI 用 `cargo deny` 风格检查脚本 `xtask/check-core-deps.sh`）。
- `platform` 之外不得出现 `cfg(target_os)` 分支。
- 落实确认：`cargo tree -p openclicky-core` 无 GUI/网络依赖；CI 三平台编译通过。

落实确认分两类：**符合决策**（实现是否遵守本决定的约束）与**达到预期**（遵守之后是否真的改善了当初关注的问题）。前者通过不证明后者成立；若仅前者成立，应重新评估本决定而不是宣布成功。

## 11 重新审视条件、可逆性与退出路径

重审条件：Tauri 某个必需能力在三平台之一不可用；或核心功能需要 WebGL/3D 渲染；或打包失败无法修复。

可逆性：中。`core` 可原样复用到 Electron（通过 FFI/子进程）或原生壳；UI 可迁移。

退出路径：改 `wry`+`tao` 自建壳（保留 Rust）；或 Electron + `napi-rs` 暴露 core。
