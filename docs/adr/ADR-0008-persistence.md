## 02 决策问题与范围边界

用什么存？哪些是权威？升级与删除如何保证不丢不残？边界：不做服务端、不做多端同步。

## 03 背景、约束、假设与证据

- 数据量小（单用户）：< 100 万行量级。
- 需求：事务（用户消息+回复+用量同事务）、可查询（任务列表/用量按天）、用户可读可改（记忆）、可删除（S4）。
- 证据：SQLite 单文件 + WAL 是桌面应用标准；记忆用 md 便于用户查看和 diff。

## 04 决策驱动因素

1. 事务性（INV-6 不重复计量）
2. 用户可见可控
3. 迁移可控
4. 零系统依赖

## 05 候选方案

| 方案 | 说明 |
|---|---|
| A. SQLite + markdown + toml | 混合 |
| B. 全 JSON 文件 | 简单 |
| C. 全 SQLite（含记忆/配置） | 统一 |

## 06 方案比较与证据强度

| 维度 | A | B | C |
|---|---|---|---|
| 事务/查询 | 强 | 弱（重写整文件） | 强 |
| 用户可读改 | 强（md/toml） | 强 | 弱 |
| 迁移 | 中 | 弱 | 中 |
| 崩溃安全 | 强（WAL） | 弱 | 强 |

证据强度：**强**（架构性质）。

## 07 决策结论

采用 **A**：

| 数据 | 载体 | 权威 |
|---|---|---|
| messages/sessions/tasks/task_steps/usage_events/audit_log | `app.db`（`rusqlite`，bundled，WAL） | 是 |
| metrics_daily | `app.db`（可重建的派生指标） | 否（派生） |
| 词典 | `app.db` 的 `dict_entries` 表 | 是 |
| 最近截图 | 仅内存 ≤30s | 否 |
| 记忆 | `memory/profile.md`、`memory/projects.md` | 是 |
| 配置 | `config.toml` | 是 |
| 词典 | `dictation/dictionary.json` | 是 |
| 最近截图 | **不落盘**；仅内存保留 ≤30 秒用于重绘 | 否 |
| 日志 | `logs/*.jsonl`（7 天） | 否 |

迁移：`PRAGMA user_version`；迁移前复制 `app.db.bak`；失败进入只读并提示。

## 08 理由与取舍

取舍：接受两种存储范式（SQL 与文本）带来的同步成本（记忆索引在 DB 中仅是引用，不做全文索引）。

## 09 后果与剩余风险

中性变化：职责与接口按本决定重新分配，团队/Agent 的工作方式随之调整；既有习惯做法需要迁移。

正面：用量与任务可事务；记忆可被用户直接编辑；删除流程可逐项列举。

负面：用户手改 md 可能导致格式错乱 → 解析容错（按行宽松解析）。

剩余风险：Linux 上磁盘同步语义差异；WAL 文件残留（启动时 checkpoint）。

## 10 实施约束与落实确认

- 单写连接（`Mutex<Connection>`）+ 读连接池（≤4）。
- 任何跨表写入必须走 `store::commit_turn`。
- 落实确认：`tests/store_*.rs`（迁移、事务回滚、删除传播、并发写）。

落实确认分两类：**符合决策**（实现是否遵守本决定的约束）与**达到预期**（遵守之后是否真的改善了当初关注的问题）。前者通过不证明后者成立；若仅前者成立，应重新评估本决定而不是宣布成功。

## 11 重审条件、可逆性、退出路径

重审：数据量 > 100 万行且查询变慢；或需多设备。

可逆：高（导出 JSON 后换引擎）。退出：迁移到 `sled`/`duckdb`，保留 schema 语义。
