## 02 决策问题与范围边界

三个平台怎么产出安装包？没有 Apple/Microsoft 开发者证书时如何仍可交付？更新如何做？边界：不上架 App Store / Microsoft Store（首版）。

## 03 背景、约束、假设与证据

- 无签名证书预算 → 必须"未签名也能装"。
- macOS 26 对未签名/未公证应用有 Gatekeeper 拦截；用户需右键打开或 `xattr -dr`。
- Windows SmartScreen 会对未签名 exe 警告（More info → Run anyway）。
- 证据：Tauri 官方打包器支持 dmg/app、nsis/msi、appimage/deb；updater 需签名密钥（与代码签名无关）。

## 04 决策驱动因素

1. 用户能装上（无证书前提下）
2. 产物可追溯
3. 升级不破坏数据
4. 未来可平滑加签名

## 05 候选方案

| 方案 | 说明 |
|---|---|
| A. CI 矩阵 + 未签名产物 + 文档指引；预留签名 env | 务实 |
| B. 必须签名后才发布 | 阻塞 |
| C. 只发源码，用户自行编译 | 对普通用户不可用 |

## 06 方案比较与证据强度

| 维度 | A | B | C |
|---|---|---|---|
| 今天可交付 | 强 | 无 | 中 |
| 用户体验 | 中（需绕过警告） | 强 | 弱 |
| 未来升级成本 | 低 | 低 | 高 |

证据强度：**强**（工具链能力已文档化）。

## 07 决策结论

采用 **A**：

| 平台 | 产物 | 签名 |
|---|---|---|
| macOS | `.dmg`（universal），`.app.tar.gz`（更新） | 未签名；预留 `APPLE_CERTIFICATE` 等 secrets，存在即自动签名+公证 |
| Windows | `.exe`（NSIS）、`.msi` | 未签名；预留 `WINDOWS_CERTIFICATE`（signtool） |
| Linux | `.AppImage`、`.deb` | 无 |

更新：Tauri updater + 独立签名密钥（`TAURI_SIGNING_PRIVATE_KEY`），公钥入库；未配置时禁用自动更新（不报错）。

回滚：Release 保留最近 3 个版本；文档给出"下载上一版覆盖安装"的步骤，并说明数据兼容策略（§17）。

## 08 理由与取舍

取舍：接受"首次打开有系统警告"，换取今天就能交付；把签名做成配置而非重构。

## 09 后果与剩余风险

中性变化：职责与接口按本决定重新分配，团队/Agent 的工作方式随之调整；既有习惯做法需要迁移。

正面：三平台同一流水线；升级路径清楚。

负面：未签名会降低信任与安装完成率；企业环境可能直接拦截。

剩余风险：macOS 未来收紧未签名应用（届时必须签名）。

## 10 实施约束与落实确认

- 发布只能由 tag 触发；构建产物必须带 commit。
- 落实确认：`.github/workflows/release.yml` 三平台 job 成功；`05-deployment.md` 三平台步骤实测。

落实确认分两类：**符合决策**（实现是否遵守本决定的约束）与**达到预期**（遵守之后是否真的改善了当初关注的问题）。前者通过不证明后者成立；若仅前者成立，应重新评估本决定而不是宣布成功。

## 11 重审条件、可逆性、退出路径

重审：获得证书；或需要商店分发。

可逆：高（CI 增补 secrets 即可）。
