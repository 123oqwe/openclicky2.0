## 01 文档范围、适用版本与权威来源

- 适用：`openclicky2.0` 仓库全部目录；三平台构建；`v2.x` 全部版本。
- 权威来源（冲突按此裁决，禁止"挑最松的一份"）：

| 问题 | 去哪里看 |
|---|---|
| 产品行为 | 源 PRD（`docs/00-baseline.md` 引用） |
| 技术承诺/契约 | `docs/01-tech-prd.md` |
| 决策理由 | `docs/adr/` 最新 Accepted |
| 模块细节 | `docs/02-sdd.md` |
| 测试预期 | `docs/04-test-design.md` |
| PR 是否合并 | GitHub 实际状态（`gh pr view`） |
| 功能是否验收 | `docs/06-acceptance.md` 中绑定 commit 的 G2/G3 结论 |
| Agent 自述 | **不算证据** |

冲突处理：产品 vs 技术 → 开 ADR 裁决；技术内部 → 以 tech-prd 为准并更新 SDD；无法裁决 → 记入 `02-sdd.md` §22 未决问题，**阻塞**相关工作。

## 02 交付物分解与工作包结构

按"用户结果"拆工作包，不按"前端做完/后端做完"拆。

| 工作包 | 目标（可验收的结果） | 验收节点 |
|---|---|---|
| WP1 骨架 | `cargo test` 绿：配置/注解/提示词/用量/存储 | G2-CORE |
| WP2 问答 | 按住说话→回答→指与画→计量，端到端可跑 | G2-ASK |
| WP3 任务 | 创建→工具→检查点→取消→恢复 | G2-AGENT |
| WP4 听写 | 增量出字→注入→词典→终端守卫 | G2-DICTATION |
| WP5 自动化 | 定时任务 + 建议预算 + 记忆注入 | G2-AUTOMATION |
| WP6 三平台交付 | macOS/Windows/Linux 安装包 + 部署文档 | G3-RELEASE |

工作包字段：目标、范围、非目标、交付物、主要依赖、对应验收节点（见上表）。

**当前状态不在本文维护**：各工作包是否通过以 `06-acceptance.md` §2 的结论为准（绑定 commit）。本文只定义"通过需要什么"。

**施工顺序**由 `ADR-0015` §07 定案、`06-acceptance.md` §3.1 展开：F1 能用 → F2 不烧钱 → F3 数据 → F4 体验。F2 之前不发布。

## 03 角色、所有权与决策权限

| 角色 | 职责 | 本项目承担者 |
|---|---|---|
| 任务负责人 | 对任务交付负责 | 实施 Agent |
| 模块负责人 | 模块边界与长期维护 | 人类维护者 |
| 集成负责人 | 跨模块组合可用 | 人类维护者（**必须显式指定**，不默认落在最后一个 PR 作者） |
| 验收负责人 | 证据与结论 | 人类维护者 |
| 发布负责人 | 开放条件与运行风险 | 人类维护者 |

权限分离（硬规则）：

| 动作 | 谁可以做 |
|---|---|
| 修改实现 | 实施 Agent |
| 修改测试基线/降低门槛 | 人类维护者（需 ADR 或本文件例外记录） |
| 修改 CI 与分支保护 | 人类维护者 |
| 宣布验收通过 | 验收负责人（Agent 只能提交证据） |
| 发布 | 发布负责人（tag 只能人类创建） |

**"所有局部任务都说完成，但整体不能用"** 由集成负责人在 G2 节点判定，不允许"最后一个 PR 合了就算完"。

## 05 依赖：必须带类型、条件、证据

禁止只写 "B 依赖 A"。每条依赖记录五元组：**对象 / 类型 / 满足条件 / 版本 / 判定证据**。

| 类型（标准名） | 含义 | 本仓库例子 |
|---|---|---|
| 决策/规格依赖 | 规则未定不能写代码 | 注解语法未定 → 不做 `annotations` |
| 开发依赖 | 缺前置产物无法开工 | 无 `ports.rs` → 不写 `voice` |
| 合并依赖 | 可先开发，不能先合 | 改 `ports` 的 PR 必须先合，调用方 PR 才能合 |
| 集成依赖 | 局部可做，联调需其他 | 前端可先做，真机验证等平台层 |
| 环境/资源依赖 | 需要设备/账户/独占资源 | 需要 macOS 才能验证 TCC |
| 验收依赖 | 下游等上游被验证 | G3 等 G2-ASK |
| 部署/开放依赖 | 代码顺序 ≠ 运行顺序 | 先迁移后启用新字段 |

写法示例：`voice` 合并前：`ports.rs` 的 `ChatProvider::complete_stream` 已进入 main、`tests/providers_openai.rs` 通过、`cargo test -p openclicky-core` 绿。

## 06 并行开发条件与资源冲突

**可并行需同时满足**：契约明确、修改责任可区分、共享资源不互相污染、有明确集成与验证安排。

共享写区（**必须串行**）：

| 共享区 | 原因 |
|---|---|
| `crates/core/src/ports.rs` | 全模块契约 |
| `crates/core/src/store/migrations.rs` | 迁移不可并行 |
| `docs/01-tech-prd.md`、`docs/02-sdd.md` | 权威文档 |
| `Cargo.toml` | 依赖解析冲突 |
| `.github/workflows/` | CI 语义 |

隔离要求：代码隔离 = 独立分支（必要时 worktree）；运行隔离 = 独立 `--data-dir`、独立端口、独立测试库。**worktree 不是安全沙箱**，不隔离数据库与凭证。

## 07 调度、WIP 与里程碑

排序依据：解锁价值 > 风险 > 业务优先级 > 资源。

WIP 限制：**同时进行 ≤ 3 个任务**；待评审 ≤ 2；待验收 ≤ 2。编码快不等于能并行——评审与验收也是容量。

里程碑用结果表达（"问答链路端到端可跑且有用量计量"），不用 PR 数量。

---

## 08 状态定义与进入/退出条件

四个状态独立记录，禁止一个"完成"包打天下：

| 状态 | 取值 | 进入 | 退出 |
|---|---|---|---|
| 任务实施 | pending / in_progress / done / blocked | 前置满足 | 交付物 + 自测证据 |
| PR 评审 | draft / in_review / approved / changes_requested | PR 打开 | 必需检查 + 批准 |
| 功能验收 | not_started / failed / passed | G2 触发条件满足 | 证据包 + 结论 |
| 发布 | blocked / staged / open / rolled_back | G3 通过 | 观察期结束 |

合法中间态示例：`实施 done；PR 已合并；G2-AGENT 未通过；发布 blocked`。

阻塞是**附加标记**（原因 + 责任人 + 解除条件），不是状态。

循环等待（任务依赖成环）必须识别并解决；任务内部的失败—修复循环不算依赖环。

## 09 PR 拆分与分支策略

- 一个 PR = 一个可理解、可评审、可验证的变化主题；生产代码 + 相关测试 + 必要文档同 PR。
- 分支：`main`（受保护）← `feat/*`、`fix/*`、`docs/*`、`chore/*`。禁止直接推 main。
- 合并：squash merge；提交信息 Conventional Commits。
- 叠加 PR：明确 base 分支、合并顺序、上游变更后如何 rebase 并重跑检查。
- 小 PR ≠ 把不可分割的变化切碎到 main 无法构建。每次合并后 `main` 必须绿。

## 10 单个 PR 的标准执行流程（10 步）

| # | 阶段 | 完成标志 |
|---|---|---|
| 1 | 接单与基线检查 | 读到任务卡全部字段；`git status` 干净；依赖满足 |
| 2 | 准备工作区 | 新分支；`cargo test` 基线跑过（知道已有失败） |
| 3 | 小型实施计划 | 列出修改点/契约影响/测试清单；超出范围即停 |
| 4 | 建立验证（红） | 先写失败测试，确认失败原因正确 |
| 5 | 实现（绿）→ 重构 | 循环到目标测试通过；不顺手改无关代码 |
| 6 | 自检 | 通读 diff；检查密钥/调试代码/无关格式；`cargo fmt`、`clippy -D warnings` |
| 7 | 正式评审 | 见 §11；按意见修改或说明理由（不得沉默忽略） |
| 8 | 集成候选检查 | 在最新 main 上 rebase → 全量测试 |
| 9 | 合并 + 合并后验证 | 合并后 main CI 绿；必要时重跑受影响验收 |
| 10 | 交接与计划更新 | 更新任务状态、下游可用性、验收节点状态 |

失败分流：代码错误 → 步骤 5；规格冲突 → 需求/设计变更（ADR）；环境故障 → 记录并阻塞；越权 → 停下请求授权。**禁止无限重试，禁止删测试换绿灯。**

## 11 PR 描述、评审与交接

PR 模板（`.github/PULL_REQUEST_TEMPLATE.md`）必含：

1. 任务/规格引用（PRD 编号、tech-prd §、ADR、测试用例 ID）
2. 变化摘要 + **没改什么**
3. 实际依赖（含未满足项）
4. 测试结果（命令 + 输出摘要）
5. 未测项与原因
6. 迁移/配置/开放影响
7. 风险与回滚方式
8. 关联验收节点

评审维度（不能只看格式）：设计、正确性、复杂度、并发、测试有效性、命名、文档、安全（密钥/注入/权限）。

交接格式（禁止"做完了，交给下一个"）：commit SHA、已完成、未解决、证据位置、可用接口、下一步约束。

## 12 CI、合并队列与合并权限

`.github/workflows/ci.yml`（已落地）在各 PR、`main` 推送与 `merge_group` 上运行。
`prepare` 作业在**没有 Cargo 工作区**的 ref 上显式输出 notice 并跳过代码检查——这是"未执行"，不是"通过"；工作区一旦出现，`rust-*` 自动启用。

| 检查 | 命令 |
|---|---|
| 格式 | `cargo fmt --all -- --check` |
| Lint | `cargo clippy --workspace --all-targets -- -D warnings` |
| 测试 | `cargo test --workspace` |
| 构建（三平台） | `cargo build --workspace` |
| 守护检查 | `bash scripts/check-invariants.sh`（core 无 GUI/网络依赖、无硬编码密钥、采集单入口） |

前端目前无自动化检查（`apps/desktop/ui/dist` 直接入库，见 ADR-0014）；新增前端构建时必须同时加 `package.json` 与 CI job。

必须防止 **"两个 PR 各自绿、一起合就红"**：合并前在最新 main 上 rebase；启用 merge queue 时必须配置 `merge_group` 触发器。

`main` 保护：必需检查（上面 5 项）、线性历史、禁强制推送、禁直推。

例外（绕过）：只有人类维护者，需在 PR 描述写原因 + 补验计划，并在 `docs/06-acceptance.md` 记录。

## 13 风险分级与专项检查触发条件

| 等级 | 判定 | 额外要求 |
|---|---|---|
| 低 | 文档、注释、纯前端样式 | 常规检查 |
| 中 | 单模块逻辑、纯函数、UI 交互 | 单测 + 集成测 |
| 高 | 权限/沙箱/SSRF、迁移、密钥、任务状态机、采集门禁、发布脚本 | 专项评审 + 对应安全用例 + G2 证据 |

按影响分级，**不按行数**。两行权限代码可以是高风险。

## 14 分层验收

| 层 | 对象 | 判断 | 载体 |
|---|---|---|---|
| G0 | 单个任务 | 输入/范围/权限/环境是否可开工 | 任务卡 |
| G1 | 单个 PR | 局部正确 + 回归 + 依赖 | CI + 评审 |
| G2 | 工作包 | 完整场景 + 跨模块规则 + 真实产物 | `06-acceptance.md` 条目 |
| G3 | 发布候选 | 三平台安装、迁移、运行、恢复 | Release 清单 |
| G4 | 开放后 | 实际运行指标 | 观察记录 |

"大验收" = G2 或 G3，有独立负责人、输入版本、证据要求，**不是最后一个 PR 顺手看一眼**。

---

## 15 验收节点定义（G2/G3 必填字段）

对象与范围 / 触发条件 / **版本基线（commit + 构建号 + 配置）** / 验收规格引用（`04-test-design.md` 用例 ID）/ 负责人与批准者 / 环境与证据位置 / 通过与失败条件 / 失败处置（建修复任务、阻塞哪些下游）/ **失效条件（改了什么要重验）** / 通过后解锁什么。

原则：**验收通过的是"这个确定组合在这些条件下的结果"，不是永久盖章。** 后续改动接口、迁移、权限、相关实现 → 重跑受影响用例，旧结论作废。

## 16 发布、观察、回退与收尾

- 合并 ≠ 部署 ≠ 开放。
- 发布清单：三平台产物、版本号、commit、更新签名、`05-deployment.md` 步骤、已知问题。
- 观察：崩溃、首次安装成功率（无法遥测 → 用 issue 反馈）、预算告警触发次数。
- 回退：保留最近 3 个 Release；回退文档步骤；数据兼容检查（SDD §20）。
- **撤回代码 ≠ 撤回已发送的邮件/已改的文件** → 回退说明必须列数据影响。
- 收尾：移除临时开关、清理兼容代码、更新文档、结束工作包。

## 17 人与 Agent 的执行约定

任务卡额外字段（Agent 专用）：执行 Agent 类型、可用工具集、可读上下文范围、可写范围、token/时间预算、检查点、停止条件、交接格式。

| 允许自动 | 需要人类 |
|---|---|
| 读写仓库内代码与测试 | 改需求、降低验收门槛 |
| 运行测试/构建 | 改 CI、保护规则 |
| 提交 commit、开 PR | 合并到 main（可用人工批准后自动） |
| 生成证据与报告 | 宣布验收通过、创建 tag、发布 |

**Agent 可以提交证据，不能凭"我已测试通过"解锁依赖。**

## 18 阻塞、返工、依赖变更与应急

- 上游 PR 被关闭/撤回/重设计 → 下游重新评估，**不得继续把失效假设当事实**（可继续无关工作）。
- 契约变化 → 通知所有消费者（在此文档 §05 记录影响集）。
- 验收失败 → 建修复任务，关联失败证据，阻塞对应发布动作，不阻塞无关开发。
- 应急修复：可走快速通道，但必须留原因、权限、影响范围、补验责任；**不得删除失败记录或永久绕过保护**。

## 19 进度、瓶颈与工程反馈

报告的应该是：可启动任务、真正阻塞交付的依赖、待评审/待验收积压、已通过的完整能力、未覆盖风险、下一个可验证结果。

不使用：代码行数、PR 数量、Agent 运行时长作为进展指标。

跟踪：周期时间、阻塞时长、评审等待、验收等待、返工比例、恢复时间。

## 20 规范落实、更新与例外

| 规则 | 执行方式 |
|---|---|
| 不能直推 main | GitHub 分支保护**已启用**（required: `docs-and-invariants`、线性历史、禁强推、禁删除） |
| 必需检查不能缺 | `.github/workflows/ci.yml` 已接入，`docs-and-invariants` 为必需检查 |
| core 不得依赖 GUI/网络 | `scripts/check-invariants.sh`（已存在并接入 CI） |
| 采集单入口 | 同上：`capture_all` 必须带 guard，脚本断言调用点 |
| 风险判定 | 人工/评审（约定） |
| 验收结论绑定 commit | 人工 + 文档（约定） |

例外记录：PR 描述 + `06-acceptance.md`「例外」小节，含有效期与到期处理。**写了规则不等于落实**：每个 G3 前抽查一次任务卡真实性、依赖有效性、证据版本、临时例外是否已过期。
