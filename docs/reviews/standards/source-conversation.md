# 第一部分 · 产品 PRD

# 第一部分：一个优秀的产品 PRD，应该包含什么？

**优秀的产品 PRD，不是一份“想做哪些功能”的清单，而是一份能够让产品、设计、工程、测试和业务负责人对产品形成一致理解的需求约定。**

它要回答：

> **为谁解决什么问题，为什么值得解决，本次做到什么范围，产品在不同情况下如何表现，以及怎样证明它满足了需求。**

Atlassian 对 PRD 的定义也强调产品的目的、功能、行为、用户需求与成功条件，而不只是页面或者功能名称。citeturn407168view0

对于你说的“大项目开工”，我建议把产品 PRD 做成一套**有主文档、有模块规格、有共用规则、可以追踪版本的产品需求体系**，而不是把所有内容塞进一份不断增长的文档。

下面先讲边界，再展开完整内容，最后给你一个具体功能的写法示例，以及开工前的审查标准。

---

## 一、先明确：产品 PRD 负责什么，不负责什么？

### 1. 产品 PRD 要把“产品行为”写清楚

这里的产品行为，不只是“用户点击按钮后显示什么”，还包括：

用户不操作时系统会不会主动工作，后台任务如何继续，权限发生变化时怎么办，多个用户同时修改时谁的修改生效，外部服务没有明确结果时如何呈现，以及数据被删除后还会不会被继续使用。

**产品 PRD 可以非常详细，但详细的是需求、规则和可观察的行为，不是内部实现方案。**

NASA 的需求编写指南虽然不是互联网产品 PRD 模板，但其中的要求值得借鉴：需求要明确、可唯一引用、可追踪，并尽量描述需要什么，而不是提前规定如何实现。citeturn407168view3

### 2. 产品层和技术层，可以这样区分

| 主题 | 产品 PRD 应该明确 | 不在本轮展开的技术实现内容 |
|---|---|---|
| 任务恢复 | 中断后保留哪些进度，用户如何继续，哪些操作不能重复 | 检查点、任务队列、恢复算法 |
| 权限 | 谁能对什么对象做什么，撤销后哪些行为停止 | 令牌、权限服务、鉴权实现 |
| 数据 | 数据代表什么，谁拥有，如何修改、导出、删除 | 数据库表、索引、存储架构 |
| 搜索 | 搜索范围、排序意图、无结果体验、权限过滤要求 | 检索引擎、向量库、排序模型 |
| 多端协作 | 哪些功能在哪些端可用，冲突如何向用户呈现 | 同步协议、缓存、通信实现 |
| Agent | 什么时候能行动，什么时候必须等待，什么算真正完成 | 模型、Harness 内部结构、调度算法 |

不过，**产品 PRD 不是不能写约束**。

例如，“必须能导入客户已有的某种文件格式”“首发必须在指定设备类别上运行”，都是合理的产品约束。关键是写明约束的来源和必要性，而不是把个人偏好的技术选型包装成用户需求。

# 二、优秀产品 PRD 的完整内容

下面这套结构是我建议用于复杂软件、平台型产品和 Agent 产品的框架。它不是要求每个小功能都填写同样多的内容，而是要求：**相关问题必须有明确答案，或者明确记录尚未解决。**

## A. 项目背景、目标与范围

### 01. 文档基本信息与生效范围

这一部分解决的是：**我们现在讨论的，到底是哪一版需求？**

应写清产品名称、文档编号、版本、负责人、参与评审者、最近更新时间、文档状态，以及对应的产品版本或发布范围。

尤其要分开记录三种状态：

**需求状态**，例如草案、评审中、已批准、已废弃；**实现状态**，例如未开发、开发中、已实现；**验证状态**，例如未验证、验证失败、已通过。

不要用一个“已完成”同时表达这三件事。

还需要定义文档的权威关系：正文、原型、共用规则和模块文档发生冲突时，由谁裁决、如何更新。不能让工程师凭感觉决定应该听哪个版本。

**写到位的标志：任何参与者都能回答“我现在应该依据哪份需求做事”。**

---

### 02. 产品摘要与产品定义

这一部分应让首次接触项目的人迅速理解产品，而不是先阅读几十页细节。

建议写清：目标用户、核心问题、提供的核心价值、产品形态、本次版本的主要交付，以及最重要的限制。

可以采用这样的句式：

> 为了帮助【目标用户】在【具体场景】中解决【具体问题】，本产品提供【关键能力】，使用户能够获得【可观察的结果】。本次版本覆盖【范围】，不覆盖【边界】。

例如，“做一个超越现有操作系统的 Agent-native OS”可以作为愿景，但还不是可执行的产品定义。

进一步需要说清：首批服务谁，保留哪些传统电脑能力，Agent 负责什么，人如何委托和接管，首发支持什么设备与工作场景。

**摘要要描述产品承诺，而不是堆叠“智能、领先、革命性”等形容词。**

---

### 03. 用户问题、研究证据与立项依据

这一部分回答：**我们怎么知道这个问题真的存在，并且值得现在解决？**

应包含问题发生的场景、频率、影响、现有解决方式，以及已有方式为什么不够好。证据可以来自访谈、实际操作观察、使用数据、工单、流失原因或客户业务流程。

GOV.UK 的用户研究指南强调，应把没有得到用户研究支持的意见视为待验证假设，并让用户需求聚焦问题，而不是预设的解决方案。citeturn407168view1

建议对关键证据记录：

> 证据来源、采集时间、样本范围、观察结果、局限，以及它支持了哪一项产品判断。

必须区分：

**事实**：“在这次观察中，用户为了完成一项任务切换了多个工具。”

**解释**：“这些切换可能增加理解成本和遗漏风险。”

**假设**：“统一入口可能减少遗漏。”

**产品决策**：“本次先验证跨工具任务的统一查看与追踪。”

不要把最后一个产品决策，反过来写成“用户已经证明需要我们设计的全部功能”。

---

### 04. 目标用户、角色与利益相关方

这一部分回答：**谁使用、谁付费、谁管理、谁受影响？**

对每类核心用户，应描述其目标、工作环境、使用频率、能力差异、当前工具、决策权限和主要障碍，而不是只写年龄、职业和收入。

对企业产品，还要区分使用者、购买者、管理员、审批者、外部协作者和支持人员。对平台产品，开发者与集成方也可能是独立用户群体。

需要明确**首要用户与暂不服务的用户**。

“所有人都能用”不能指导首发范围；“先服务需要委托跨应用任务、但仍要保留传统桌面控制权的个人用户”，才开始具备设计指导意义。

对于 Agent 产品，还要区分：人类用户的目标，与 Agent 作为被授权执行者的职责。**Agent 不是天然拥有独立授权的用户。**

---

### 05. 核心场景、用户任务与需求

这一部分回答：**用户在什么情况下，需要完成什么事情？**

建议每个核心场景写清：

> 谁，在什么环境下，因为什么触发，需要完成什么任务，当前如何完成，希望得到什么结果，有什么限制。

场景应该描述完整任务，而不只是一个按钮。

例如：

> 用户在外出时发现一项工作即将到期，希望通过手机委托电脑上的 Agent 完成，并在完成后取得可使用的产物。

这比“支持手机遥控”更有用，因为它进一步引出设备在线状态、权限、任务执行、结果取回、中断处理等产品问题。

用户故事可以作为简洁入口，但不应取代完整规格。GOV.UK 将用户故事的目标视为核心，并通过验收条件确认用户需求是否真正得到满足。citeturn407168view2

**一个场景通常会跨越多个页面、对象和模块，不能把它拆到最后只剩一组彼此无关的页面功能。**

---

### 06. 产品目标与成功指标

这一部分回答：**产品产生什么改变，才算有价值？**

建议区分三类指标。

**用户结果指标**，衡量用户是否更容易得到所需结果，例如任务成功率、完成时间、返工量。

**业务结果指标**，衡量产品是否形成持续价值，例如有效使用、留存、付费或服务成本。

**保护性指标**，用于防止主要指标改善的同时制造其他损害，例如误操作、越权、重复执行、投诉或不必要打扰。

Google Research 的 HEART 研究提供了从产品目标映射到用户体验指标的思路，而不是仅凭容易采集的数据决定衡量什么。citeturn610188view1

每个正式指标要说明：定义、分子分母、观察窗口、基线、目标值、数据来源、负责人，以及异常数据的处理方式。

例如，“任务完成率达到某个百分比”仍然不够明确。必须定义什么算任务、什么算完成，取消是否计入，等待中的任务如何呈现，失败是否被排除。

**没有基线就写“基线待采集”，不要为了显得完整而编造数字。**

---

### 07. 产品定位、设计原则与方案取舍

这一部分回答：**为什么选择这条产品路线，而不是其他路线？**

建议描述现有替代方案、用户为什么继续使用它们、迁移成本在哪里，以及本产品准备在哪些具体结果上改善体验。

这里的替代方案不只有直接竞品，也包括人工流程、表格、现有软件组合，以及用户干脆不做。

设计原则应该能裁决冲突。

例如：

> 当后台自动化效率与用户当前操作发生冲突时，优先保护用户的当前操作。

这可以直接影响窗口焦点、输入设备占用和通知策略。

而“用户至上”“极致智能”通常无法单独裁决一个具体问题。

重要方案还应保留简短的取舍说明：考虑过什么、选择了什么、放弃了什么、付出了什么代价，以及什么新证据会触发重新评估。

---

### 08. 本次范围、非目标、优先级与版本边界

这一部分回答：**这次到底做什么，不做什么？**

建议至少把需求分为：本次必须交付、本次候选、后续考虑，以及明确不属于产品方向。

每一项范围都应有边界。例如，“支持文件管理”需要进一步说明支持哪些对象、哪些操作、哪些位置、哪些权限和哪些限制。

还应写清版本依赖：哪些能力必须共同交付，缺少哪项就无法形成完整用户价值。

不要只划分成“第一期做前端，第二期做后台”。产品层应尽量按**可以被真实使用的完整场景**划分版本。

另外，优先级、承诺和实现状态是不同概念：

> “优先级高”不代表已经承诺本次交付；“已写入计划”不代表已经实现；“已经实现”不代表已经验证。

---

## B. 产品结构、流程与详细行为

### 09. 产品能力结构与信息架构

这一部分回答：**产品由哪些能力构成，用户如何理解并进入这些能力？**

应分别定义：

**能力结构**：产品有哪些业务能力，各自负责什么、不负责什么。

**信息架构**：用户从哪些入口进入，如何导航、搜索、切换上下文和找到结果。

**交互渠道**：哪些能力通过桌面、网页、手机、语音、命令行或机器接口提供。

对于你这类既服务人又服务 Agent 的产品，不应只画 GUI 页面。还需要说明外部 Agent 可以发起哪些操作、获得什么反馈，以及这些操作是否受同一套权限和业务规则约束。

这里描述的是产品能力与渠道关系，不是服务架构或协议字段。

**需要防止的情况是：同一能力在两个入口里拥有不同权限、不同状态定义，甚至不同“完成”标准。**

---

### 10. 核心业务对象、术语与关系

这一部分回答：**产品中的东西分别是什么，它们之间有什么关系？**

建议为每个核心对象定义：业务含义、创建方式、拥有者、关键属性、关联对象、生命周期，以及用户能对它执行的操作。

例如，任务、执行记录、产物和审批不能都被叫作“任务”。

“用户希望完成的一项工作”和“系统对这项工作的第几次执行”可以是两个不同概念；执行失败不一定意味着用户目标被取消，重新执行也不一定应该创建一个重复目标。

还应明确容易混淆的关系：

删除任务是否删除产物？归档项目后能否继续检索？联系人被删除后，历史记录如何呈现？断开一个数据源后，哪些信息还保留？

**这里写业务含义和产品规则，不是数据库表设计。**

---

### 11. 端到端用户旅程与业务流程

这一部分回答：**用户怎样从需求产生，走到获得结果？**

应覆盖首次进入、初始化或连接、首次价值、持续使用、修改与协作、异常恢复，以及退出、迁移或停用。

每条关键流程需要区分：用户动作、系统动作、需要决策的节点、等待条件、外部参与方和最终结果。

特别要写清跨模块的交接。

例如：

> 连接账户 → 获得相应能力 → 创建任务 → 检查权限 → 执行 → 核验结果 → 交付 → 后续追踪。

每个箭头都可能存在业务条件。账户连接成功，不一定意味着全部能力可用；执行结束，也不一定意味着目标已完成。

对于 Agent 产品，还应区分**人的日程**与**Agent 的执行队列**。纯后台工作不应仅因为需要安排顺序，就被默认塞进用户日历。

---

### 12. 逐项功能需求与统一功能规格

**这是产品 PRD 的主体。**

每项进入开发的功能，都应具备足够明确的输入、行为、输出、限制和验收条件。

我建议采用下面的统一规格。复杂功能可以拆成多个独立需求，简单功能可以引用共用规则，不必机械复制所有内容。

| 字段 | 应该写到什么程度 |
|---|---|
| 功能标识 | 唯一编号、名称、所属模块、适用版本 |
| 需求来源 | 对应用户问题、场景、目标或必要约束 |
| 用户与权限 | 谁能使用，对哪些对象生效 |
| 触发与入口 | 用户从哪里进入，或什么事件会自动触发 |
| 前置条件 | 执行前必须满足什么；不满足时如何处理 |
| 输入 | 输入内容、来源、默认值、必填项、有效范围 |
| 正常行为 | 系统按什么业务顺序完成什么事情 |
| 输出与影响 | 用户得到什么，哪些对象或外部状态发生改变 |
| 分支与异常 | 信息缺失、权限不足、失败、中断时如何表现 |
| 状态与操作 | 当前状态允许什么操作，如何进入下一状态 |
| 业务规则 | 引用哪些共用规则，有没有局部例外 |
| 数据与隐私 | 读取什么、保存什么、展示给谁 |
| 质量要求 | 性能、可靠性、兼容性等适用约束 |
| 验收条件 | 如何从可观察结果判断满足需求 |
| 依赖与未决问题 | 依赖什么，哪里尚未确定，谁负责解决 |
| 关联材料 | 对应的流程、原型、规则、证据及其版本 |

需求语句建议采用这样的形式：

> 在【前置条件】下，当【触发事件】发生时，系统必须【产生明确行为或结果】，并满足【约束】。

把一项大功能拆成可独立引用的需求，而不是用一段话同时要求十几种行为；这也符合 NASA 关于单项需求清晰、独立和可唯一引用的建议。citeturn407168view3

---

### 13. 业务规则与跨模块一致性

这一部分回答：**发生冲突时，产品按什么规则决定？**

建议为重要规则分配编号，注明适用范围、优先顺序、例外和生效条件。

典型内容包括默认值、排序规则、额度计算、状态变更限制、数据来源冲突、重复提交、并发修改、对象删除后的关联处理。

例如，“用户设置优先”仍然可能不够清楚。

必须进一步明确：当前明确指令、历史偏好、管理员限制、任务专属设置和系统默认值发生冲突时，谁优先？哪些限制不能被普通指令覆盖？

对于共用规则，应只保留一处权威定义，让各模块引用，而不是各自重写一版。

**一个模块局部看起来正确，但与其他模块组合后互相矛盾，仍然意味着整体产品需求没有定义完整。**

---

### 14. 状态、异常、边界与恢复

这一部分回答：**产品不仅在顺利时怎么工作，在不顺利时又怎么工作？**

应为有生命周期的对象定义状态、进入条件、退出条件、允许操作、用户可见信息和是否属于终态。

对于异步工作，尤其要区分：

“已收到请求”“已开始”“等待条件”“部分完成”“结果待确认”“成功”“失败”“已取消”。

这些状态不一定适用于所有功能，但不能把性质不同的情况全部压成“进行中”或者“失败”。

每个重要异常都应回答：

> 已经完成了什么？还没有完成什么？是否产生外部影响？系统接下来会做什么？用户可以做什么？

还要覆盖重复提交、断网、离线、多端冲突、授权过期、资源不足、对象被删除以及外部结果不明。

**取消、停止、撤销、回滚和恢复，不应在没有定义的情况下互换使用。**  
已经发生的外部行为能否撤回，必须按具体能力写清，不能只凭界面上的“取消”按钮承诺。

---

### 15. 交互、界面、内容与通知

这一部分回答：**用户怎样理解产品、操作产品和判断当前情况？**

应明确页面目的、主要信息、可用操作、输入验证、加载反馈、空状态、错误状态、保存方式、返回行为和关键提示内容。

例如，进入一个配置页面后，用户修改的内容是立即生效、离开时保存，还是必须点击保存？修改失败时是否保留输入？多端打开时如何提示冲突？

通知也需要产品规则：什么值得通知、什么只进入记录、什么必须打断用户、什么可以汇总，以及用户怎样控制频率。

对于你要求的“未来风、科技风、有审美”，PRD 应把它转成体验方向和约束，例如信息层级、视觉密度、动效是否妨碍操作、运行状态是否清晰。

**视觉稿用于表达设计，文字规格用于明确规则；两者应相互引用，不能相互替代。**

---

## C. 全局质量、权限与外部边界

### 16. 权限、安全与数据生命周期

这一部分回答：**谁可以接触什么，系统可以替谁做什么，数据最终去哪里？**

建议按下面的结构描述权限：

> 主体 × 对象 × 动作 × 条件 × 生效范围 × 有效期。

权限不是简单的“管理员或普通用户”，还可能与账户、项目、文件、联系人、金额、时间和任务有关。

应明确授权来源、默认权限、授权提示、审批方式、撤销方式、权限变化后的在途任务处理，以及用户能查看的操作记录。

数据生命周期需要说明收集目的、保存范围、访问范围、保留期限、导出、删除、备份中的处理，以及断开数据源后的行为。

例如，“删除账户”要说明会删除哪些内容、何时完成、有什么保留例外；不能只写“支持注销”。

涉及法律或合同的限制，应记录适用地区、约束来源和待专业核验事项，而不是笼统写“满足全部合规要求”。

---

### 17. 非功能需求与质量标准

这一部分回答：**产品做到什么质量才算可用？**

建议根据产品类型覆盖以下维度：

| 维度 | 产品层应该定义的问题 |
|---|---|
| 性能 | 哪些动作需要多快完成，在哪些设备、数据规模和网络条件下衡量 |
| 可靠性 | 什么算服务失败，哪些工作不能丢失，用户如何恢复 |
| 数据完整性 | 重复、覆盖、丢失或部分写入时应有何保证 |
| 容量 | 支持多少对象、账户、文件、并行任务或协作者 |
| 兼容性 | 哪些平台、设备、文件格式和辅助技术属于承诺范围 |
| 无障碍 | 键盘、读屏、缩放、对比度、动效等达到什么要求 |
| 国际化 | 支持什么语言，以及日期、时区、数字格式如何处理 |
| 资源与成本 | 用户设备和账户资源如何受限，接近或超过额度时怎么办 |
| 可恢复性 | 中断、重启或升级后哪些状态和产物必须保留 |

对于 Web 界面的无障碍要求，可以明确引用适用的 WCAG 版本和等级，而不是只写“支持无障碍”；WCAG 本身提供了可测试的成功条件。citeturn585262view2

质量指标应写成可验证的约定。例如：

> **示例目标，非通用标准：**在已定义的基线设备和数据集条件下，打开任务列表后，至少 95% 的测量样本应在 1 秒内达到可交互状态。

设备、数据集、测量起止点和阈值依据还需要明确；只写“响应时间小于 1 秒”仍然可能产生歧义。

**指标是待验证的要求，不是已经实现的成绩。**

---

### 18. 外部集成、兼容、迁移与退出

这一部分回答：**产品怎样进入用户原有的环境，又怎样让用户安全离开？**

每个关键集成都应说明用户为什么连接它、连接后获得什么能力、授权不足时缺少什么、数据更新如何呈现，以及连接中断后的体验。

不能把“账户已连接”直接等同于“产品已经能够读取、搜索、写入和执行全部操作”。

对于迁移，应说明可以迁移什么、哪些内容不支持、如何处理重复和冲突、用户如何核对结果，以及迁移失败后原数据是否受影响。

对于退出，应明确导出范围、格式、未完成任务、已产生费用、共享内容和第三方权限的处理。

对于操作系统类产品，这里还应该覆盖安装、升级、已有文件和应用的兼容承诺，以及恢复或卸载后的用户资产保护。

---

### 19. 商业规则、运营与支持能力

这一部分回答：**产品在真实运营时，谁来处理那些不能只靠普通用户界面完成的事情？**

商业产品需要明确套餐权益、计费单位、额度、试用、升级降级、取消和退款等会影响体验的规则；内部产品则可能需要成本分摊、服务范围或资源配额。

运营与支持能力应覆盖问题反馈、故障说明、用户申诉、必要的人工处理、配置管理和支持人员权限。

例如，“支持团队可以帮助用户排查失败任务”还需要定义：支持人员能看到什么、是否需要用户同意、能否修改内容、操作是否留痕。

这不意味着产品 PRD 要包含完整的营销计划或财务模型。

**凡是会改变用户权益、产品行为或日常可运营性的业务规则，都不能完全留到上线后再决定。**

---

## D. AI / Agent 产品的专项要求

### 20. AI 能力边界、控制权与结果可信度

普通软件可以按适用性裁剪这一章。对于你的 Agent-native 产品，我建议把它作为必需章节。

Microsoft 的人机交互指南强调，应让用户理解 AI 能做什么、可能怎样出错，并支持纠正、解释和全局控制。citeturn610188view0

在此基础上，你的 PRD 需要明确以下几个方面。

**首先，能力边界。**  
系统只能建议、可以起草，还是可以实际执行？哪些任务支持，哪些任务不支持？外部能力缺失时如何降级？不能把“理论上某个模型可以做到”写成产品已承诺的能力。

**其次，意图和上下文边界。**  
信息不足时何时可以采用默认值，何时必须澄清？允许读取哪些数据？历史偏好如何查看和纠正？来自网页、文件或邮件的内容，不能因为包含指令就被视为用户授权。

**再次，行动与控制权。**  
哪些行为可在既有授权内自动执行，哪些需要单次确认？任务执行中用户如何修改、停止或接管？增加新步骤、新对象或新支出时，原授权是否仍然适用？

**然后，结果和证据。**  
必须区分“生成了计划”“调用了工具”“工具返回成功”“外部目标状态得到确认”。产物放在哪里，引用来自哪里，哪些结果尚未核实，都应有明确表现。

**最后，质量与变化。**  
不同任务类型如何评估质量，哪些错误属于不可接受，模型或能力更新后如何防止关键场景退化？统计性的质量目标要注明场景和数据范围，不能只给一个脱离任务的“准确率”。

对于 Agent，我建议明确禁止以自述替代验证：

> Agent 说“完成了”，不能单独作为产品完成状态的依据。

同时，不要把所有步骤都设计成人工审批。应按明确的风险和授权规则划分自动执行范围，否则“自动化”可能只是把用户变成连续点击确认的人。

---

## E. 验证、度量与发布

### 21. 产品分析、反馈与假设验证

第 06 章定义成功是什么；这一章定义：**用什么证据判断产品是否正在接近成功。**

应说明关键行为事件的业务含义、用户如何提供反馈、如何分析失败和放弃，以及哪些假设需要通过研究或实验验证。

例如，“任务完成事件”是在模型停止输出时发生，还是在产物生成并完成核验后发生？如果这里不一致，产品指标就可能失真。

对关键假设，应记录验证方法、目标用户、通过与失败条件，以及结果会影响哪项产品决策。

这里可以定义事件和指标的业务口径，但没有必要提前规定分析平台或埋点代码。

**“没有人投诉”不应被直接当作“体验很好”；“点击率高”也不应被直接当作“用户问题得到解决”。**

---

### 22. 产品验收标准与需求追踪

这一部分回答：**什么证据可以证明一项需求已经满足？**

产品验收条件应描述可观察的结果。GOV.UK 将验收条件定义为用于确认服务满足用户需求的一组结果。citeturn407168view2

建议每项关键需求都有独立的验收编号，并能关联到场景、设计材料和后续验证结果。

例如：

> **前提：**用户没有某文件的读取权限。  
> **操作：**用户通过任意受支持入口请求查看该文件。  
> **预期：**系统不返回文件内容，并提供符合权限规则的反馈。

除了正常路径，还需要覆盖重要的权限、失败、边界和跨模块情况。不是要求机械穷举所有组合，而是确保高风险组合没有漏掉。

这里还要分清三件事：

**需求验收**：行为是否满足约定。

**发布准入**：这个版本是否满足交付条件。

**产品效果验证**：用户问题是否真的得到改善。

一项功能可以通过需求验收，却仍然没有产生足够用户价值。后者需要真实使用与研究证据，不能由“测试通过”代替。

---

### 23. 发布范围、阶段目标与上线后处理

这一部分回答：**怎样把这些需求变成一个可以交付和持续使用的版本？**

建议描述首批开放对象、开放能力、已知限制、产品层面的依赖、迁移或引导要求、支持安排，以及扩大范围的条件。

里程碑应尽量用结果表达。

“任务模块完成”不够明确；“指定用户可以从创建任务走到取得可使用产物，并处理规定的失败场景”更接近产品交付。

还应明确上线后观察什么，发生什么情况需要暂停某项能力，以及暂停后用户的任务、数据和产物如何处理。

这里只定义产品侧的准入和用户影响，不展开部署系统、工程排期或发布流水线。

---

## F. 不确定性与需求维护

### 24. 风险、假设、待决策事项与变更记录

这一部分回答：**哪些地方尚未确定，谁来决定，变化会影响什么？**

我建议至少检查价值、可用性、技术可行性和业务可持续性四类风险。SVPG 的“四大风险”框架也强调，应尽早面对这些风险，由产品、设计和工程协作解决，而不是只追求交付功能。citeturn585262view0

每个重要未决问题应包含：问题内容、影响范围、负责人、需要什么证据、最晚何时解决，以及未解决时是否阻塞某项工作。

不要只留下“待定”。

变更记录也不能只是“优化了权限设计”。应说明原规则、新规则、变更原因、影响需求、适用版本，以及是否需要重新验证。

**需求允许变化，但不能悄悄变化。**

# 三、到底要写多具体？看一个功能规格示例

下面用一个缩小范围的例子说明写法：

> **功能：用户让 Agent 将一份已选定的文件通过邮件发送给一名明确的收件人。**  
> 本例限定为用户已经选择“每次发送前确认”的策略，不代表所有 Agent 任务都必须逐次审批。

### 不够好的写法

> 支持 Agent 自动发送邮件，支持附件，保证安全，失败后自动重试。

这里几乎每个词都存在歧义：发给谁，使用哪个账户，哪个附件版本，什么是安全，失败是否真的没有发出去，以及重试会不会重复发送。

### 更好的写法

**功能边界**

用户选择一个发送账户、一名收件人和一份文件版本。系统生成待发送内容，展示发送对象与附件，在获得当前内容对应的确认后提交发送。

本次不包含群发、定时发送或自动追加附件。

**输入与前置条件**

发送账户可用；收件人对应明确地址；主题、正文和附件版本可识别；文件读取权限与发送权限有效。

收件人存在歧义时，不允许根据姓名猜测地址。附件不可访问时，保留已填写内容并提示问题，不得静默删除附件后发送。

**核心需求**

| 编号 | 产品要求 |
|---|---|
| REQ-MAIL-001 | 系统在请求确认前展示发送账户、收件地址、主题、正文和附件版本 |
| REQ-MAIL-002 | 收件人、正文或附件版本在确认后发生变化时，原确认失效 |
| REQ-MAIL-003 | 在提交发送前发现授权已撤销时，系统阻止发送并保留草稿 |
| REQ-MAIL-004 | 外部结果无法确定时，显示“发送结果待确认”，不得直接标记为成功或自动重复发送 |
| REQ-MAIL-005 | 只有取得足够的外部确认依据后，才显示对应的发送成功状态 |
| REQ-MAIL-006 | 产品分别定义“已提交发送”和“已送达”的证据要求，不得将前者呈现为后者 |
| REQ-MAIL-007 | 用户取消时，系统说明哪些步骤已停止、哪些外部行为可能已经发生，不承诺无法保证的撤回 |

**状态与恢复**

请求提交前可以取消并保留草稿。请求已经提交但结果不明时，取消后仍需保留结果待确认的信息；不能让“取消”抹掉可能已经发生的外部行为。

只有能够确认原请求不会再产生发送效果，并且授权仍然有效时，才进入允许重新发送的流程。

**验收条件示例**

| 场景 | 预期结果 |
|---|---|
| 收件人姓名匹配到两个地址 | 请求用户选择，不发生发送 |
| 用户确认后修改附件版本 | 旧确认不再有效，重新展示待发送内容 |
| 提交前撤销发送权限 | 不提交发送，草稿仍可访问 |
| 提交后外部响应中断，结果无法确定 | 显示结果待确认，不自动重复提交 |
| 外部证据只证明提交成功 | 不显示已送达 |
| 查看完成记录 | 能看到实际发送对象、对应内容版本及可用的确认依据 |

这里没有选择数据库、模型、邮件接口或任务队列，但产品行为已经比“支持发送邮件”明确得多。

**这就是产品 PRD 应有的具体程度：足以讨论实现和验证，不需要工程师重新猜测产品想表达什么。**

# 四、大项目应该怎样组织这些内容？

我建议采用下面的结构，而不是要求所有内容永远放在同一个文件里。

| 文档层级 | 主要负责什么 |
|---|---|
| **主产品 PRD** | 产品定义、用户、目标、整体范围、能力结构、关键旅程、重大约束及文档索引 |
| **领域／模块 PRD** | 某个业务领域的对象、流程、功能、局部规则、异常和验收 |
| **共用产品规则** | 权限、状态术语、通知、数据生命周期、多端行为等跨模块约定 |
| **版本范围清单** | 本次发布采用哪些需求版本，交付哪些能力，有什么依赖和已知限制 |

平台差异足够大时，可以增加端侧规格，但优先引用共用需求，只记录差异。不要为桌面、手机和网页各复制一套核心业务规则。

建议建立这样的追踪关系：

**问题证据 → 用户需求 → 场景 → 功能需求 → 验收条件 → 验证结果。**

产品目标和指标则用于判断这些需求交付后，是否确实改善了用户结果。

维护时遵守一个原则：

> **同一条规则只在一个地方拥有权威定义，其他地方通过编号和版本引用。**

Atlassian 也强调利用链接逐步展示详细材料、共同维护需求，并避免需求文档因实现和反馈变化而过时。citeturn407168view0

---

# 五、开工前，怎样判断这份产品 PRD 足够好？

我建议用下面的审查表，而不是用页数判断质量。

| 审查问题 | 不合格的信号 |
|---|---|
| 为什么做？ | 只有创始人的愿景，没有问题证据或明确假设 |
| 为谁做？ | 所有人都是目标用户，没有首要场景 |
| 本次做什么？ | 范围只有模块名称，没有交付边界 |
| 产品如何行为？ | 正常流程依赖口头补充，异常让工程自行决定 |
| 规则是否一致？ | 不同页面、入口或模块对同一件事定义不同 |
| 权限和数据是否明确？ | 只有“保证安全”，没有授权、撤销和数据处理规则 |
| 质量能否衡量？ | 使用“快速、稳定、智能”等无法判定的表述 |
| 如何验收？ | 只有“页面存在、按钮可点、Demo 能演示” |
| 未知问题是否受控？ | 大量“待定”，没有负责人和影响范围 |
| 变化能否追踪？ | 原型、文档和实际实现分别代表不同版本 |

还需要补充一个重要判断：

**大项目开工，不等于必须先把未来几年所有功能写到字段级，然后才能做任何工程。**

我建议按阶段确定精度：整体方向、关键边界和跨模块约束先统一；近期要交付的场景写到可实现、可验收；远期需求保留目标、范围和待验证假设。高风险或高不确定性的部分，可以先通过原型和技术探索获得证据，再形成正式承诺。Atlassian 也将“工程开始前就把整个项目所有细节写死”列为应避免的模式。citeturn407168view0

**真正的开工门槛，不是没有任何未知，而是：当前承诺范围内的重要产品行为已经清楚，关键风险有人负责，未知事项不会被偷偷当成已确认需求。**

---

## 最后，把产品 PRD 的核心压缩成一句话

> **优秀的产品 PRD，要把“我要做一个很厉害的产品”，变成“这些用户在这些场景下，可以通过这些能力得到这些结果；系统遵守这些规则，在这些边界内运行，并通过这些证据证明需求已被满足”。**

它既不能只讲愿景，也不能提前变成代码设计；既要覆盖完整用户任务，也要允许团队通过新的证据修正方案。

**对你这种大项目而言，最重要的不是多写几百个功能，而是让目标、范围、对象、流程、规则、状态、权限和验收之间能够相互对应，没有关键断点。**


# 第二部分 · 技术实现 PRD

# 第二部分：一个优秀的技术实现 PRD，应该包含什么？

**优秀的技术实现 PRD，要把“产品希望提供什么能力”，转化成“工程准备怎样兑现这些能力，以及凭什么相信能够兑现”。**

它不是把产品功能换成技术名词，也不是写一份：

> 前端用什么、后端用什么、数据库用什么、模型用什么。

而是要明确：

> **系统必须满足什么技术要求；采用什么总体方案；各部分如何协作；数据、权限和状态如何保持正确；在故障、增长和升级时如何工作；最后如何验证、交付和持续运行。**

对于你这种“大项目开工”的文档体系，我建议把它定位为：

**技术需求与总体实现方案，是连接产品 PRD、详细设计、工程执行和验证工作的技术总纲。**

下面先把边界讲清楚，再展开完整内容，最后用上一轮的邮件场景示范写法。

---

## 一、先区分：技术实现 PRD 与其他文档是什么关系？

在你这套文档体系里，建议按下面的职责分工组织。这里约定的是**内容归属**，不是要求每个团队都采用完全相同的文件名称。

| 文档 | 主要回答的问题 | 与技术实现 PRD 的关系 |
|---|---|---|
| **产品 PRD** | 为谁解决什么问题？产品应如何表现？什么结果算满足需求？ | 提供产品目标、功能、规则、质量要求和边界 |
| **技术实现 PRD** | 如何把产品要求转成可实现、可集成、可验证、可运行的系统？ | 定义技术要求、总体架构、关键契约和工程约束 |
| **ADR** | 某项重要架构决策为什么这样选择？接受了什么代价？ | 保存关键决策依据，技术实现 PRD 引用其结论 |
| **SDD** | 具体模块、数据结构、接口和算法如何设计？ | 将总体方案细化到可以实施的设计 |
| **测试与验收规格** | 用什么数据、环境、步骤和证据证明要求被满足？ | 展开技术实现 PRD 中定义的验证要求 |
| **工程工作方式与执行计划** | 谁负责什么？怎样开发、评审、集成、发布和处理问题？ | 将技术范围和依赖转化成日常工程工作 |

**一个重要的分界：不是“技术实现 PRD 不能有细节”，而是“它优先明确会影响全局、模块协作和技术承诺的细节”。**

例如，数据库里某个普通展示字段如何命名，可以在详细设计中确定；但“同一业务操作如何避免重复执行”“哪个组件拥有修改任务状态的权力”，不能因为属于技术细节就推到后面。

同样，接口完整字段可以保存在专门的接口规格中，但接口的语义、权限、失败行为和版本兼容规则，必须在总体方案中明确并引用。

arc42 的架构文档框架也分别处理目标、约束、结构、运行场景、部署、跨领域规则、质量与风险，而不是把架构压缩成一张技术栈图。citeturn724000view0

---

# 二、优秀技术实现 PRD 的完整内容

我建议将其组织成六组：**技术基线、系统设计、运行质量、交付验证、工程约束，以及产品类型专项要求。**

---

## A. 技术基线：到底要实现什么，承诺到什么程度？

### 01. 文档基线、负责人和适用范围

这一章解决：

> **当前工程应该依据哪一版产品需求、哪一版技术方案开展工作？**

需要写清项目名称、文档编号、版本、技术负责人、模块负责人、评审参与者、适用发布版本，以及关联的产品 PRD、ADR、设计和接口规格。

有已有系统时，还应注明对应的代码版本、已部署版本和现状调查时间。

尤其要区分：

**拟议方案、已批准方案、已实现能力、已验证能力。**

“准备采用某种机制”不等于“系统已经拥有这种保证”；一项设计通过评审，也不意味着它已经通过实际故障测试。

还应明确修改权限与冲突处理：技术方案与产品承诺不一致时，谁负责裁决，哪些变化需要重新评审。

**写到位的标志：团队不会把设想当事实，也不会依据不同版本各自开工。**

---

### 02. 技术背景、现状、目标与非目标

这一章回答：

> **从什么起点出发，解决什么技术问题，这次不解决什么？**

对于新项目，要说明团队规模、运行环境、目标设备、首发能力、资源预算和外部限制。

对于已有项目，要补充现有架构、已知缺陷、当前性能、数据规模、历史兼容要求，以及哪些部分继续复用。

需要明确区分三类内容：

**硬约束**，例如必须兼容某种已有接口。

**方案选择**，例如决定采用某种存储系统。

**待验证假设**，例如预计某个第三方服务能够支持目标并发量。

不要把偏好的技术选型写成不可改变的约束，也不要把供应商宣传转写成已经验证的能力。

技术非目标也应明确。例如，本次不自研模型、不承诺任意设备兼容、不支持跨区域容灾，或者暂不支持已有任务在不同执行环境之间迁移。

**不做什么写清楚，才能判断方案是否过度设计，或是否偷偷削减产品范围。**

---

### 03. 产品需求到技术需求的追踪关系

这一章回答：

> **每一项产品承诺，由哪些技术要求和组件负责兑现？**

不能只把产品 PRD 复制一遍，而应将产品行为拆解成工程上需要满足的要求。

例如：

| 产品要求 | 派生技术要求 | 主要责任组件 | 验证方向 |
|---|---|---|---|
| 关闭界面后，后台任务继续执行 | 任务生命周期不得绑定界面进程；状态需要持久化 | 任务服务、执行运行时 | 关闭客户端后检查任务与产物 |
| 重复点击不得重复执行同一操作 | 定义请求去重与业务操作幂等规则 | 接入层、执行层 | 重复请求和并发测试 |
| 撤销权限后，不得启动新的受限操作 | 执行前重新检查有效授权，并定义撤销生效边界 | 权限组件、执行网关 | 授权与执行竞态测试 |
| 用户能取得真实产物 | 定义产物存储、关联关系、访问控制与核验条件 | 产物组件、核验组件 | 产物读取与完整性检查 |

技术需求的来源不一定都是某一条功能需求，也可以来自安全要求、运行要求、平台限制或必要的基础能力，但都应记录来源与理由。

NASA 的系统工程指南强调需求的清晰性与可追踪性，并将利益相关方要求、技术需求、逻辑分解和设计方案视为相互迭代的过程。citeturn269150view0

**不要出现两种断点：产品承诺没有技术承接，或者工程建设没有需求依据。**

---

### 04. 可衡量的质量目标与技术保证

这一章回答：

> **什么叫够快、够可靠、够安全、能够支撑目标规模？**

至少应按项目需要定义性能、可用性、正确性、数据完整性、容量、兼容性、资源消耗和恢复能力。

每个目标都要写明：

**适用场景、环境、负载、数据规模、指标定义、目标阈值、测量方法、观察窗口和责任人。**

例如，“接口响应小于一秒”不够明确。需要说明测量起止点，是否包含网络时间，统计平均值还是百分位，以及失败请求如何计入。

这里可以使用 **SLI（实际测量的服务指标）**和 **SLO（对该指标设定的目标）**。Google SRE 强调目标应围绕用户实际得到的服务结果，并明确测量方式，而不仅是收集容易取得的服务器指标。citeturn724000view2

还要区分两类要求：

**统计性目标**，例如一定比例的请求在规定时间内返回。

**必须保持的正确性约束**，例如跨用户读取不得绕过权限检查。

不能因为整体可用性允许一定错误比例，就把越权访问也当成可以消耗的“错误预算”。

**目标值、设计估计值和实测结果必须分别标注。**

---

## B. 系统设计：准备怎样实现，各部分如何协作？

### 05. 系统边界与总体架构

这一章回答：

> **系统包括什么，不包括什么，与谁交互，部署在哪里？**

建议按照需要提供几种相互一致的视图：

| 视图 | 应说明什么 |
|---|---|
| **系统上下文** | 用户、外部系统、第三方服务与本系统的边界 |
| **应用与模块结构** | 主要应用、服务、运行时、存储及其职责 |
| **部署视图** | 哪些部分在本地、云端、移动端或隔离环境中运行 |
| **关键运行流程** | 一项请求经过哪些组件，如何取得结果 |
| **数据流与信任边界** | 数据从哪里来，经过哪些处理，在哪里跨越权限边界 |

C4 模型提供系统上下文、容器、组件和代码等不同层级的结构视图，并提供动态与部署视图；其官方说明也强调不必机械使用全部层级，只保留有价值的视图。citeturn724000view1

对你的项目，特别需要区分：

**用户界面在哪里，控制逻辑在哪里，实际执行在哪里，权威数据在哪里。**

“用户在手机点击执行”，并不代表任务在手机运行；“统一控制台”，也不代表所有执行进程共享相同权限。

**架构图上的箭头必须有含义：调用、事件、数据复制还是授权关系，不能全部用一条线含糊表示。**

---

### 06. 子系统划分、职责与所有权

这一章回答：

> **每个模块负责什么，谁拥有它的数据和行为，模块之间怎样划界？**

每个关键模块应说明职责、不负责的事项、输入输出、依赖、拥有的数据、对外能力、失败影响，以及负责实现和运行维护的人。

特别需要明确：

谁可以修改状态，谁只是读取；谁决定执行，谁实施执行；谁核验结果，谁只展示结果。

例如，在一个任务系统中，可以分别定义任务管理、调度、执行、权限和产物模块。但不能让多个模块都在没有规则的情况下决定“任务是否已经完成”。

**模块划分不等于必须拆成微服务。**

我建议先明确逻辑边界，再根据隔离需求、部署需求、伸缩需求和团队维护能力，决定哪些模块需要独立进程或独立部署。

不要为了显得架构先进，把一个小团队可以维护的系统拆成几十个必须分别运维的服务。

---

### 07. 关键运行流程、状态机与并发规则

这一章回答：

> **系统运行起来后，一项工作怎样从输入走到完成？**

至少覆盖关键成功流程、长时间等待、失败恢复、取消、权限变化，以及多个执行者同时操作的情况。

对于关键流程，要明确调用顺序、同步与异步边界、状态写入位置、外部影响发生点、超时边界和完成判定。

对有生命周期的对象，要定义状态转换规则：

谁可以发起转换，必须满足什么条件，是否允许重复转换，遇到旧消息或并发修改怎么办。

例如，“执行器失联后重新分配任务”不是完整设计。还要回答：

原执行器只是暂时失联、随后又继续工作时，如何防止两个执行器同时修改同一个对象？

此时技术实现 PRD 至少要确定并发控制原则及责任组件，不能只写“通过锁解决”，把锁的作用范围和失效条件全部留下。

**产品 PRD 定义用户应看到什么状态；技术实现 PRD 还要定义怎样保持这些状态与真实执行一致。**

---

### 08. 数据架构、权威来源与一致性

这一章回答：

> **系统保存什么，什么数据说了算，发生冲突或中断时如何保持正确？**

需要包含核心实体、标识符、关系、数据拥有者、生命周期，以及主要读写路径。

更重要的是明确：

**权威数据、派生数据、缓存、搜索索引和分析数据分别是什么。**

例如，搜索索引暂时落后时，不能自动把搜索结果当作任务当前状态的最终依据。

对于写入，要说明事务边界、并发修改规则、版本检查、消息与数据的关联，以及失败后的修复方式。

如果一次业务操作既写数据库又发送事件，就需要处理其中一步成功、另一步失败的问题。AWS 的事务发件箱模式说明了这类“双写”风险，也指出事件可能重复投递，消费方仍需处理幂等。citeturn240257view2

还要写清数据删除如何传播到缓存、索引和派生结果，备份恢复后如何防止已删除数据重新进入正常使用。

**“统一数据库”更应落实为统一的数据含义、权威来源和访问规则，而不是强制所有类型的数据都放进同一种存储。**

---

### 09. 接口、事件与跨模块契约

这一章回答：

> **模块之间怎样合作，双方分别可以依赖什么保证？**

接口规格不能只有路径、参数和返回示例。

还应明确身份和权限要求、操作语义、前置条件、失败分类、重复请求行为、并发冲突、超时、限流以及版本兼容规则。

对于异步接口，应区分：

**请求已接收、任务已持久化、执行已开始、外部操作已提交，以及业务结果已确认。**

对于事件，需要定义生产者、消费者、事件标识、关联对象、版本、顺序要求、重复处理和重新读取规则。

HTTP 接口可以通过 OpenAPI 等机器可读规格描述；OpenAPI 本身用于定义与编程语言无关的 HTTP API 接口说明。citeturn240257view5

但业务保证仍要写清：一个返回成功的响应，到底承诺了什么？

**跨模块契约应有一处权威定义，并通过版本引用，不能由不同团队分别维护互相矛盾的副本。**

---

### 10. 客户端、多端协作与本地状态

这一章回答：

> **用户所在的设备与后台系统怎样协同，断开连接后会怎样？**

应说明哪些状态保存在客户端，哪些由服务器或本地守护进程负责；哪些操作可以离线，哪些必须在线；重新连接时如何同步。

还要定义输入草稿、上传进度、流式输出、任务状态订阅、通知、多端修改和版本不兼容的处理。

例如，界面关闭后任务继续执行，需要说明下一次打开时，如何重新发现任务和读取进度，而不是依赖之前那条连接仍然存在。

对于桌面软件，要考虑进程崩溃、系统休眠、设备重启、磁盘不足和权限变化。

对于多端产品，应列出端侧能力差异，而不是把“跨平台”写成一项笼统承诺。

**界面状态不能被直接当作真实业务状态。**

---

### 11. 技术选型、外部依赖与可行性证据

这一章回答：

> **为什么选择这些技术，它们是否真的满足要求？**

对于重要选型，应说明需求依据、候选方案、当前选择、关键代价、退出成本、维护责任和验证状态。

外部依赖还需要记录能力范围、版本、限额、许可约束、数据处理边界、失败方式以及替代路线。

技术验证应当有明确问题，例如：

> 在目标设备上，这种隔离方式能否满足兼容性和性能要求？

而不是“已经跑通官方示例，所以可用于生产”。

建议记录验证环境、测试代码版本、输入数据、测量结果、未覆盖条件和结论。

**可行性验证的结果应该允许推翻原方案。**

详细的重大选型理由可以放进 ADR；技术实现 PRD 保留决策摘要、适用条件和引用。

---

## C. 运行质量：安全、故障和规模变化时怎样工作？

### 12. 安全架构、权限执行与隐私保护

这一章回答：

> **保护什么，防范谁，控制在哪里真正生效？**

应从资产、威胁和信任边界出发，明确身份认证、授权、凭证管理、数据隔离、加密、审计和高风险操作控制。

不能只写“使用某种登录协议，所以系统安全”。

尤其要明确：界面检查之外，执行端是否再次鉴权；用户、Agent、服务和插件使用什么身份；凭证能否被任意组件读取；权限撤销后在途任务如何处理。

对于 Agent 系统，权限不能依赖模型自行判断。OWASP 明确建议在下游系统实施授权，对操作逐次执行策略校验，并限制扩展拥有的功能与权限。citeturn240257view3

隐私要求也要落实到具体数据路径：哪些内容可进入外部模型，哪些日志需要脱敏，谁能查看任务记录，数据保留与删除如何执行。

**“用户授权过”不等于“后续所有关联行为永久获得授权”。**

---

### 13. 故障模型、重试、恢复与外部副作用

这一章回答：

> **哪些东西可能失败，失败后怎样继续而不制造更大的错误？**

需要定义超时、重试次数、退避策略、负载限制、重复处理、隔离范围、恢复流程和必要的人工处理路径。

至少区分：

**明确没有执行、明确已经执行、执行结果未知。**

网络超时只说明调用方没有及时得到结果，不足以证明外部操作没有发生。安全重试需要明确的请求标识、幂等语义以及相关保留规则，而不只是给代码加一个重试循环。citeturn724000view3

还要区分不同恢复方式：

**重试**是再尝试某一步；**恢复**是从已知进度继续；**回滚**是撤销特定范围内的变化；**补偿**是执行新的业务操作来处理已有影响。

补偿不一定能恢复原始状态，也可能失败。Microsoft 的补偿事务指南明确讨论了并发变化、不可逆操作和补偿失败的处理问题。citeturn240257view1

**不要把“数据库支持事务”“队列保证投递”直接扩大成“所有外部行为保证恰好执行一次”。**

---

### 14. 性能、容量与资源隔离

这一章回答：

> **系统要承受什么工作负载，瓶颈在哪里，接近上限时怎么办？**

容量模型应描述请求量、任务到达速率、平均与长尾执行时间、并行任务数、数据增长、外部调用次数和突发负载。

不能只写“支持一百万用户”，因为不同用户行为对应的工作量可能完全不同。

应说明容量估算依据、测试目标、扩容条件、限流规则、队列上限和过载时的行为。

对于多用户、多 Agent 或多项目系统，还要定义资源公平性：一个任务能占用多少计算、内存、网络、存储和外部调用额度。

对于本地软件，应考虑后台任务对前台交互、设备功耗和磁盘空间的影响。

**性能预算需要分配到关键链路，不能让每个模块都声称自己很快，但整条用户流程仍然很慢。**

---

### 15. 可观测性、审计与运行支持

这一章回答：

> **出问题后，团队能否知道发生了什么、影响谁、从哪里恢复？**

应定义关键日志、指标、调用链、业务事件、告警、运行看板和问题诊断入口。

OpenTelemetry 将 traces、metrics、logs 等作为不同的遥测信号；它们需要围绕具体诊断和运行目标组织，而不只是“接入一个监控工具”。citeturn240257view4

建议通过稳定标识关联一次用户请求、业务任务、执行尝试、外部操作和最终产物。

还应区分：

**运行日志**用于排查系统问题；**业务记录**描述用户工作；**审计记录**证明谁在什么权限下做了什么。

三者可以关联，但不能随意混为一体。

这一章还要说明告警由谁处理，哪些事件必须升级，恢复操作需要什么权限，以及如何避免把凭证和敏感内容写入日志。

**“出了问题可以看日志”，不是充分的运行方案。**

---

## D. 交付与验证：怎样安全上线并持续演进？

### 16. 环境、构建、部署与软件供应链

这一章回答：

> **怎样从源代码得到可信、可追踪、可重复交付的运行系统？**

应说明开发、测试、预发布和生产环境的差异，配置与密钥的管理方式，基础设施创建方式，以及构建、发布和回退路径。

构建产物要能关联到代码、依赖、配置和版本；关键依赖需要记录来源和更新策略。

自动检查应覆盖项目适用的测试、安全扫描、依赖检查和接口兼容检查。

NIST SSDF 将安全开发覆盖到组织准备、软件保护、安全生产与漏洞响应，而不是只在上线前做一次安全测试。citeturn269150view2

对于使用 Agent 开发和测试的团队，还要明确测试环境是否允许真实发送、真实删除、真实支付或访问生产凭证。

**“测试通过”不能以对真实用户环境造成未授权影响为代价。**

具体分支管理、代码评审操作和日常协作流程可以在工作方式文档展开；这里明确交付必须经过哪些技术关口。

---

### 17. 数据迁移、版本兼容、升级与回退

这一章回答：

> **系统变化之后，旧数据、旧客户端和正在执行的工作怎么办？**

需要覆盖数据结构变更、历史数据回填、接口兼容、客户端版本差异、插件版本、配置变更和旧能力下线。

不能只写“发布失败就回滚代码”。

必须检查：新版本是否已经写入旧版本无法理解的数据？已有任务是否依赖新版本逻辑？回退后，重复处理风险是否增加？

对于数据库变更，可以在总体方案中明确兼容期和迁移策略，再由详细设计给出脚本与操作步骤。

对于灾难恢复，要定义可接受的数据损失范围、恢复时间目标、备份范围和恢复演练要求。

**备份存在，与已经证明能够恢复，是两种不同状态。**

---

### 18. 验证策略、证据要求与发布准入

这一章回答：

> **哪些证据能够支持“这套实现满足要求”的判断？**

这里应定义验证层次和范围，例如模块测试、接口契约测试、集成测试、端到端测试、性能测试、安全测试、故障注入和恢复演练。

但不必把全部测试步骤重复写进技术实现 PRD。详细数据、环境、操作步骤和预期结果，由后续测试规格承接。

每项关键技术要求应能关联到验证方法、责任人、证据位置和当前结果。

要特别检查跨模块场景：单个服务都通过测试，不代表任务从创建到真实交付的整条链路正确。

发布准入还应覆盖监控、告警、容量、支持责任和应急控制。Google 的生产就绪评审将架构依赖、监控、应急响应、容量、变更管理和性能共同纳入运行准备，而不只检查功能。citeturn240257view0

**测试计划是准备怎么证明；测试报告才记录已经证明了什么。两者不能混写。**

---

## E. 工程约束：成本、依赖和不确定性怎样受控？

### 19. 成本模型与预算控制

这一章回答：

> **系统做得出来之后，是否用得起、维护得起？**

建议分别估算研发与维护成本、固定基础设施成本、单次执行成本、存储与网络成本，以及失败重试和人工处理带来的成本。

对于 Agent 产品，不能只计算一次模型调用费用。还应包括上下文增长、多轮调用、工具使用、核验、失败任务和重复尝试。

比“每次请求成本”更有意义的指标，往往是**每个成功完成的用户任务所消耗的总成本**。

模型应写清使用假设、计价依据、价格日期、估算区间和敏感因素。

运行时还需要预算控制：如何计量、预留、限制并发消耗、处理达到上限的任务，以及避免多个任务各自认为“还有预算”。

**成本应该影响架构选择，而不是等账单出现后才补救。**

---

### 20. 实施分解、依赖关系与集成顺序

这一章回答：

> **技术方案怎样拆成能够并行推进、最终集成的工作？**

在技术实现 PRD 中，应至少有子系统交付物、主要依赖、技术负责人、风险验证顺序和阶段集成目标。

详细工期和每日安排可以放到执行计划中，但这里必须回答哪些工作依赖哪些契约，哪些风险需要先验证，哪些模块可以并行建设。

我建议阶段目标按可运行的端到端能力定义，而不只是：

> 第一阶段完成界面，第二阶段完成后端。

例如，先打通一条真实任务路径，并证明它具备权限检查、持久化、结果读取和基本失败恢复，再扩展更多执行方式。

**并行开发的前提是关键契约明确，不是把所有工作同时交给不同 Agent。**

---

### 21. 风险、技术债、决策索引与变更控制

这一章回答：

> **哪些地方还不知道，接受了什么代价，什么变化会让方案失效？**

每个关键风险应记录发生条件、影响、验证或缓解办法、负责人、解决时点和备选方案。

例如，“某平台可能无法支持目标权限范围”，就应明确由什么验证来关闭风险，以及验证失败后产品范围或实现方案如何调整。

技术债也应明确：暂时省略了什么、为什么接受、会造成什么后果、在什么条件下必须处理。

重要决策通过 ADR 保存历史和依据；技术实现 PRD 维护当前有效结论，避免把已经被替代的方案继续当作现行架构。

发生变化时，应检查产品承诺、接口、数据、权限、测试、成本和发布方式是否受到影响。

**不能因为实现困难，就由工程默默把“必须支持”改成“尽量支持”。**

---

## F. 按产品类型增加专项技术规格

### 22. AI、Agent、平台和操作系统专项要求

这些内容不是每个项目都需要，但对你的 Agent-native 项目尤其重要。

### 对 AI / Agent 系统，需要增加什么？

建议至少写清以下技术契约：

| 领域 | 必须明确的问题 |
|---|---|
| **模型接入** | 能力要求、版本、上下文限制、结构化输出、超时和替代条件 |
| **Agent 定义** | 身份、使命、配置版本、上下文范围、可调用能力和权限 |
| **Harness 接入** | 支持什么生命周期、状态、暂停、取消、恢复和产物接口 |
| **调度与路由** | 先满足哪些权限与能力限制，再怎样权衡质量、成本和速度 |
| **工作流执行** | 步骤依赖、并行规则、等待条件、检查点、重试预算和终止条件 |
| **上下文与记忆** | 来源、权限过滤、更新、纠正、压缩、删除与跨任务隔离 |
| **工具与行动** | 参数校验、授权执行点、重复调用和外部副作用处理 |
| **多 Agent 协作** | 共享什么、不共享什么，谁拥有写入权，冲突如何处理 |
| **结果核验** | 工具返回、产物存在和目标达成分别依据什么判断 |
| **质量评测** | 任务分类、测试数据、评判标准、关键失败类型和版本回归 |

这些是我建议对 Agent 系统增加的工程约定。安全边界尤其需要放在模型之外实施，而不是仅通过提示词要求模型遵守；这与 OWASP 对最小权限和下游授权检查的建议一致。citeturn240257view3

还要避免三个概念混淆：

**统一模型入口，不等于统一 Harness。**

**统一显示执行记录，不等于统一掌握执行控制权。**

**接入了某个外部 Agent，不等于它支持暂停、恢复、迁移或完整审计。**

这些能力需要通过适配契约和实际验证逐项确认。

### 对真正可安装的操作系统，需要增加什么？

若用于你的操作系统项目，不能只写桌面界面与 Agent 服务。

还应明确底层系统复用范围、启动与安装、驱动和硬件支持、进程与资源管理、文件系统、网络、用户与权限、应用兼容、系统更新、恢复环境，以及本地特权组件的隔离边界。

其中每项都要标明：

**继承已有能力、修改已有能力，还是自行实现；支持到什么范围；如何验证。**

这样才能分清“产品拥有这项能力”和“团队亲自重写这项能力”，也能防止把一个桌面应用误写成完整操作系统的实现方案。

# 三、每一项关键技术需求，应该怎样写？

前面的章节解决整体覆盖；下面这个格式解决单项要求的可执行性。

我建议采用：

| 字段 | 内容 |
|---|---|
| **编号与名称** | 能够唯一引用的技术要求 |
| **来源** | 对应产品需求、质量要求或必要约束 |
| **规范性要求** | 在什么条件下，系统必须产生什么行为或保持什么保证 |
| **适用范围** | 哪些组件、对象、环境和版本适用 |
| **实现策略** | 准备依靠什么机制满足要求 |
| **保证边界** | 在什么条件下成立，哪些情况不能保证 |
| **责任归属** | 实现、集成、验证与运行责任 |
| **验证与证据** | 如何检查，证据在哪里，当前验证结果如何 |
| **关联材料** | ADR、详细设计、接口规格和测试规格 |
| **状态与风险** | 已确定、待验证、已实现或已验证，以及剩余问题 |

尤其要把下面三件事分开：

> **要求：必须做到什么。**  
> **方案：准备怎样做到。**  
> **证据：已经通过什么验证，支持哪些结论。**

这比“系统采用先进架构，确保高可靠”更接近一份真正能够指导工程的文档。

# 四、用上一轮的邮件场景，看技术实现 PRD 应该多写什么

沿用上一轮的产品要求：

> 用户选择一个账户、一名收件人和一份附件，由 Agent 准备邮件；本例采用每次发送前确认的策略。结果未知时，不得伪装成功或盲目重复发送。

下面是**示例技术方案**，不是对某个已有实现的描述。

## 1. 从产品要求派生技术要求

| 编号 | 技术要求 |
|---|---|
| TR-MAIL-001 | 只有任务与操作意图成功持久化后，系统才返回相应的接收确认 |
| TR-MAIL-002 | 同一用户使用同一请求标识提交相同请求时，不创建重复业务操作；内容不同则报告冲突 |
| TR-MAIL-003 | 确认记录必须绑定发送账户、收件人、正文和附件的具体版本 |
| TR-MAIL-004 | 实际提交发送前，由执行网关校验当前授权和确认的有效性 |
| TR-MAIL-005 | 外部发送结果不明确时，保存“结果未知”，禁止按普通失败流程直接重新发送 |
| TR-MAIL-006 | 发送状态必须依据适用的外部证据更新，不能由 Agent 的自然语言回复直接决定 |

这里，“防重复”已经不再是一句产品愿望，而是形成了请求语义、数据约束和执行责任。

## 2. 明确责任与关键数据

示例中可以划分任务管理、授权检查、发送适配、结果核对和产物记录等逻辑职责，不必因此全部拆成独立服务。

需要保存的关键关系包括：

**任务标识、业务操作标识、内容版本、确认记录、授权依据、执行尝试、外部请求标识和结果证据。**

必须区分一次业务发送与多次技术执行尝试。重试不能悄悄变成一个新的业务发送意图。

## 3. 明确持久化与执行边界

一种候选方案是将任务状态与待发送事件在同一数据库事务中记录，再由执行组件读取并处理。

这种安排需要继续定义事件去重、并发领取和结果写回机制；它解决的是内部状态与事件协调问题，并不自动提供外部邮件发送的恰好一次保证。事务发件箱仍需处理重复消息这一点，在 AWS 的模式说明中也有明确提示。citeturn240257view2

## 4. 把重要故障写成明确行为

| 故障 | 技术方案必须规定的行为 |
|---|---|
| 客户端重复提交 | 返回既有操作或明确冲突，不新增重复发送意图 |
| 数据已提交，但事件尚未交付 | 根据持久化记录恢复内部交付，而不是要求用户重新创建任务 |
| 执行器在外部提交后崩溃 | 保留可能已经发送的事实，进入核对流程，不直接再次发送 |
| 确认之后内容被修改 | 原确认不再适用于修改后的内容 |
| 执行前权限被撤销 | 阻止尚未提交的受限操作；已经提交的操作按已定义边界处理 |
| 供应商结果无法确定 | 使用其可靠的查询或幂等能力核对；没有足够保证时保留未知并进入人工核对流程 |

**“暂时没有查到邮件”不能被直接当作“肯定没有发送”。**

外部服务是否支持安全重试、如何识别相同请求、标识保留多久，都属于必须确认的依赖契约，而不是由本地生成一个随机 ID 就能解决的问题。citeturn724000view3

## 5. 定义需要提交的证据

这一项功能的验证，应覆盖重复提交、并发处理、事件重复交付、执行器崩溃、权限变化、内容版本变化和外部结果未知。

证据可以包括测试结果、状态记录、调用记录、数据库检查和外部系统中的可核对结果。

**这才是技术实现 PRD 比产品 PRD 多出来的核心内容：不仅说明应该怎样表现，还说明依靠什么结构与机制保持这种表现，以及保证在哪里结束。**

# 五、开工前，怎样判断技术实现 PRD 已经足够好？

我建议从三个不同阶段判断，而不是只设一个含糊的“文档通过”。

| 阶段 | 应具备的条件 |
|---|---|
| **可以进入详细设计** | 产品范围、技术目标、架构边界、关键依赖和高风险问题已有明确结论或验证计划 |
| **某个范围可以进入实现** | 该范围的关键契约、数据所有权、状态规则、失败行为与验证要求已经清楚 |
| **某个版本可以进入生产** | 实现和验证证据满足准入要求，监控、容量、迁移、恢复与运行责任准备到位 |

一份可以进入实现的技术 PRD，至少应经得住下面这些追问：

**每项产品承诺由谁兑现？各模块的接口与数据含义是否一致？故障时有没有明确行为？关键权限在哪里执行？质量目标怎样测量？依赖失效怎么办？升级如何保护已有数据与任务？尚未解决的问题由谁负责？**

还需要强调：

**大项目并不需要在开工前，把未来几年所有模块的字段与算法全部写死。**

我建议先明确全局约束和关键契约，把当前交付范围细化到可以实施；远期范围保留清楚的目标、依赖与假设。需求、架构和设计应随证据迭代，而不是把一次早期文档评审当成永久正确的结论。NASA 的系统设计流程同样强调这种迭代与逐层细化。citeturn269150view0

---

## 最后的判断标准

> **优秀的技术实现 PRD，应该让一个没有参与早期讨论的工程负责人，看完后能够判断：系统要保证什么、准备怎样实现、各部分怎样协作、哪里可能失败、如何验证，以及需要哪些资源才能交付。**

它不需要替代所有详细设计和测试文档，但不能把决定项目成败的关键问题留成一句“后续实现时处理”。

**产品 PRD 定义产品承诺；技术实现 PRD 则要把承诺变成有机制、有边界、有责任人、有验证路径的工程约定。**


# 第三部分 · ADR

# 第三部分：一个优秀的 ADR，应该包含什么？

**优秀的 ADR，要把一项重要技术选择背后的依据、取舍和代价保存下来，让未来的团队既不会盲目推翻它，也不会因为“以前就是这么做的”而不敢改变。**

ADR 是 **Architecture Decision Record，架构决策记录**。它记录一项具有架构意义的决策及其理由；一个项目通常会积累多份 ADR，共同组成决策日志，而不是把所有决策塞进一份大文档。citeturn464779view1

你可以把它最核心的问题记成：

> **在当时的背景和约束下，我们为什么选择 A，而不是 B？这个选择要求我们遵守什么、接受什么代价，以及什么变化会让它需要重新审视？**

这里有一个与前两轮非常重要的区别：

**产品 PRD 和技术实现 PRD 需要覆盖产品或系统的整体范围；单份 ADR 则应该聚焦一项重要决策。**

---

## 一、先明确：ADR 负责什么，不负责什么？

沿用前两轮的文档分工：

| 文档 | 主要负责什么 |
|---|---|
| **产品 PRD** | 定义用户问题、产品能力、业务规则和产品承诺 |
| **技术实现 PRD** | 定义技术要求、总体架构、关键机制、系统契约和实现边界 |
| **ADR** | 记录一项重要架构选择，以及选择依据、被放弃的方案和接受的后果 |
| **SDD** | 展开具体模块、接口、数据结构、算法和运行流程的详细设计 |
| **测试与验收规格** | 定义怎样通过测试和证据证明实现满足要求 |
| **工程工作方式** | 定义谁参与决策、怎样评审、如何开发集成，以及发现偏离时如何处理 |

例如，同样讨论“任务中断后恢复”：

**技术实现 PRD** 会说明系统采用怎样的持久化、执行与恢复机制。

**ADR** 则要解释：为什么恢复状态由统一任务服务持有，而不是由各个 Agent 自己保存？当时考虑了哪些方案？为什么接受统一服务带来的依赖和维护成本？

**SDD** 再写具体的数据结构、状态转换和恢复协议。

Microsoft 的 ADR 指南特别提醒：不要把决策记录写成设计指南；详细材料可以链接出去，但决策本身及其理由应该能够独立读懂。citeturn464779view3

**所以，ADR 不是技术实现 PRD 的缩写版，也不是把已经选好的技术重新介绍一遍。**

---

## 二、什么事情值得写 ADR？

不是所有代码修改都需要 ADR。

判断的重点，是这项选择是否影响系统结构、关键质量、模块关系、公共接口，或者会带来显著的改变成本。AWS 的 ADR 指南也把结构、非功能要求、依赖、接口和重要构建方式列入记录范围。citeturn977886view0

对于你的项目，我建议重点记录这几类选择：

| 决策类型 | 值得记录的问题示例 |
|---|---|
| **系统结构** | 采用模块化单体还是拆分服务？哪些组件必须独立运行？ |
| **权威与所有权** | 谁拥有任务状态？谁有权修改共享数据？ |
| **安全边界** | Agent 的授权由谁执行？插件能否取得原始凭证？ |
| **执行与可靠性** | 长任务由谁恢复？重复操作和结果未知如何处理？ |
| **接口与兼容** | 外部 Harness 通过什么能力契约接入？哪些能力不做统一？ |
| **关键依赖** | 哪些能力自研，哪些依赖外部框架或服务？为什么？ |
| **难以逆转的选择** | 数据标识、存储格式、应用兼容路线、系统升级机制如何确定？ |

反过来，普通按钮文案、局部变量名称、没有架构影响的内部重构，通常放在相应规格或代码评审中即可。

但不要机械地认为“低层细节不属于架构”。一个看似很小的规则，如果决定跨服务数据是否一致，也可能值得单独记录。

### 一份 ADR 应该多大？

我的建议是：

> **能够作为一个整体被接受、被反对和被替代的一项决策，写成一份 ADR。**

例如，“统一行动服务负责外部操作状态”可以包含必要的职责边界，因为这些边界共同构成同一个决定。

但“选什么数据库”“采用什么权限模型”“选择什么前端框架”，如果可以独立改变，就不应该仅因发生在同一次会议里而合成一份。

# 三、一个优秀 ADR 的完整内容

先区分**基础结构**和**复杂决策的增强内容**。

经典 Nygard 模板包含五项：**标题、状态、背景、决策、后果**。MADR 等模板进一步加入候选方案、比较理由、决策参与者和落实确认等内容。不存在要求所有项目填写同样几十个字段的唯一模板。citeturn467165view3

下面这十二项，是我建议你用于大项目的审查结构。

**十二项问题需要考虑，不代表每份 ADR 必须写成十二章。简单决策可以合并；复杂证据可以放附件。**

---

## 01. 决策标识、状态、负责人和适用范围

这一部分回答：

> **这是什么决定，现在处于什么状态，对谁、对什么版本生效？**

建议包含以下信息：

| 信息 | 应该说明什么 |
|---|---|
| **编号和标题** | 能够稳定引用，并从标题看出决策主题 |
| **决策状态** | 提议中、已接受、已拒绝、已被替代等 |
| **关键日期** | 提出时间、决策时间，以及必要时的生效时间 |
| **作者／负责人** | 谁负责整理依据、推动评审和跟进后续问题 |
| **决策者** | 谁有权接受这项选择 |
| **适用范围** | 哪个产品、模块、端、环境或版本适用 |
| **关联记录** | 依赖、替代或限制了哪些既有决策 |

标题要有辨识度。

不够好的标题是：

> ADR-007：Agent 架构。

更好的标题是：

> ADR-007：由统一行动服务持有邮件发送操作的权威状态。

还需要把**决策状态与实施状态分开**。

“Accepted，已接受”表示已经决定采用这个方向，不表示代码已实现、生产已部署或验证已通过。我建议实施进度与验证结果放在关联工作项中维护，ADR 保存当时的决定及其适用条件。

AWS 的流程也将 ADR 的接受记录与后续代码、设计和实现中的使用区分开来。citeturn662167view0

---

## 02. 决策问题与范围边界

这一部分回答：

> **我们现在究竟要决定哪一件事？**

不要一上来就写：

> 我们决定采用某框架。

先把问题说清楚：

> 多种执行环境都可以发起同一类外部操作时，谁负责保存业务操作状态、协调恢复，并防止不同执行者作出互相矛盾的判断？

接着明确**本次决定什么，不决定什么**。

例如，本次决定邮件操作状态的所有权；不决定模型供应商，不决定数据库品牌，也不改变产品既有的用户授权规则。

这一步有两个好处：评审不会无限扩散，后续团队也不会把一项局部决定误读成整个系统的永久原则。

**“选择一个统一平台”太宽；“确定某一类状态由谁拥有”才开始具备可讨论的边界。**

---

## 03. 背景、约束、假设与证据

这一部分回答：

> **这个问题为什么在现在出现？我们知道什么，还不知道什么？**

我建议明确区分四种信息。

**已知事实。**  
已有系统怎样运行，已经观察到什么问题，产品已明确要求什么。

**硬约束。**  
哪些条件不能由这项架构选择自行改变，例如必须兼容某接口、数据不能离开规定环境。

**工作假设。**  
哪些判断暂时作为设计前提，例如预计会接入多个外部执行环境，但具体调用分布尚未测量。

**未知事项。**  
哪些关键能力还没验证，可能改变结论。

例如：

> “预计某方案能满足目标吞吐”是设计假设，不是已经完成的性能证明。

对于引用的证据，建议记录来源、版本或日期、测试环境、结论及局限。外部基准与自己的实际负载不同，就不能直接当作本项目性能保证。

还要保留一个很重要的事实：

**有时我们选择一个方案，是因为已有团队更熟悉它、当前交付窗口更适合它，而不是因为它在所有方面都更优秀。**

这些条件应当写出来，而不是用“行业最佳实践”掩盖真实原因。

---

## 04. 决策驱动因素与优先顺序

这一部分回答：

> **我们依据什么判断方案好坏？这些目标冲突时，谁优先？**

“性能、成本、稳定性、安全性都很重要”，不足以支撑选择。

应该明确哪些属于**必须满足的门槛**，哪些属于**可权衡的偏好**。

例如，可以在一项外部执行决策中约定：

> 先满足授权与操作正确性，再比较恢复能力和维护复杂度；在这些条件满足之后，才比较响应速度与成本。

这里的顺序是示例，不是所有系统的通用排序。

关键在于：**不能让某方案凭较低成本，抵消它没有满足安全硬约束的问题。**

我建议把驱动因素写成可以影响结论的句子：

> 由于当前团队无法维护多套独立恢复实现，本次优先降低重复维护范围。

这比“要求可维护性强”更有决定作用。

---

## 05. 真正考虑过的候选方案

这一部分回答：

> **我们有哪些现实可行的选择？**

每个候选方案至少要说明基本思路、适用范围、关键依赖，以及它的真正优势。

不要为了证明预选方案正确，故意写两个明显糟糕的陪衬方案。

我建议在有意义时，保留**维持现状、推迟决定或缩小范围**等选项。例如，暂时不引入一个复杂组件，可能比提前建设更符合当前需求。

但“缩小范围”如果改变产品承诺，需要产品侧同意，不能由 ADR 单方面完成。

也不需要机械凑出三个方案。若只有一个方案满足硬约束，应说明其他路线为何被排除，而不是编造竞争者。

MADR 将候选方案和各自的利弊作为重要内容，目的就是让未来读者理解选择背后的真实取舍。citeturn662167view2

---

## 06. 方案比较与证据强度

这一部分回答：

> **这些方案在同一组条件下表现如何，我们对比较有多大把握？**

建议按前面的驱动因素比较，而不是对每个方案使用不同标准。

例如，不能拿 A 的演示环境性能，与 B 的高负载生产数据直接比较；也不能给 A 只计算订阅费用，却给 B 计算全部维护成本。

比较中应区分：

**已验证的能力、合理推断的收益，以及尚未验证的主张。**

量化评分可以辅助讨论，但不能制造虚假的精确性。

“方案 A 得 8.7 分，方案 B 得 8.4 分”，如果权重和数据都没有依据，并不会比清楚说明取舍更客观。

我建议对关键结论写明：

> 目前支持这个判断的证据是什么？证据覆盖了哪些条件？哪项未知最可能推翻它？

Microsoft 的指南也建议记录决策的信心程度，以便后续识别哪些选择更值得重新审视。citeturn464779view3

---

## 07. 清晰、可执行的决策结论

这一部分回答：

> **我们到底决定了什么？**

这是 ADR 中最不能模糊的地方。

不够好的写法：

> 建议尽量统一状态管理，未来可以考虑接入更多框架。

更好的写法：

> 本提案采用统一行动服务保存邮件业务操作的权威状态。Agent 和 Harness 通过该服务创建、查询和恢复操作，不直接修改最终发送状态。供应商适配器负责返回供应商侧的结果证据。

处于 Proposed 状态时，要明确这是**待批准的提案结论**；接受以后，它才成为适用范围内的已批准决定。

结论还应说明必要的例外：哪些已有组件暂时豁免，豁免由谁批准，何时结束。

AWS 的指南强调，决策部分应直接说明团队采用什么，而不是停留在含糊的建议性表达。citeturn977886view0

一个实用句式是：

> **在【背景】下，为满足【主要要求】，我们选择【方案】，不采用【主要替代方案】，因为【决定性理由】，并接受【主要代价】。**

---

## 08. 选择理由与关键取舍

这一部分回答：

> **为什么是这个方案，而不是最有竞争力的那个替代方案？**

“决策结论”说明选择了什么；“选择理由”必须解释为什么。

建议至少回答：

所选方案满足了哪些关键约束？最大的竞争方案输在哪里？当前选择最大的弱点是什么？为什么仍然可以接受？

例如：

> 我们不是认为分散式状态管理永远错误，而是当前系统需要跨执行环境交接任务，且缺乏维护多套一致恢复协议的资源。因此，本阶段优先统一操作状态，接受新增共享组件的维护责任。

这比“统一服务更先进、更可靠”有用得多。

特别需要记录：

**我们优化的是哪个阶段、哪个场景、哪类负载，而不是宣布某种技术普遍优于其他技术。**

未来背景变化时，团队才能判断原理由是否仍然成立。

---

## 09. 正面后果、负面后果与剩余风险

这一部分回答：

> **接受这项选择以后，我们获得什么，又承担什么？**

后果不能只写收益。

经典 ADR 结构明确要求记录正面、负面和中性后果，而不是把它写成方案宣传材料。citeturn464779view0

建议这样区分：

| 类型 | 应该记录什么 |
|---|---|
| **正面后果** | 改善了什么能力，减少了什么问题 |
| **负面后果** | 新增的成本、依赖、性能损耗、迁移负担或限制 |
| **中性变化** | 职责重新分配、接口需要变化、工作方式需要调整 |
| **剩余风险** | 采取措施后仍然无法消除的风险和不确定性 |

例如，统一行动服务可能减少恢复规则的重复实现，但也增加共享组件的故障影响范围。

不能只写“通过高可用解决风险”。还要说明高可用方案是否已确定、是否已验证，以及仍然有哪些无法保证的情况。

我建议对重要负面后果关联后续负责人或工作项：

> 接受新增运维责任，由运行负责人建立相应监控与恢复方案；未完成前，不开放对应生产能力。

**“我们接受这个代价”必须意味着有人知道如何承担，而不只是把它写在文档里。**

---

## 10. 实施约束与落实确认

这一部分回答：

> **后续设计和代码怎样证明自己遵守了这个决定？**

这里不需要复制完整 SDD 或测试方案，但应列出由决策直接产生的约束。

例如：

> 邮件发送状态只能由指定服务更新。  
> Agent 不能绕过行动接口直接使用生产发送凭证。  
> 新增供应商适配器必须遵守同一组状态和结果证据契约。

然后说明怎样确认这些约束得到落实：设计评审、接口契约检查、代码依赖检查、故障测试或其他方法。

MADR 专门设置了 Confirmation，用于说明设计和实现是否符合 ADR，以及如何检查。citeturn977886view3

我建议再区分两种确认：

**符合决策。**  
实现是否真的采用了规定的结构和约束？

**达到预期。**  
采用这个结构之后，是否真的改善了当初关注的问题？

前者通过，不代表后者必然通过。

如果代码符合 ADR，但实际效果不佳，应重新评估决策，而不是因为“已经按文档做了”就停止检查。

---

## 11. 重新审视条件、可逆性与退出路径

这一部分回答：

> **什么时候应该重新考虑？改变它要付出什么代价？**

这一项是我建议复杂项目特别补充的内容。

不要只写“未来视情况调整”，而应记录可识别的变化。

例如，目标规模超出已验证范围，供应商能力发生关键变化，本地离线要求改变原部署假设，或者实际维护成本明显偏离估计。

还要写清改变决策涉及什么：

是修改配置即可，还是必须迁移数据、重写适配器、改变公共接口，甚至要求用户重新授权？

**可替换不等于无成本，也不等于立即可以回滚。**

如果当前方案具有明显锁定成本，就应提前记录可导出的数据、需要保留的接口边界和退出障碍。

对于暂缓的决定，我建议写清再决定的时间或触发事件，以及等待期间允许采用的临时方案。不能把“以后再说”包装成经过管理的架构选择。

---

## 12. 评审、异议、关联决策与历史

这一部分回答：

> **谁参与了选择，哪些意见尚未解决，它与其他决定是什么关系？**

应记录谁负责起草，谁提供专业意见，谁作出决定，以及哪些受影响的团队需要知情。

**作者不一定是最终决策者，最终决策者也不需要永远是 CTO。**

我建议根据影响范围分配决策权：局部模块由相应负责人处理，跨模块或重大安全边界按既有治理规则处理。AWS 同样鼓励团队成员创建和拥有 ADR，而不是把全部架构研究集中在一个人身上。citeturn662167view1

重要异议应留下摘要：

> 反对意见是什么？为什么没有采用？什么新证据会使这个意见重新成为决定性因素？

这不是把整场会议逐字抄进文档，而是保留可能影响未来判断的内容。

关联关系则要说明：本记录依赖什么、细化了什么、替代什么，或在哪个限定范围构成例外。

**两个 ADR 出现冲突时，不能简单以“编号更大”或“修改时间更新”决定谁优先。应检查范围、生效条件和明确的替代关系。**

# 四、ADR 的生命周期应该怎样管理？

## 1. 先有提案，再有已接受的决定

建议采用简单而明确的状态约定：

| 状态 | 含义 |
|---|---|
| **Draft：草稿** | 问题和方案尚在整理，不能作为已批准约束 |
| **Proposed：提议中** | 已形成可评审提案，等待决定 |
| **Accepted：已接受** | 有权决策者已经接受，在规定范围内生效 |
| **Rejected：已拒绝** | 提案没有被采用，应保留拒绝理由 |
| **Superseded：已被替代** | 新记录已经改变原决定，应链接到替代记录 |
| **Deprecated：已弃用** | 不再作为继续采用的方向；替代与迁移情况需另行说明 |

这是一套建议约定，不是要求所有团队使用相同状态名称。

还要区分两件事：

**接受的 ADR 中没有被选中的候选方案**，不需要每个都新建一份 Rejected ADR。

只有曾作为独立提案进入决策流程、后来被拒绝的记录，才需要单独保留其拒绝状态。

## 2. 决策改变，要新增记录，而不是改写历史

AWS 和 Microsoft 的指南都强调：已接受的决策应保留，方向变化时通过新的 ADR 替代旧记录，并建立链接。citeturn662167view0turn464779view3

例如：

> ADR-007 原来规定操作状态集中管理。  
> ADR-021 因新的离线要求，决定在明确范围内采用本地权威状态。  
> ADR-021 解释变化依据，并说明它替代 ADR-007 的哪些部分、对什么版本生效。

我建议项目约定允许更新状态和替代指针，或追加带日期的说明，但不应把原来的选择理由悄悄改成现在的理由。

**历史记录解释过去为什么这样做；当前有效索引告诉团队现在应该遵守什么。**

新决策被接受，也不代表旧部署瞬间完成迁移。实际迁移范围和进度仍需关联到执行计划。

## 3. ADR 必须可发现、可引用、可检查

我建议在项目中设置统一位置，例如：

```text
docs/architecture/decisions/
```

通过索引展示编号、主题、状态、适用范围、负责人和替代关系。

可以存储在 Git 或具备历史与权限能力的文档系统中；AWS 的指南同时列出了代码仓库和 Wiki 这两种常见选择。citeturn662167view1

后续设计、代码评审和测试应引用相关 ADR，但不必让每个微小改动都经过一轮架构委员会审批。

**ADR 的目标是减少反复争论和隐性偏离，不是给所有工作增加同样的审批负担。**

# 五、沿用邮件场景：一份 ADR 应该怎么写？

下面是一份教学示例，展示内容和边界。**它不是你项目已经批准的技术选型，也没有虚构测试结果。**

## ADR-007：由统一行动服务持有邮件发送操作的权威状态

### 基本信息

**状态：**Proposed。  
**适用范围：**通过系统触发的邮件发送与恢复，不扩展到所有外部工具。  
**负责人：**行动执行模块负责人，待实际指定。  
**决策者：**按项目既有决策权限指定。  
**实施与验证：**尚未完成。

### 背景与问题

本示例假设多个 Agent 或 Harness 可以参与一项工作，因此同一发送任务可能经历执行者切换、进程中断和恢复。

外部请求超时后，调用方可能无法判断操作是否已经发生；盲目重试可能产生重复副作用。AWS 的幂等 API 说明也讨论了这类结果不明与重试问题。citeturn977886view1

本次需要决定：

> **邮件业务操作状态及其恢复责任，应由 Agent、供应商连接器，还是统一行动服务持有？**

本次不决定数据库品牌，不改变用户授权策略，也不重新定义邮件产品功能。

### 决策驱动因素

本示例首先要求状态与操作正确性，其次要求跨执行环境的一致恢复。

在满足这些要求后，再比较维护范围、供应商接入成本和运行复杂度。

### 候选方案

| 方案 | 主要优势 | 主要代价 |
|---|---|---|
| **A：每个 Agent／Harness 自己持有状态** | 执行环境自治，局部实现自由 | 需要多套一致的恢复实现，跨环境交接更复杂 |
| **B：每个供应商连接器持有独立状态** | 状态与供应商能力靠近，连接器可独立演进 | 跨供应商行为与状态汇总需要额外协调 |
| **C：统一行动服务持有业务状态，适配器处理供应商差异** | 状态所有权与跨环境恢复规则集中 | 新增共享组件及其故障、隔离和运维责任 |

这些优劣是示例中的设计分析，不是已经完成的性能或成本测量。

### 决策提案

**提议采用方案 C。**

统一行动服务拥有邮件业务操作的权威状态。Agent 和 Harness 提交意图、查询进度，不直接决定最终发送状态。

供应商适配器负责调用供应商能力，并将可核对的结果证据返回给行动服务。

这里的“统一”指**统一责任与状态语义**，不要求只有一个进程或单台机器。

### 选择理由

本示例最重视跨执行环境交接时的一致性。

相较方案 A，方案 C 将恢复规则从各个 Harness 中分离出来。相较方案 B，它减少了业务状态分散在不同供应商实现中的情况。

我们因此优先选择统一业务状态，接受新增共享组件，而不是认为集中式方案在所有场景都优于分散式方案。

### 后果与剩余风险

预期收益是统一状态与恢复语义，并减少不同执行环境对同一操作作出冲突判断的机会。

接受的代价是共享组件的维护、访问控制和故障影响范围；部分原本能直接发送邮件的 Agent，也需要改用规定接口。

这一决定**不会凭空提供供应商没有承诺的幂等能力，也不能消除所有外部结果未知的情况**。

具体供应商的请求标识、有效期和安全重试边界仍需要验证。安全重试依赖明确的服务契约，不是本地生成一个 ID 就能保证。citeturn977886view1

### 实施约束与确认

后续详细设计需要实现操作标识、状态所有权、结果证据关联，以及适配器契约。

验证需要覆盖：不同执行者重复恢复同一操作、外部提交后执行器崩溃，以及返回结果不明时的处理。

设计和测试应证明实现遵守所选边界，但不能把有限测试写成“任何条件下绝不重复”的无限保证。

### 重新审视条件

若离线需求改变状态权威位置，实际负载暴露出不可接受的瓶颈，或共享组件的隔离成本超出预期，应重新比较这些方案。

容量、供应商契约和故障隔离尚未验证；这些事项必须由相应负责人在实施或发布准入前按风险完成。

---

这份示例没有展开数据库表、完整接口字段和全部状态机，因为那些属于后续设计。

但它已经回答了 ADR 最重要的问题：

**为什么由统一服务持有状态，为什么没有选择另外两种责任划分，接受了什么代价，以及什么变化可能推翻当前选择。**

# 六、对你的人＋多 Agent 工程团队，还应该加什么约束？

在你的工程体系里，我建议让 ADR 同时服务于人和执行 Agent，但不要把它变成一份“Agent 永远照做”的提示词。

研究 Agent 可以整理候选方案和证据，评审 Agent 可以寻找反例，作者 Agent 可以起草 Proposed 记录；最终接受应遵循项目已有的决策权限，不能因为几个 Agent 互相表示同意，就伪装成负责人已经批准。

实施 Agent 应根据任务范围读取**适用的已接受决策及其替代关系**，而不是把历史目录里的所有 ADR 当成同时有效。

发现任务与有效 ADR 冲突时，应明确指出冲突，进入已有的例外或变更流程，不能悄悄换技术路线。

还需要保留两个边界：

**ADR 说明为什么采用某种权限架构，不会自动授予 Agent 外部操作权限。**

**ADR 可以引用验证证据，但模型生成的“测试通过”文字，不是实际测试证据。**

这能让 ADR 成为约束工程行为的依据，而不是又一批无人检查的文档。

# 七、怎样判断一份 ADR 已经足够优秀？

我建议用下面的检查表审查，而不是看它写了多少页。

| 检查问题 | 不合格信号 |
|---|---|
| **是否只有一个明确的核心决定？** | 多项可以独立变化的选择混在一起 |
| **是否解释了当时的背景与约束？** | 只介绍技术，没有说明为什么现在需要它 |
| **是否比较了现实可行的替代方案？** | 所选方案全是优点，其余全是缺点 |
| **是否给出了决定性理由？** | 只有“先进、成熟、最佳实践”等泛泛表述 |
| **是否诚实区分事实、假设与未知？** | 把预期、供应商宣传或演示结果写成生产保证 |
| **是否记录了代价与剩余风险？** | 只有收益，没有后续责任 |
| **是否能指导后续实现与检查？** | 读完仍不知道哪些行为符合或违反决定 |
| **是否能判断何时重新审视？** | 既没有适用条件，也没有改变理由 |
| **是否保留审批与替代关系？** | 无法判断是提议、已接受，还是早已失效 |

最后还要提醒一点：**ADR 不是必须在开工前一次写完的整套答案。**

架构决策会随项目演进不断出现。Nygard 的原始说明也强调，决策不会全部发生在项目开始时，并主张短小、聚焦、便于未来开发者理解的记录。citeturn464779view0

我的建议是：当前实施范围依赖的关键决定先明确；不影响当前工作的远期选择，不必为了“文档齐全”过早锁死。

---

## 最后，把优秀 ADR 的标准压缩成一句话

> **让后来的人看得懂：当时为什么这样选、现在必须遵守什么、我们主动接受了什么代价，以及什么证据足以让我们换一种做法。**

**产品 PRD 定义承诺，技术实现 PRD 组织实现，ADR 保存关键选择的理由与边界。它的价值不是让决定永远不变，而是让坚持与改变都有依据。**


# 第四部分 · SDD

# 第四部分：一个优秀的 SDD，应该包含什么？

**优秀的 SDD，要把已经确定的产品要求、总体技术方案和架构决策，细化成一套能够指导具体实现、模块集成和验证的设计说明。**

这里的 SDD 指 **Software Design Description / Software Design Document，软件设计说明书**。

它的核心问题是：

> **系统具体由哪些软件单元组成；每个单元接收什么、处理什么、输出什么；数据和状态怎样变化；单元之间怎样协作；遇到并发、错误和中断时，如何继续遵守产品承诺。**

NASA 对详细设计的要求非常直接：基于软件架构，描述更低层的软件单元，使其能够被编码、编译和测试，并减少实现者对关键设计的自行猜测。citeturn988837view0

但要注意：

**SDD 的目标不是让工程师不需要思考，而是让工程师不必在写代码时，重新猜测业务规则、补定义接口、临时决定安全边界。**

---

# 一、先校准：SDD 与前面三份文档是什么关系？

## 1. SDD 不一定只包含“底层设计”

不同组织的文档边界并不完全相同。例如，NASA 的软件设计说明书内容同时覆盖架构、组件分解、接口、算法、数据结构和执行逻辑，并允许引用其他文档中已经定义的内容。citeturn507456view3

因此，**不是行业规定必须先写“技术实现 PRD”，然后再写一份完全不重叠的 SDD。**

沿用你已经建立的文档体系，我建议这样划分：

| 文档 | 在你这套体系中的主要职责 |
|---|---|
| **产品 PRD** | 定义用户需求、产品行为、业务规则和验收结果 |
| **技术实现 PRD** | 定义系统总体方案、关键技术要求、模块边界和工程约束 |
| **ADR** | 保存重要技术选择的依据、取舍、代价和适用条件 |
| **SDD** | 把这些要求和决策细化成具体组件、数据、接口、算法、状态和执行设计 |
| **测试与验收规格** | 规定如何用环境、数据、步骤和证据验证需求与实现 |

**前一轮技术实现 PRD 已经写清的总体架构和通用规则，在 SDD 中引用即可，不应再复制一份维护。**

## 2. 用同一个问题，看它们的详细程度

以“任务中断后能够恢复”为例：

| 文档 | 应写的内容 |
|---|---|
| **产品 PRD** | 中断后哪些进度保留，用户怎样继续，哪些行为不能重复 |
| **技术实现 PRD** | 使用持久化任务状态、执行检查点和恢复机制；明确责任组件 |
| **ADR** | 为什么由统一任务服务持有恢复状态，而不是由每个 Agent 自行保存 |
| **SDD** | 检查点具体保存什么、何时提交、恢复入口是什么、状态怎样转换、旧执行者怎样处理、哪些步骤允许重试 |
| **测试与验收规格** | 在哪些位置制造中断，如何恢复，预期得到什么结果，保留哪些证据 |

**技术实现 PRD 说“用什么机制”；SDD 要继续说明“这个机制在本系统里具体怎样工作”。**

---

# 二、SDD 应该写到多细？

我建议采用一个判断标准：

> **让两名没有参加早期讨论的工程师，分别实现相互协作的模块时，不需要各自猜测接口含义、状态规则和失败行为。**

这不要求他们写出一模一样的代码。

他们可以采用不同的内部函数组织方式，但不能一个认为“成功”表示已收到请求，另一个认为“成功”表示外部操作已经完成。

需要详细约束的，主要是：

**可观察行为、跨模块契约、数据正确性、安全边界、并发行为、关键算法，以及恢复机制。**

可以保留实现自由的，则是不会改变这些约定的局部细节，例如普通私有函数怎样拆分、局部变量怎样命名。

**不是每个函数都必须写伪代码，也不是每个类都必须画 UML。详细程度应跟风险、复杂度和协作需要对应。**

---

# 三、一个优秀 SDD 的完整内容

下面是我建议你采用的结构。它是**内容覆盖框架**，不是要求每个模块都机械填写同样多的文字。

## A. 设计基线与范围

### 01. 文档标识、版本、负责人和适用范围

首先说明：这份设计覆盖什么，以及当前处于什么状态。

应包括文档编号、版本、设计负责人、评审者、适用模块、目标发布版本，以及对应的产品需求、技术总纲、ADR 和代码基线。

特别要区分：

**待评审设计、已批准设计、已经实现的设计，以及已经验证的设计。**

“SDD 已通过评审”不能被写成“系统已经实现了这些保证”。

对于已有系统，还要明确本次描述的是现状还是目标设计。当前状态与计划状态不同的地方，应单独标出，不能混在同一张图里让读者自行判断。

**这一章的交付结果，是一份清楚的设计边界和版本依据。**

---

### 02. 需求分配、设计约束与追踪关系

这一章要把上层要求落实到具体设计单元。

例如，一条“撤销授权后不得启动新的受限操作”的要求，需要对应到授权检查组件、执行入口、缓存失效规则，以及在途操作的处理设计。

我建议至少建立：

> **产品／技术需求 → 设计单元 → 接口或状态规则 → 对应验证项。**

设计单元也要能反向说明自己为什么存在，避免出现无法解释用途的工程建设。

对于会影响实现的要求，应明确属于哪一类：

**必须遵守的约束、已经批准的设计选择、暂时采用的假设，或者尚未解决的问题。**

同时标记重要的“不变量”——也就是无论经历正常流程、并发还是恢复，都必须保持的条件。

例如：

> 同一次确认只适用于被确认的内容版本。  
> 没有相应权限的调用者不能取得对象内容。  
> 外部执行结果未知时，不能直接记录为确定成功。

这些不变量应成为后面数据、状态、接口和恢复设计共同遵守的约束。

---

### 03. 系统位置、结构分解与共用约定

SDD 需要给读者足够的上下文，但不必重写全部架构。

应说明本模块位于哪里，依赖谁，被谁调用，部署在哪个进程或设备，以及对应哪些代码包和运行组件。

这里尤其要区分：

**逻辑模块、代码包、进程、服务和部署实例。**

一个逻辑模块不一定对应一个独立服务，一个服务也可能包含多个清楚分界的模块。

共用约定则包括标识符、时间、时区、编码、错误格式、版本命名、权限上下文和日志关联方式。

我建议把共用约定放在统一位置，模块 SDD 只写适用关系和例外。

结构视图之外，还要有必要的运行视图。arc42 的运行视图明确覆盖关键用例、外部交互、启动停止，以及错误和异常场景，而不是只画静态模块连接。citeturn985076view0

---

## B. 软件单元与数据设计

### 04. 模块、组件与关键软件单元的详细设计

这是 SDD 的主体之一。

对每个关键软件单元，应写清：

**职责、输入、输出、内部状态、主要处理逻辑、依赖、资源所有权、失败行为和调用限制。**

例如，“发送执行器”不能只写成“负责发送邮件”。

还要说明它从哪里取得任务，是否可以修改内容，在哪里检查授权，怎样选择适配器，如何保存执行结果，以及是否拥有重新发送的权力。

对关键操作，我建议采用这样的描述结构：

| 内容 | 应说明什么 |
|---|---|
| **前置条件** | 调用前必须满足什么 |
| **输入约束** | 数据类型、有效范围、来源和权限要求 |
| **处理逻辑** | 按什么规则完成操作 |
| **后置条件** | 成功后必须产生什么结果或状态 |
| **副作用** | 是否写数据库、发消息或改变外部系统 |
| **失败行为** | 返回什么，已经发生的变化怎样处理 |
| **并发约束** | 是否允许同时调用、重复调用或重入 |
| **资源责任** | 谁申请、持有和释放连接、文件、内存等资源 |

**关键不是把组件介绍得很长，而是让它的责任和保证足够明确。**

---

### 05. 数据模型、数据结构与数据字典

产品 PRD 说明“这些对象在业务上是什么”；SDD 要说明“它们在实现中怎样被准确表达”。

应定义实体、标识符、关系、字段、类型、长度、枚举、默认值、可空性、精度、单位，以及数据创建和修改规则。

特别要写清容易引发不一致的细节：

空值、字段缺失和空字符串是否相同？时间保存的是时间点还是本地日程？金额采用什么单位和舍入规则？文件引用是否绑定具体版本？

接口和数据字典不应只有字段名称。NASA 的接口设计指导也明确涵盖类型、格式、单位、范围、精度、更新条件、数据来源与安全限制。citeturn507456view5

对包含共享内存、二进制协议或底层系统的软件，还应进一步定义内存布局、字节序、对齐和所有权。

**“这个字段是 JSON”不等于这个字段已经完成设计。JSON 内部结构和语义同样需要约束。**

---

### 06. 存储、事务、读写路径与一致性

这一章要说明数据怎样真正被保存和修改。

应包含表或集合结构、主键、唯一约束、外键、必要索引、访问路径、事务边界，以及并发冲突处理。

尤其要说明：

**哪些数据是权威记录，哪些只是缓存、索引或派生视图。**

例如，用户刚撤销权限时，读取操作依据什么状态鉴权？能否依赖尚未更新的缓存？如果不能，设计用什么机制保证这一点？

“使用数据库事务”仍然不够。必须明确哪些读写处于同一事务，隔离级别是什么，提交失败后如何处理。

以 PostgreSQL 为例，即使选择 Serializable 隔离级别，应用仍然需要处理序列化失败并重试事务；选择较强隔离并不会免除应用侧的失败处理。citeturn345525view4

如果一次操作既写业务数据又发布事件，还要设计两者的协调。事务发件箱可以处理这类双写问题，但消息仍可能重复交付，消费方仍需处理重复。citeturn988837view3

---

### 07. 同步接口与调用契约

每个重要接口都应该让调用方知道：

> **我可以怎样调用，能依赖什么保证，失败后应该怎么办？**

除了路径或函数签名，还应定义输入输出结构、身份要求、前置条件、错误类型、超时、重复请求、并发冲突、分页、排序和版本兼容规则。

对于 HTTP 接口，可以用 OpenAPI 保存机器可读定义；它用于描述接口能力，也可供文档、代码生成和测试工具使用。citeturn507456view0

但是，**有了接口文件，不代表业务语义已经完整。**

例如，异步操作返回 `202 Accepted`，表示请求已被接受处理，不表示处理已经完成，更不保证最终一定执行成功。citeturn507456view1

因此，SDD 还应定义本系统何时返回这个响应、响应对应什么持久化状态、后续到哪里查询，以及用户如何区分“已接收”和“已完成”。

对进程间通信、插件接口、命令行和本地系统调用，也需要相同程度的语义约定，而不是只关注 Web API。

---

### 08. 事件、消息和异步协议

异步系统不能只有一句“通过消息队列通信”。

我建议对每类事件或命令明确生产者、消费者、消息标识、业务对象标识、结构版本、顺序要求、重复处理和保留规则。

尤其要区分：

**命令**表达“请求做某件事”；**事件**表达“某件事已经发生”。

不要把“请求发送”与“已经发送”用相似名称混在一起。

还应明确消费者处理成功的判定点、何时确认消息、处理失败如何重试、何时进入人工处理，以及历史消息能否重新处理。

AsyncAPI 可以用于机器可读地描述消息、通道和异步接口，但系统具体承诺的顺序、重复和恢复行为仍需在设计中表达清楚。citeturn444624view1

**重新读取历史事件，不应被默认等同于重新执行历史外部操作。**

---

## C. 执行逻辑与动态行为

### 09. 关键场景的端到端执行设计

这一章把前面的静态组件连接成真实运行流程。

对关键场景，应通过时序图、活动图或清楚的步骤说明，交代谁调用谁、传递什么、在哪里持久化、哪里等待，以及哪里产生外部影响。

不能只写顺利流程。

至少应覆盖与当前模块有关的初始化、正常执行、失败、中断恢复、取消和关闭。

例如，“用户关闭界面后任务继续运行”，SDD 就要说明后台进程如何独立运行，客户端重新打开时如何重新发现任务，怎样补取进度，以及怎样避免重复创建。

**时序图上的每一个成功箭头，都应该能对应到真实接口和明确的成功含义。**

---

### 10. 状态机与状态转换规则

状态枚举只是开始，状态转换规则才是重点。

每个转换应明确：

**当前状态、触发事件、执行主体、进入条件、状态写入、副作用、失败去向，以及是否允许重复触发。**

例如：

> 从“待执行”进入“执行中”，需要具备有效授权、匹配的内容版本和合法的执行所有权。

还要定义非法转换如何处理，以及同时发生两个转换时谁能成功。

尤其不要把不同对象的状态混成一个字段。

任务状态、某次执行尝试的状态、用户审批状态和外部操作结果，可能需要分别建模。一个执行进程退出，不等于业务任务取消；请求提交成功，也不等于最终目标达成。

**状态必须对应事实和证据，不能只是方便界面显示的标签。**

---

### 11. 算法、业务规则和关键计算

对于影响结果的算法，应说明输入、输出、计算步骤、边界条件、终止条件和异常处理。

例如，任务调度不能只写“按优先级排序”。

还需要规定优先级如何计算，同分如何处理，任务等待过久怎样处理，依赖未完成时如何过滤，以及某项输入缺失时使用什么规则。

关键算法可以用伪代码、决策表或公式表达，但要定义符号和参数来源。

对于搜索、排序、规划和推荐，还应说明确定性规则与概率性输出的边界，以及失败时采用什么回退行为。

NASA 的软件设计指导也将算法、数据操作、输入输出、控制流和时序纳入具体设计内容。citeturn444624view2

**“让模型判断”“用智能算法优化”都不能单独构成算法设计。**

---

### 12. 并发、调度、取消与资源协调

这一章解决多个执行者同时工作时的行为。

应明确哪些工作可以并行，哪些必须互斥，锁定什么对象，锁的生命周期是什么，以及冲突发生后等待、拒绝还是重新读取。

对于任务领取，需要设计执行所有权、失联检测和恢复行为。

一个必须回答的问题是：

> 原执行者只是暂时失联，系统已经准备让新执行者接管；原执行者又恢复了，此时谁还能修改状态或执行外部操作？

不能只写“使用分布式锁”，却不解释锁过期后的行为。

取消也需要明确传播方式、检查点和生效边界。用户请求取消后，哪些步骤必须停止，哪些正在进行的外部请求无法保证撤回，都应与产品约定一致。

对于底层软件，还应包含线程交互、死锁规避、内存所有权和资源释放。

---

### 13. 错误分类、重试、恢复与补偿

每个关键失败点应有明确设计，而不是统一返回“系统错误”。

我建议至少区分：

**输入或权限问题、可恢复的暂时故障、不可继续的确定失败，以及外部结果未知。**

每类错误需要说明错误代码、对外信息、可否重试、重试责任方、次数或时间预算，以及后续状态。

网络超时不能直接证明外部操作没有发生；安全重试需要明确的幂等契约和重复请求处理，而不是简单再次调用。citeturn988837view4

对于恢复，要写清检查点内容、保存时机、恢复入口，以及哪些数据必须重新核实。

对于补偿，要说明如何处理已经发生的影响。补偿并不一定恢复到原始状态，也可能失败，Microsoft 的补偿事务模式明确强调了这些边界。citeturn345525view0

**重试、恢复、取消、回滚和补偿，是不同的设计机制，不能混用。**

---

## D. 客户端、安全与外部集成

### 14. 前端、交互实现与多端状态

SDD 不是只写后端。

前端部分应说明页面和组件如何组织，数据从哪里来，哪些状态在本地，哪些由服务端持有，以及用户操作如何转成业务请求。

还需要设计加载、空状态、错误反馈、输入保留、保存失败、重复提交和权限变化后的界面行为。

例如，用户编辑一份草稿时收到旧版本的后台更新，界面能否直接覆盖当前输入？不能覆盖时怎样显示冲突？

多端协作应明确状态订阅、断线重连、增量同步、重复事件和冲突处理。

无障碍与国际化要求，也需要对应到焦点管理、键盘操作、语义标记、文本资源和时间格式等具体实现。

**产品 PRD 定义体验；SDD 说明怎样使这些体验在真实数据和异常条件下成立。**

---

### 15. 安全控制、授权执行与隐私设计

这一章要把安全要求落实到具体执行点。

应明确身份从哪里来，授权由谁判断，凭证存在哪里，调用上下文如何传递，以及哪些路径必须经过相同检查。

权限不能只存在于前端按钮状态中。

对于 Agent 系统，OWASP 明确建议在下游系统执行授权和策略校验，而不是依赖大模型自行决定某项行动是否被允许。citeturn507456view2

SDD 还应细化授权缓存失效、对象级权限、数据脱敏、敏感日志、隔离边界、密钥轮换和删除传播。

特别要处理“检查时有权限，真正执行时权限已变化”的情况。

这里需要明确授权与执行之间的生效边界。如果实现只能提供比产品承诺更弱的保证，应回到产品和架构层解决，不能在 SDD 里悄悄降低要求。

---

### 16. 第三方系统、插件与复用组件

对外部依赖，SDD 应写的是**怎样接入和约束它**，不是复制供应商介绍。

需要明确依赖版本、调用方式、适配层职责、数据转换、凭证使用、错误映射、限流、能力检查和替代条件。

尤其要说明外部能力与内部统一接口之间的差异。

例如，某个供应商没有取消或恢复能力，适配层就不能因为内部接口存在这些方法，而返回虚假的“取消成功”或“恢复成功”。

对于复用开源框架，应区分原生能力、配置获得的能力、自己新增的适配，以及尚未验证的部分。

**“框架支持某功能”与“本项目已经正确接入并验证该功能”，是两个不同结论。**

---

## E. 运行、资源与演进设计

### 17. 性能预算、容量和资源控制

技术实现 PRD 定义质量目标；SDD 要继续说明具体实现怎样满足目标。

应将关键流程分解，给出计算、存储、网络、外部调用和排队等环节的预算与测量点。

还要明确并发上限、连接池、缓存大小、队列上限、背压策略，以及达到资源上限时系统如何拒绝、等待或降级。

“背压”可以理解为：下游处理不过来时，限制上游继续送入工作，避免任务无限堆积。

指标应对应用户得到的服务结果，而不只是服务器看起来是否健康；Google SRE 的 SLO 指导强调了这种用户结果导向。citeturn345525view2

对于 Agent 产品，还应落实模型调用、上下文、工具调用和重试的预算计量与并发扣减，不能让多个任务重复使用同一笔剩余额度。

**估计值、设计目标和实测值应分开记录。**

---

### 18. 日志、指标、调用追踪与审计

“接入监控”不是完整设计。

应明确记录什么事件、包含哪些字段、怎样关联同一任务、保存多久、谁可以读取，以及哪些敏感信息禁止记录。

OpenTelemetry 将日志、指标和调用追踪作为不同遥测信号；SDD 应进一步规定本系统如何使用这些信号定位问题。citeturn345525view1

我建议用稳定标识关联：

> 用户请求 → 业务任务 → 执行尝试 → 外部操作 → 结果证据。

同时区分业务记录、运行日志和审计记录，明确各自用途与保留规则。

重要告警要说明触发条件、抑制或聚合规则、处理责任，以及对应恢复入口。

**不要记录了大量文本，却无法判断某次操作是否真的产生了外部影响。**

---

### 19. 配置、部署与运行生命周期

SDD 应说明组件怎样启动、加载配置、连接依赖、进入可服务状态，以及怎样停止和释放资源。

配置项需要定义类型、默认值、合法范围、覆盖顺序、变更权限和生效方式。

特别要区分可以动态修改的参数，以及必须重启或迁移才能改变的参数。

运行生命周期应覆盖启动失败、依赖不可用、健康检查、优雅退出、未完成任务交接和重启恢复。

对于桌面软件，还应处理系统休眠、用户注销、设备重启和磁盘不足。

部署流水线和操作步骤可以引用其他文档，但组件必须向运行环境提供什么接口，应由设计明确。

---

### 20. 迁移、版本兼容与回退

这一章要解释新旧版本如何共存，而不只是“升级失败就回滚”。

应覆盖接口、数据结构、配置、消息格式、客户端和检查点格式的兼容关系。

数据迁移需要明确执行顺序、回填、校验、部分失败恢复，以及迁移过程中哪些读写仍然允许。

对长任务尤其需要回答：

> 老版本创建的任务，能否由新版本恢复？新版本写入的检查点，旧版本还能否读取？

回退也应区分代码回退、数据回退和外部影响处理。

已经发送的邮件、已经发生的外部修改，不能因为恢复了旧代码就当作没有发生。

**SDD 必须指出哪些变化可逆，哪些只能继续向前修复。**

---

## F. 验证、评审与维护

### 21. 可测试性设计与验证接口

这一章不是提前写完整测试规格，而是保证系统具备被可靠验证的条件。

应说明可以怎样隔离外部依赖，怎样注入时间、随机数和故障，怎样检查内部状态，以及怎样核对外部结果。

例如，恢复逻辑需要能在关键位置制造中断；超时规则需要可控时钟；并发行为需要能重复构造竞争条件。

还应提供可关联的验证接口、测试数据约束和环境隔离要求。

必须避免一个问题：

**模拟服务永远返回成功，不能证明真实系统的失败恢复已经正确。**

我建议同时维护两条验证关系：

**实现是否符合 SDD；SDD 所定义的实现是否满足上层需求。**

只验证第一条，可能得到一个“完全符合错误设计”的系统。

---

### 22. 设计评审、未决问题与变更记录

最后应说明这份设计还有哪些未知，哪些问题阻塞实现，谁负责解决，需要什么证据。

不要只写“待定”。

需要明确问题影响、负责人、解决条件、临时限制，以及是否允许相关范围先行开发。

设计变更应同步检查接口、数据、状态、安全、测试和迁移影响。若改变了架构决策，则应更新相应 ADR 关系，而不是只修改局部设计。

SDD 也不是写完后永久不变。NASA 的详细设计指导明确要求随需求、约束和实现反馈维护设计，并强调避免过度复杂和不必要的文档负担。citeturn988837view0

**文档应该反映经过批准的当前设计，同时保留能够追踪变更的历史。**

---

# 四、沿用邮件例子：SDD 到底应该比上一轮具体多少？

下面是一个**教学用的局部 SDD 示例**。为展示详细程度，暂时采用上一轮提出的“统一行动服务持有权威状态”方案；这不表示你的实际项目已经批准或实现了它。

## 1. 先定义数据与身份

不能把“邮件任务”作为一个没有结构的大对象。

本例至少区分：

| 对象／字段 | 设计含义 |
|---|---|
| `operation_id` | 一次业务发送意图的稳定标识 |
| `content_version` | 本次发送内容的具体版本 |
| `snapshot_ref` | 不可变的发送内容快照，包括账户、收件人、正文和附件版本 |
| `approval_id` | 绑定该操作与内容版本的确认记录 |
| `attempt_id` | 某一次技术执行尝试，不等于新的业务发送 |
| `provider_reference` | 外部供应商返回的可核对标识 |
| `version` | 用于识别并发修改的记录版本 |

这里应规定：

**重试可以产生新的执行尝试，但不能悄悄产生新的业务发送意图。**

同样内容的两封邮件，也不一定是重复操作。用户可能确实希望发送两次，因此不能仅凭正文相同就合并。

---

## 2. 定义接口语义

| 接口 | 本例约定 |
|---|---|
| `POST /mail-operations` | 创建业务操作与内容快照，返回操作标识和待确认状态 |
| `POST /mail-operations/{id}/approve` | 由有权用户确认指定内容版本，生成绑定记录 |
| `POST /mail-operations/{id}/dispatch` | 持久化合法的发送请求；返回接收状态，不表示邮件已发送 |
| `GET /mail-operations/{id}` | 返回当前权威状态、内容版本和允许查看的结果证据 |

每个接口还要补齐输入 Schema、错误类型和权限要求。

例如，确认版本与当前版本不一致时，不能默认确认新内容。

对于重复提交，本例可规定在明确的调用者、操作类型和去重有效期范围内：

> 相同请求标识、相同内容，关联已有操作；相同请求标识、不同内容，返回冲突。

正式 SDD 还必须定义去重记录保留期及过期后的行为。不能把有限的去重窗口写成永久保证。

---

## 3. 定义状态转换，而不只是状态名称

本例可以采用以下局部状态模型：

| 状态 | 含义与限制 |
|---|---|
| `WAITING_APPROVAL` | 尚无适用于当前内容版本的有效确认 |
| `READY` | 已具备确认条件，但执行前仍需检查授权与当前版本 |
| `DISPATCHING` | 已进入发送执行阶段，可能正在产生外部影响 |
| `SUBMITTED` | 有足够证据证明供应商接受了发送，不等于已送达 |
| `UNKNOWN` | 无法确定外部操作结果，禁止直接按普通失败重发 |
| `FAILED` | 已有足够依据判定本次执行失败，并保留失败原因 |
| `CANCELLED` | 在规定的取消边界内停止了操作 |

关键转换要写成规则，例如：

> 只有当前仍为 `READY`，且内容、确认、授权和记录版本均满足条件时，执行者才能取得启动许可并进入 `DISPATCHING`。

对于撤权、取消与启动同时发生的情况，正式设计必须定义先后判定与生效边界，并与产品要求一致。

---

## 4. 定义持久化与外部执行顺序

一种示例安排是：

**接收发送请求时**，在本地事务中保存业务状态和待处理事件。

**执行者领取时**，通过原子条件更新取得该操作的执行资格，并保存执行尝试。

**调用供应商时**，使用对应的内容快照与适配器契约，不重新让 Agent 任意修改已确认内容。

**取得结果后**，依据供应商证据更新业务状态。

这仍然不等于外部邮件被保证“恰好发送一次”。内部事务和消息协调不能自动替代供应商的幂等契约。citeturn988837view3turn988837view4

---

## 5. 把最危险的故障写清楚

例如：

> 供应商已经接受邮件，但执行器在保存结果前崩溃。

不合格的设计是：

> 任务失败，自动重试。

本例更明确的设计是：

> 操作进入结果核对路径；优先使用可靠的供应商标识和查询能力确认结果。不能确认时保留 `UNKNOWN`，不得仅因超时重新发送。

还有一种情况：

> 两个执行器收到同一条待发送消息。

本例需要规定，只有成功取得执行资格的执行器可以继续；重复消息本身不能触发第二次外部发送。

不过，若后续允许执行资格过期与接管，就必须继续设计旧执行者恢复后的处理，不能认为一个条件更新已经解决所有故障场景。

**这才是 SDD 的详细程度：把“使用幂等、状态机和恢复机制”，变成具体对象、接口、转换条件和失败处理。**

---

# 五、对你的 Agent-native 项目，SDD 还需要哪些专项内容？

通用 SDD 仍然是基础，但我建议为 Agent 系统增加下面这些设计内容：

| 专项 | SDD 必须继续细化到什么程度 |
|---|---|
| **Agent 定义** | 身份、配置版本、输入输出、可用工具、上下文范围和终止条件 |
| **Harness 适配** | 生命周期接口、状态映射、暂停／取消／恢复能力及不支持时的行为 |
| **执行循环** | 每轮读取什么状态，何时调用模型，怎样解析结果，何时继续、等待或停止 |
| **工作流与任务图** | 节点与边的数据结构、依赖条件、并行与汇合、失败传播、循环上限 |
| **上下文与记忆** | 数据来源、读取权限、写入条件、版本、纠正、压缩和删除传播 |
| **多 Agent 协作** | 共享对象、写入所有权、交接协议、冲突与重复执行处理 |
| **行动网关** | 参数校验、授权执行、凭证使用、外部副作用和结果未知处理 |
| **结果核验** | 产物标识、证据结构、核验规则，以及“无法验证”如何表示 |
| **模型与策略变化** | 模型、提示词、工具 Schema 和策略版本如何关联到执行记录与评测 |

这里最重要的原则是：

**提示词可以定义 Agent 的工作方式，但不能替代状态协议、权限执行和外部操作契约。**

尤其是授权，应由实际执行系统强制检查，而不能只写在 Agent 的角色提示词里。citeturn507456view2

对于你讨论过的真正操作系统项目，还应增加适用的底层模块设计，例如进程间通信、特权服务、应用隔离、系统更新与恢复，以及硬件和驱动交互。每部分都要明确是继承已有能力、修改已有实现，还是自行开发，避免把复用能力写成已经自行实现。

# 六、大项目的 SDD 应该怎样组织？

我建议采用**主索引＋模块设计＋权威契约文件**，而不是一份不断膨胀的巨型文档。

| 层级 | 主要内容 |
|---|---|
| **主 SDD／设计索引** | 当前设计基线、模块关系、全局约定和文档导航 |
| **模块 SDD** | 具体组件、数据、算法、状态、接口和故障设计 |
| **跨模块契约** | 共用数据模型、事件、权限上下文、错误规则和协议 |
| **机器可读设计材料** | API Schema、消息 Schema、迁移文件、配置 Schema 等 |
| **验证关联** | 设计约束对应的测试、检查和证据位置 |

**同一项定义应只有一个权威来源。**

例如，字段已经在权威 Schema 中定义，SDD 应引用它，并补充业务含义与约束；不要手工复制三份字段表。

NASA 的软件设计说明指导也允许通过引用其他文档、数据字典或工具中的内容来组织设计，而不是强制全部重复写入一个文件。citeturn507456view3

对于人和多个编码 Agent 并行工作的团队，我建议每个工作包都附上对应的需求、有效 ADR、模块 SDD 和接口版本。这样，执行者拿到的是具体设计边界，而不是一份模糊的全项目愿景。

---

# 七、开工前，怎样判断一份 SDD 已经足够优秀？

可以用下面的表进行评审：

| 检查问题 | 不合格的信号 |
|---|---|
| **要求是否落实到设计？** | 上层承诺没有对应组件、接口或状态规则 |
| **模块能否独立实现并正确集成？** | 双方对字段、成功含义或调用顺序理解不同 |
| **数据是否有明确约束？** | 只有实体名称，没有类型、版本、事务和所有权 |
| **动态行为是否完整？** | 只有正常流程，没有并发、取消和恢复 |
| **安全是否落到执行点？** | 只写“需要权限”，没有说明谁在哪里校验 |
| **失败是否有明确去向？** | 所有错误都重试，所有超时都被当作失败 |
| **设计是否可以被验证？** | 无法构造故障、检查状态或核对外部结果 |
| **升级是否保护现有工作？** | 没有数据、消息、客户端和在途任务的兼容设计 |
| **实现是否仍有合理自由？** | 机械规定所有私有函数，却遗漏跨模块契约 |
| **文档是否与当前设计一致？** | 已批准、已实现和已验证混成一个状态 |

还要区分两个时间点：

**可以进入实现**，意味着当前交付范围的关键设计已经明确，重要未知有受控的验证计划。

**可以发布生产**，则需要实现、测试、监控、恢复和运行准备等实际证据。

一份再完整的 SDD，也不能直接代替后者。

---

## 最后，把优秀 SDD 的标准压缩成一句话

> **让开发者知道具体怎样实现，让不同模块能够正确协作，让测试者知道需要验证哪些约束，也让维护者知道系统在异常情况下为什么会这样运行。**

**产品 PRD 定义承诺，技术实现 PRD 确定总体方案，ADR 保存选择依据，SDD 则把它们落到具体的软件结构与运行规则。**

它最重要的价值，不是增加文档数量，而是把那些本来会在编码、集成或上线后才暴露的关键歧义，提前变成可以讨论、检查和验证的设计。


# 第五部分 · 测试设计与验收规格（TDS，对话中称 TDD）

# 第五部分：一份优秀的 TDD，应该由什么组成？

**优秀的测试设计与验收规格，要把“我们认为产品做对了”，变成“在明确的条件下，我们用这些方法检查了这些要求，取得了这些证据，并且知道还有哪些风险没有排除”。**

它不能只是测试用例清单，更不能只是“所有测试通过”的一句结论。

它需要回答：

> **测什么、为什么测、怎样测、在哪里测、使用什么数据、凭什么判定对错、留下什么证据，以及什么条件下可以接受这个版本。**

## 先校正一个容易混淆的名称

**TDD 通常指 Test-Driven Development，即测试驱动开发，是一种开发方法，不是一份文档。**它把编写测试、实现代码和重构交织起来，常用“先看到测试失败，再实现使其通过，随后重构”来描述。citeturn285877search11

沿用我们前四轮的分工，这一轮讨论的是：

**测试设计与验收规格。项目内部可以将其命名为 Test Design Document，但应在术语表中明确含义，避免与测试驱动开发混淆。**

而且，严格来说，你需要的是一套相互关联的材料：测试计划、测试设计与用例、执行规程、证据要求和验收规则。**实际测试报告是在执行后产生的，不能在开工时提前写成“已通过”。**NASA 的软件工程指导也分别定义测试计划、测试规程与测试报告，而不是将三者视为同一种材料。citeturn904570view0turn904570view1turn904570view2

下面我会按你这个大项目的需要展开：**先讲文档边界，再讲完整组成，然后给出一个具体用例，最后说明怎样判断它足以指导开工和验收。**

---

# 一、它与 PRD、ADR、SDD 的关系是什么？

在你的文档体系中，建议这样理解：

| 文档 | 定义什么 | 测试设计与验收规格怎样承接 |
|---|---|---|
| **产品 PRD** | 用户需求、业务规则、体验和产品承诺 | 检查用户是否获得规定的结果 |
| **技术实现 PRD** | 技术要求、总体架构、质量目标与系统边界 | 检查性能、可靠性、安全和系统协作是否满足要求 |
| **ADR** | 重要技术选择与约束 | 检查实现有没有违反有效的架构决定 |
| **SDD** | 组件、接口、数据、状态、算法和故障处理 | 设计相应的接口、状态、并发与恢复测试 |
| **测试设计与验收规格** | 检查方法、数据、环境、判定标准和证据要求 | 为执行测试和作出验收决定提供依据 |

这里最重要的一点是：

**测试不能只依据 SDD，也不能把当前代码的行为当作正确答案。**

例如，产品要求“撤销授权后不能启动新的受限操作”，但 SDD 漏掉了执行前检查。假如测试也只照着 SDD 写，就可能得到一个“完全符合错误设计”的实现。

因此，我建议同时保留两条检查线：

**设计符合性：代码是否按批准的设计实现？**

**需求符合性：这个实现是否真的满足产品与技术要求？**

发现两者冲突，应回到需求和设计层解决，不能为了让测试变绿，直接修改预期结果。

---

# 二、优秀测试设计与验收规格的完整组成

我建议把它组织成五组、二十项内容。它们是**覆盖问题的框架**，不是要求所有模块写同样长的文档。

## A. 测试依据、范围与策略

### 01. 文档基线、测试对象与目标

这一章首先回答：

> **我们准备验证哪个系统、哪个范围、哪个版本？**

应写清文档编号、负责人、适用发布版本、测试对象、目标能力，以及所依据的 PRD、技术要求、ADR 和 SDD 版本。

对于实际执行，还需要关联代码提交、构建产物、配置和依赖版本。

我建议把三种状态分开：

**测试设计已经批准，测试脚本已经实现，测试已经执行并取得结果。**

例如，某用例已经写好，但因为外部环境尚未准备完成而没有执行，就不能标记为“已验证”。

对于多端产品，还应明确本次覆盖哪些客户端、后台服务、设备、插件和外部连接，不要用“整个系统”掩盖实际范围。

---

### 02. 测试依据与双向追踪矩阵

这一章回答：

> **每项重要要求怎样被检查？每个测试为什么存在？**

我建议建立下面的关系：

**需求／风险 → 测试条件 → 测试用例 → 执行记录 → 结果证据 → 缺陷或验收结论。**

例如：

| 要求或风险 | 应检查的条件 | 主要证据 |
|---|---|---|
| 重复提交不得重复产生业务操作 | 同标识重复请求、并发请求、重复消息 | 业务记录、执行记录和外部影响数量 |
| 撤销权限后不得启动受限操作 | 撤权前后、授权缓存未更新、执行竞态 | 授权记录、实际调用和状态变化 |
| 外部结果未知时不得宣称成功 | 请求已提交但响应丢失 | 外部结果、系统状态和用户界面 |
| 用户可以取得真实产物 | 完成后读取、权限变化、文件损坏 | 实际文件、完整性检查和访问结果 |

NASA 的测试规程指导明确包含需求追踪，以及测试与要求之间的双向关联。citeturn442144view0

但要进一步区分：

**有测试关联，只说明存在检查安排；执行通过并具有有效证据，才能支持对应的验证结论。**

一个需求关联了十个测试，其中九个没跑，不能算“需求已验证”。

---

### 03. 风险分析、优先级与不测范围

这一章回答：

> **测试资源有限时，什么必须先查、深入查？哪些地方本次没有覆盖？**

我建议按错误的影响、发生条件、暴露范围和恢复难度安排测试深度。

例如，错误地发送邮件、跨用户读取数据和丢失用户文件，不能与一个轻微排版问题获得同样的测试优先级。

同时应明确：

**本次不适用、延期验证、环境受限而无法验证，以及主动接受残余风险，是不同情况。**

每个重要缺口都应记录原因、影响、负责人和后续条件。

不能只写：

> 暂不测试某供应商。

需要进一步说明：这个供应商是否仍在发布承诺内？未测的是什么？是否因此限制开放范围？

测试计划中的风险、约束、资源和测试方式本来就需要一起考虑；ISTQB 的测试计划内容也明确涵盖这些要素。citeturn442144view4

---

### 04. 测试策略、层级与责任分配

这一章回答：

> **不同问题在哪里检查，怎样避免全靠最后一次端到端演示？**

建议按项目结构划分：

| 层级 | 主要检查什么 |
|---|---|
| **单元／组件测试** | 局部规则、计算、数据转换和边界处理 |
| **组件集成测试** | 数据库、队列、服务模块之间的真实协作 |
| **系统测试** | 完整系统的功能与质量要求 |
| **系统间集成测试** | 与外部服务、设备或其他系统的接口和行为 |
| **验收测试** | 目标用户和业务负责人关心的完整任务与结果 |

测试层级与测试类型需要区分：**安全、性能、回归并不是只能放在某一个“最后阶段”的测试层级。**ISTQB 对测试层级、测试类型和维护测试作了分别处理。citeturn705519view1

此外，还应安排需求评审、设计评审、代码检查等静态活动。

我建议不要机械规定“必须多少比例单元测试、多少比例端到端测试”。应根据风险、反馈速度、环境成本和集成复杂度决定组合。

---

## B. 测试设计、执行条件与判定依据

### 05. 场景模型、测试条件与覆盖方法

这一章回答：

> **怎样从功能说明里系统性地推导测试，而不是凭感觉列例子？**

我建议至少检查三种覆盖：

**输入覆盖：**正常值、边界值、非法值、缺失值，以及输入之间的组合。

**行为覆盖：**正常流程、分支、状态转换、异常与恢复。

**上下文覆盖：**不同角色、权限、设备、版本、网络和依赖状态。

例如，“上传文件”不只是上传一个正常 PDF，还要考虑零字节文件、接近限制的文件、上传中断、相同名称、错误类型、空间不足和权限撤销。

多维组合过多时，可以使用组合测试方法减少测试数量；NIST 的组合测试工作就是围绕参数交互覆盖展开的。citeturn594925view3

但我建议保留一个限制：

**组合抽样不能自动替代已知高风险的完整场景。**

已经知道“并发＋撤权＋缓存滞后”可能出问题，就应该直接验证这个组合，而不是期待它碰巧进入抽样集。

---

### 06. 正确性判定依据：凭什么认为结果对了？

这是整份文档最容易缺失、也最重要的部分之一。

测试领域常用 **Test Oracle** 表示判定测试结果是否正确的依据。针对测试预言问题的研究也强调，需要能够区分正确行为与错误行为的判断基础。citeturn559909academia18

我建议在项目里直接称为**判定依据**，并对关键测试写清：

预期结果来自哪里？使用什么独立计算、批准规则、参考数据或外部事实进行核对？允许什么误差？无法取得依据时怎样处理？

例如：

> 检查余额计算，不能再次调用被测的余额计算函数来生成“预期余额”。

> 检查邮件是否发送，不能只读取被测系统自己写出的“发送成功”。

对于异步行为，还要定义时间条件：

**在什么时间内应该发生什么，以及在这段时间内什么绝对不应该发生。**

“最终应该成功”如果没有观察窗口、前提和超时处理，就不足以形成可执行的测试。

---

### 07. 单个测试用例的完整规格

**这是测试设计的主体。**

我建议关键用例采用下面的统一结构：

| 字段 | 应写的内容 |
|---|---|
| **编号与名称** | 唯一标识，名称直接表达要验证的行为 |
| **目的与关联** | 对应需求、风险、设计约束和验收条件 |
| **测试类型与责任人** | 在哪一层执行，谁维护、谁执行、谁复核 |
| **版本与环境** | 被测构建、配置、依赖和测试工具版本 |
| **前置条件** | 用户身份、权限、业务状态和依赖状态 |
| **输入与数据** | 数据集、记录、文件、参数及其版本 |
| **操作步骤** | 按什么顺序执行，在哪个位置等待或注入故障 |
| **预期结果** | 输出、状态、数据变化、外部影响和禁止发生的行为 |
| **判定规则** | 阈值、时间窗口、容差、统计方式和正确性依据 |
| **证据要求** | 必须保留的日志、记录、文件、截图或测量数据 |
| **清理与恢复** | 怎样停止后台工作并恢复到已知状态 |
| **自动化关联** | 对应脚本、执行入口、标签和依赖关系 |

NASA 的测试规程也明确要求测试标识、版本、前提、步骤、输入输出、预期结果、通过标准，以及能够重跑测试的信息。citeturn442144view0

**实际结果、运行状态和证据位置，应保存在具体执行记录中，不应覆盖原来的预期结果。**

同一个用例可以执行很多次，每次都应有独立记录。

---

### 08. 执行规程、初始化与清理

这一章回答：

> **别人拿到这份规格，能不能在不靠作者口头指导的情况下执行？**

需要说明启动哪些组件、准备哪些数据、如何检查环境就绪、怎样执行，以及失败后怎样安全结束。

尤其要明确测试之间的依赖。

一个测试依赖上一个测试留下的数据，就需要明确这个关系；更稳妥的安排通常是为它准备独立的初始化过程。

我建议对涉及外部影响的测试定义：

**允许访问的账户和目标、最大执行次数、资源或费用上限、停止条件，以及紧急中止方式。**

清理不能只是删除数据库记录。

如果后台 Agent 仍在运行，清理完数据后它又继续发送请求，测试环境就没有真正恢复。

---

### 09. 测试环境、替身范围与真实性边界

这一章回答：

> **测试到底运行在什么环境？哪些是真的，哪些是模拟的？**

应明确真实组件、测试替身、模拟器、供应商沙箱、设备型号、网络条件和与生产环境的差异。

特别要区分：

**测试替身通过：**说明系统在约定的模拟行为下表现符合要求。

**真实集成通过：**说明实际适配器与外部系统在此次条件下完成了协作。

**生产效果：**还受到真实配置、流量、用户数据和供应商变化的影响。

Google SRE 指出，测试环境与生产环境不完全相同，测试也无法覆盖所有场景，因此发布后仍可能暴露问题。citeturn442144view3

所以，模拟不是问题。问题是：

**把模拟测试的结果，包装成已经验证了真实外部能力。**

---

### 10. 测试数据、版本与隔离

这一章回答：

> **使用什么数据测试，怎样确保数据代表了真实问题，又不会污染用户环境？**

应说明数据来源、生成方法、版本、规模、权限、保留期和清理规则。

我建议数据集不仅包含“干净正常数据”，还应覆盖重复、冲突、缺失、历史版本、损坏、特殊字符和边界数据。

对于多用户系统，需要专门准备不同用户和不同权限范围的数据，检查隔离是否有效。

对于时间、随机数和外部响应，应记录可控制的条件，避免结果变化后无法解释原因。

生产数据不能因为“更真实”就直接复制到测试环境。需要经过适当授权、最小化和脱敏，并确认测试操作不会影响真实用户。

---

## C. 必须覆盖的专项质量测试

### 11. 数据一致性、并发、故障与恢复

这一章要把 SDD 中的状态和恢复设计，转成具体故障实验。

我建议按关键操作的时间位置设计故障：

**操作前、内部记录提交后、外部影响发生后、结果返回前，以及结果保存前。**

同时检查重复消息、并发请求、执行者失联、旧执行者恢复、进程重启和依赖断开。

例如，外部请求超时不等于外部没有执行；AWS 的幂等 API 指导明确讨论了这种结果不明与安全重试问题。citeturn594925view1

测试应检查的不只是“最后恢复了”，还包括：

有没有重复影响？有没有丢失进度？有没有错误覆盖新数据？有没有把未知结果误判成功？有没有在恢复后继续使用失效授权？

**进程重新启动成功，不等于业务恢复正确。**

---

### 12. 安全、权限与隐私测试

我建议按下面的矩阵构造安全测试：

**身份 × 对象 × 操作 × 权限范围 × 当前状态。**

例如，验证一个无权用户不能在界面读取文件，还需要检查他是否能绕过界面，直接通过 API、搜索、导出、缓存或 Agent 工具取得相同内容。

权限测试既要验证拒绝，也要验证合法请求不会被错误阻止。

对于 Web 应用，可以将适用的 OWASP ASVS 要求映射到测试，并固定引用版本与要求编号；ASVS 本身提供安全控制验证依据，并强调版本化引用。citeturn705519view3

对 Agent 产品，必须进一步验证执行端的授权控制，而不只是模型是否“愿意遵守”。OWASP 明确要求下游系统实施授权和策略校验，不能依赖大模型判断某操作是否允许。citeturn559909view3

---

### 13. 性能、容量、稳定性与成本

这一章回答：

> **在什么负载下，系统是否达到已经约定的质量目标？**

每项性能测试应定义负载模型、数据规模、并发、持续时间、预热、测量起止点、统计口径和环境配置。

我建议同时观察：

响应时间分布、错误与超时、排队长度、资源占用、长时间运行趋势，以及单位成功任务的成本。

不要只看平均响应时间，也不要把失败请求全部从统计中移除。

测试至少应区分正常负载、目标峰值、超载，以及超载后的恢复。具体阈值应来自产品和技术要求，不能随意套用一个“行业通用数字”。

**系统快速拒绝全部请求，可能拥有很好看的响应时间，却没有满足任何有效服务目标。**

---

### 14. 用户体验、多端兼容与无障碍

这一章要验证用户能否真正完成任务，而不只是页面存在、按钮可点。

我建议让目标用户从正常入口开始，自行理解、操作、处理错误并取得结果；记录完成情况、阻碍和需要的帮助。

还要覆盖不同屏幕、输入方式、浏览器或系统版本，以及离线、切换设备、恢复连接和多端冲突。

对无障碍，自动工具可以提供检查，但不能单独判定网站符合无障碍要求；W3C 明确要求结合有知识的人工评估。citeturn904570view3

对于你强调的真实 Demo，这意味着：

**测试不能依赖演示者知道隐藏按钮、预设正确输入，或者替用户完成关键步骤。**

---

### 15. 安装、升级、迁移与运行验收

这一章回答：

> **新版本进入真实环境时，会不会破坏已有用户的工作？**

我建议覆盖安装、升级、数据迁移、版本混用、回退、备份恢复、配置变化，以及正在运行的任务。

恢复测试不能只检查“备份文件存在”，而应实际恢复并核对数据和业务状态。

迁移测试也不能只检查“脚本退出码为零”，还要检查记录数量、关联关系、权限、历史版本和业务结果。

对于你的操作系统项目，还应按实际支持范围增加启动、休眠唤醒、设备断连、磁盘不足、系统更新中断和恢复环境测试。

发布后的渐进开放与观察也应有规则。Google SRE 将金丝雀发布描述为有限范围、有限时间的部署与评估，用于判断是否继续扩大发布。citeturn555888view2

---

## D. 自动化、证据与缺陷处理

### 16. 自动化策略、回归与测试自身质量

这一章回答：

> **哪些测试自动运行，何时运行，失败后如何处理？**

我建议明确代码提交、合并、定时运行和发布候选阶段分别执行哪些检查，并写清维护人、运行时长和环境成本。

自动化不只是脚本数量。测试本身也要有可信的断言、可控数据和清楚的失败信息。

一个简单反例：

> 测试执行了全部计算代码，但从未检查结果，那么代码都跑过，也不能说明计算正确。

还应定义不稳定测试的处理。Playwright 就分别标记首次通过、重试后通过的 flaky，以及持续失败。citeturn555888view1

我建议保留第一次失败及全部重试记录，不能通过反复重跑删除问题。

**产品内部的重试，与测试运行器重新执行整个用例，是两件不同的事情。**

对于关键验收测试，降低阈值、跳过用例和更新参考答案，应经过明确复核，不能成为“让流水线变绿”的捷径。

---

### 17. 执行记录、证据包与结果报告

这一章回答：

> **以后能不能复核这次测试到底发生了什么？**

每次运行应关联测试版本、被测构建、配置、数据集、环境、执行时间、运行标识、实际结果和证据位置。

NASA 的测试报告指导要求记录结论、剩余缺陷、环境影响、具体结果、过程偏离，以及测试配置和执行记录。citeturn442144view1

我建议项目明确区分：

**通过、失败、被阻塞、未执行、无法判定。**跳过的用例还需要记录原因与批准信息。

还要注意：

**系统按要求呈现“结果未知”，可以是一次测试通过；测试人员没有足够证据判断系统行为，才是测试无法判定。**

结果汇总必须公开分母。

例如，计划测试一百项，九十项通过、十项被阻塞，不能报告为“全部通过”。可以说已完成判定的九十项全部通过，但仍有十项缺少验证。

截图可以证明界面表现，却不能单独证明后台数据或外部操作正确。证据类型必须与所声称的结果匹配。

---

### 18. 缺陷管理、修复确认与回归

这一章回答：

> **发现问题以后，怎样确认它真的被解决，而不是只收到“已修复”的回复？**

我建议每个缺陷记录复现条件、预期与实际结果、受影响版本、证据、影响程度、处理优先级和责任人。

影响程度与处理顺序应分开。例如，某问题影响严重，但只有尚未开放的功能会触发；是否立即阻塞发布，需要结合实际发布范围决定，而不是修改它的严重程度。

修复后，应执行两类检查：

**确认原问题消失，以及检查修改是否破坏其他行为。**

对于无法稳定复现的问题，也应保存首次失败证据和已知条件，不要直接关闭为“无法复现”。

缺陷修复如果改变原需求，应先完成需求变更，而不能仅修改测试预期来适应实现。

---

## E. 验收、责任与持续维护

### 19. 进入条件、通过条件、退出条件与发布规则

这一章必须区分四件事：

| 判断 | 应回答的问题 |
|---|---|
| **可以开始测试** | 环境、数据、构建和观察能力是否就绪？ |
| **单个用例通过** | 规定的结果和禁止行为是否全部得到检查？ |
| **本轮测试可以结束** | 覆盖、缺陷、未测项和证据是否满足阶段要求？ |
| **版本可以发布** | 测试结果与其他运行准备是否足以支持发布决定？ |

ISTQB 将进入条件定义为开始活动的前提，将退出条件定义为宣布活动完成所需满足的条件。citeturn442144view5

我建议对关键安全约束采用明确的阻断规则，对一般质量指标采用事先批准的阈值和评估方法。

不要仅规定“总体通过率超过 95%”。剩余 5% 可能恰好包含越权、数据损坏或重复外部操作。

还需要定义暂停和恢复测试的条件，例如环境失真、证据采集失败、测试影响到真实用户，或错误规模失去控制。

**因时间或预算耗尽而停止测试，不等于测试目标已经达到。**

存在例外发布时，应记录残余风险、责任人、限制范围、有效期和补救计划；例外不会把原来的失败结果变成通过。

---

### 20. 角色、资源、变更与维护规则

这一章回答：

> **谁对测试设计、执行证据和验收决定负责？**

我建议至少明确需求负责人、实现负责人、测试维护者、执行者、结果复核者和发布决定者各自的责任。

一个小团队可以由同一个人在不同阶段承担多种角色，不必虚构一整套部门。但关键结果不能只靠实现者自述。

资源计划应包含环境准备、测试数据、执行时间、供应商额度、真实设备，以及修复后的重测成本。

需求、接口、权限、模型、提示词、配置或依赖变化时，应进行测试影响分析，确定哪些证据已经不适用于新版本。

**测试规格应提前参与需求与设计，而不是等代码全部写完后，再补一份证明“做对了”的材料。**

---

# 三、你的 AI／Agent 项目，还需要额外补哪些内容？

**通用软件测试仍然必需，但只做通用测试，还不足以评价 Agent 的实际能力。**

我建议增加一个独立的“Agent 评测与安全验证”部分。

## 1. 明确测的是整个系统，而不只是模型

需要固定或记录：

**模型及可获得的版本标识、Agent 配置、提示词、Harness、工具契约、权限策略、记忆数据、检索数据和评测环境。**

Anthropic 的 Agent 评测说明明确区分 Agent Harness 与 Evaluation Harness：前者让模型执行任务，后者负责组织评测、记录和评分；评测对象是模型与运行框架共同构成的系统。citeturn705519view4

因此，模型不变，但 Harness 的压缩、恢复或工具处理改变，也需要相应回归。

---

## 2. 同时检查结果、过程约束与禁止行为

我建议将每个 Agent 场景写成：

> **初始环境＋任务目标＋授权范围＋可用能力＋允许的结果＋禁止的行为。**

例如，允许 Agent 自由选择检索顺序，但不允许读取未授权文件。

不要为了匹配测试，把所有正确实现都强制成同一条工具调用路线；只有权限、审批或业务规则确实要求某个步骤时，才把它设为强制路径。

同时，完成判定应查看真实环境结果。Anthropic 用预订场景说明：Agent 声称预订成功，与环境中是否真正存在预订，是不同判断。citeturn705519view4

对你的产品，应该专门覆盖记忆污染、跨任务上下文泄漏、错误工具参数、重复执行、失效授权、多 Agent 冲突、预算耗尽和虚假完成。

---

## 3. 规定数据集、重复运行与统计口径

生成式系统可能在相同任务上产生不同结果，因此要区分一个测试任务与针对该任务的多次运行。Anthropic 的评测框架明确使用 task 和 trial 的区分。citeturn705519view4

我建议至少报告：任务数量、每项运行次数、成功与失败分布、超时、成本、关键违规，以及结果的不确定性。

不能只展示最好的一次。

**“十次里至少成功一次”与“每次都可靠成功”，不是同一种产品能力。**

数据集应覆盖正常、边界和对抗场景，并保留不用于日常调参的评估集。OpenAI 的评测指导同样强调任务特定目标、代表性数据、边界与对抗样例，以及持续评测。citeturn594925view0

测试中暂未发现违规，只支持“在这些运行中未观察到违规”，不构成对所有未来输入的保证。

---

## 4. 评分器也需要验证

能够通过代码核对的结果，优先采用确定的检查，例如文件是否存在、内容是否符合约束、是否发生越权调用。

需要模型评价写作质量或复杂任务质量时，应定义评分维度、评分样例、裁决规则和人工复核方式。

OpenAI 的评测指导强调，模型评分需要与人工标签校准，也提醒人工判断之间本身可能存在分歧。citeturn559909view0

我建议不要让同一个实现 Agent 自己修改验收数据、降低通过标准，再给自己的结果盖章。

**多几个 Agent 互相同意，不自动等于独立验证。**

测试输入、评分规则和运行证据应有明确的修改权限，验收结论需要来自实际执行结果。

# 四、沿用邮件场景：一条优秀测试用例应该怎样写？

下面是一条**教学示例，不是已经执行的测试报告**。

为了明确控制故障，本例使用受控供应商测试替身；内部行动服务、数据库和队列使用待测实现。

## 用例：供应商已受理，但响应丢失后不得盲目重复发送

### 1. 基本信息

**用例编号：**TC-MAIL-RECOVERY-001。

**关联要求：**外部发送结果不明确时，不得直接标记成功或按普通失败重复发送。

**风险：**重复发送，或将未核实状态错误展示为完成。

**初始条件：**有一项合法邮件操作，内容和附件版本已确定，用户确认与授权有效。

**环境限制：**全部邮件进入测试接收端，不允许发送给真实联系人。

### 2. 测试替身契约

本例假设测试供应商可以：

持久化记录已受理的操作；按客户端操作标识查询；在受理后主动丢弃响应；通过独立管理接口提供外部影响记录。

这些是**本例测试环境的能力约定**，不是对所有邮件供应商的能力声明。

### 3. 执行步骤与检查

| 步骤 | 操作 | 应检查的结果 |
|---|---|---|
| **1** | 创建并确认一项邮件操作 | 内容版本、确认记录和授权对应一致 |
| **2** | 提交发送，等待测试供应商确认已持久化受理记录 | 独立接收记录中出现一次受理 |
| **3** | 丢弃供应商响应，并使执行器在保存结果前退出 | 系统没有获得可用于确认发送成功的响应 |
| **4** | 暂时关闭结果查询，重启执行组件 | 在设计规定的恢复窗口内进入结果核对或未知状态 |
| **5** | 再次投递该操作的重复队列消息 | 不因消息重复而产生第二次发送影响 |
| **6** | 恢复可靠的结果查询 | 系统根据证据进入已提交状态，不擅自显示已送达 |
| **7** | 收集证据，停止任务并清理环境 | 无残留后台执行，证据能够关联到本次运行 |

正式规格还应把恢复窗口、查询超时和测试总时限写成具体值，引用已经批准的技术要求，而不是让脚本无限等待。

### 4. 通过条件

本例要求：在规定的事件顺序和观察窗口内，测试供应商只记录一次发送影响；系统在结果未确定时不宣称成功；取得可靠证据后才更新状态；内容版本与确认一致。

同时应检查界面没有把“已提交”错误表达为“已送达”。

**只要其中一项不满足，这条用例就不能通过。**

### 5. 必须保留的证据

我建议至少保留业务操作与执行尝试标识、内容版本、故障注入位置、状态变化、外部接收记录、调用记录，以及被测构建和配置。

若测试环境无法提供独立接收记录，就不能仅凭系统日志宣布“没有重复发送”；应记录证据不足并处理相应测试状态。

### 6. 这条测试不能证明什么？

它不能单独证明真实供应商具有相同查询能力，也不能证明所有故障顺序下都不会重复。

还需要其他用例覆盖：无法查询结果、旧执行者恢复、授权撤销、确认后修改内容、真实供应商适配，以及多端重复提交。

**优秀测试用例不仅写清能证明什么，也写清结论在哪里结束。**

# 五、大项目应该怎样组织这些材料？

我建议采用“主文档＋分模块规格＋执行材料＋证据”的方式：

| 材料 | 作用 |
|---|---|
| **主测试计划与验收规则** | 定义范围、风险、策略、环境、责任和阶段标准 |
| **模块／场景测试规格** | 定义测试条件、用例、数据和判定依据 |
| **执行脚本与测试基础设施** | 实现初始化、运行、故障注入和证据采集 |
| **运行记录与报告** | 保存每个构建、每次运行的真实结果和限制 |
| **发布验收记录** | 记录是否接受、残余风险、限制范围和责任人 |

ISO/IEC/IEEE 29119-3 的公开说明也将软件测试文档定位为可适用于不同组织、项目和生命周期的文档模板体系，而不是要求所有团队把内容塞进一个文件。citeturn705519view0

建议保持**一处权威定义**：验收阈值不能在 PRD、测试文档和脚本中各写一个不同数字；数据集和评分规则也应有版本。

文档解释为什么这样测，脚本执行检查，报告记录发生了什么。三者相互引用，不相互冒充。

# 六、怎样判断这份 TDD 已经足够优秀？

开工前，我建议用下面这张表审查：

| 问题 | 不合格信号 |
|---|---|
| **测试范围清楚吗？** | 只写“全面测试”，不知道覆盖哪些版本和能力 |
| **需求与风险有对应检查吗？** | 用例很多，但关键承诺没有覆盖 |
| **预期结果有独立依据吗？** | 当前程序输出什么，就认为什么正确 |
| **别人能执行吗？** | 依赖作者口头指导和手工准备 |
| **正常、异常与并发都考虑了吗？** | 只有一条成功演示路径 |
| **环境真实性说清了吗？** | 模拟通过被写成真实集成通过 |
| **证据能复核吗？** | 只有截图或“Agent 说测试成功” |
| **未测项与失败公开吗？** | 通过重跑、跳过和修改分母美化结果 |
| **验收与发布有明确条件吗？** | 只看总通过率，不看关键风险 |
| **变更后会重新验证吗？** | 更换模型、接口或配置，继续沿用旧结论 |

最后还要区分两个阶段：

**足以开工的测试规格**，意味着近期交付范围的关键测试条件、判定依据、数据与环境需求已经明确，能够反过来指导设计和实现。

**足以验收的证据体系**，则意味着相关测试已经实际执行，结果、未测项和残余风险能够被复核。

前者不能代替后者。

---

## 最后，把优秀 TDD 的标准压缩成一句话

> **让团队在实现之前知道怎样判定对错，在实现之后拿得出可信证据，在准备发布时说得清哪些要求已经得到验证、哪些风险仍然存在。**

**SDD 负责说明“系统具体怎样工作”；测试设计与验收规格负责说明“怎样检查它是否真的按要求工作”。**

它的价值不在于生成上千条测试，而在于让重要承诺有检查方法、让失败无法被掩盖、让“完成”成为一个有证据和边界的判断。


# 第六部分 · 工程执行计划与协作交付规范（Agent 工作方式）

**有必要，而且对你这种“人＋多个 Agent 并行开发”的大项目，我建议把它作为前五类文档之外，单独维护的一套工程执行资料。**

但它不应该再重复一遍产品需求、架构设计和测试用例。它负责的是：

> **谁基于哪份规格完成什么工作；哪些条件满足后才能开始；哪些工作可以并行；哪些 PR 必须按顺序合并；什么时候进行组合验收；谁依据什么证据放行；失败以后怎样返工、阻塞或重新安排下游。**

我建议命名为：

# 第六部分：《工程执行计划与协作交付规范》

英文可以使用 **Engineering Execution Plan & Delivery Playbook**。这是我建议的名称，不必再创造一个团队容易混淆的缩写。

**最核心的区别是：前五类文档主要定义“要做什么、怎样设计、怎样证明正确”；这套资料定义“团队怎样把它们持续变成经过验证的交付物”。**

---

# 一、为什么已经有 PRD、ADR、SDD 和测试规格，还需要它？

因为下面这些问题，不能仅靠设计文档回答：

“后端接口没实现，前端能不能先做？”

“两个 Agent 都要修改任务状态模型，谁先改？”

“某个 PR 自己测试通过了，但它依赖的另一个 PR 还没合并，可以合并吗？”

“六个 PR 都合并了，是否意味着整个功能已经完成？”

“谁负责把这六个 PR 放在同一个版本中进行完整验收？”

“验收失败以后，哪些任务必须暂停，哪些仍然可以继续？”

这些都是**执行、协调和交付决策**。

以我们前几轮的“邮件发送恢复”为例：

| 文档 | 应该记录什么 |
|---|---|
| **SDD** | 操作状态如何保存，结果未知怎样处理，执行器怎样恢复 |
| **测试规格** | 在哪里制造中断，预期行为是什么，需要什么证据 |
| **工程执行计划与协作交付规范** | 谁实现状态存储，谁实现适配器；哪个 PR 依赖哪个；何时开展恢复验收；谁负责验收；失败后阻塞哪些发布动作 |

**因此，有必要存在这一层责任；但不一定要存在一份几十万字的独立大文档。**

我建议将它组织成三个相互关联的部分：

| 部分 | 变化频率 | 主要内容 |
|---|---|---|
| **稳定的工作规范** | 相对低 | 任务拆分、PR 流程、评审规则、验收分层、权限与异常处理 |
| **滚动的工程执行计划** | 随版本调整 | 工作包、任务依赖、并行安排、集成顺序、里程碑与资源 |
| **实时任务与交付记录** | 持续更新 | 任务状态、实际 PR、构建版本、验收记录、阻塞原因和证据 |

不要把第三部分完全靠手工复制到第一部分里，否则很容易出现“文档说完成了，仓库却还没合并”的矛盾。

---

# 二、先统一五个概念，否则依赖与验收一定会混乱

## 1. 工作包、任务、PR、验收节点和发布，不是同一个东西

我建议在文档开头明确下面的定义：

| 对象 | 含义 | 示例 |
|---|---|---|
| **工作包** | 为一个明确结果组织的一组工作 | 交付“可确认、可发送、可恢复的邮件能力” |
| **任务** | 有负责人、输入、输出和完成条件的一项工作 | 实现发送状态存储；验证供应商重试契约 |
| **PR** | 请求将一组代码或配置变化合入目标分支的变更单元 | 增加操作状态表、写入逻辑及相关测试 |
| **验收节点** | 对一组指定交付物作出是否满足要求的判断 | 验证完整邮件场景及故障恢复 |
| **发布／开放动作** | 将指定版本部署或向规定用户启用 | 对试点用户启用自动发送能力 |

**一个任务可以对应多个 PR；一个工作包通常包含多个任务；有些任务根本不需要 PR。**

例如，供应商能力核验、性能测量和用户验收可能主要产生报告或证据，而不是代码。

同样，一个 PR 可以交付完整功能的一小部分。Google 的工程实践明确建议让变更保持自包含，通常只处理功能的一部分，并包含相关测试，而不是要求一次提交整个功能。citeturn649045view2

因此，不要简单建立：

> 一个功能＝一个任务＝一个 PR＝一次验收＝一次发布。

这会把拆分、并行和风险控制全部绑死。

---

## 2. “可以开始”“可以合并”“可以验收”“可以发布”必须分开

这是你这份文档最重要的设计原则。

例如，前端可以依据已经批准的接口契约开始开发，但真实端到端验收必须等待后端可用。

再如，一个新增能力可以先以未开放状态合入主分支，但不代表它已经获准对用户启用。

Google 的工程指南就举过类似情况：协议定义与调用代码可以同时评审，但提交顺序仍需要先协议、后调用方。**并行工作和顺序集成并不矛盾。**citeturn649045view2

我建议把这四个判断作为独立字段，而不是用一个模糊的“依赖前一个任务完成”代替。

---

# 三、一份优秀的文档，具体应该包含什么？

下面是我建议用于你这类项目的完整结构。重点不是章节数量，而是相关问题都有明确归属。

## A. 执行基线与责任

### 01. 文档范围、适用版本与权威来源

应说明本规范适用于哪些仓库、团队、Agent、环境和发布版本。

同时明确关联的产品 PRD、技术实现 PRD、有效 ADR、SDD 和测试规格。

最重要的是定义**不同信息在哪里说了算**：

需求以哪个版本为准；当前 PR 状态从哪里读取；测试结论以哪个运行记录为准；谁可以批准验收和发布。

例如，我建议约定：

> PR 是否合并，以仓库中的实际状态为准；功能是否验收，以对应验收节点的版本化结论为准；Agent 的工作总结不能替代这两种记录。

还应规定发生冲突时的处理方式，不能让执行者随意挑选最容易通过的那份文档。

---

### 02. 交付物分解与工作包结构

这一章回答：

> **怎样把一个产品版本拆成能够分工、集成和验收的工作？**

我建议按“用户结果或技术结果”组织工作包，再拆解任务和 PR。

例如：

> 邮件能力工作包 → 契约、状态、授权、适配、界面、编排、恢复、验收和发布准备。

不要只按部门拆成：

> 前端做完、后端做完、测试做完。

这种划分没有直接说明何时能够形成一个完整可用的结果。

DORA 的小批量工作指导强调，应把工作拆成可测试、可反馈的小批次，而不是积累大量变化后才统一发现问题。citeturn649045view3

每个工作包应明确目标、范围、非目标、交付物、主要依赖，以及最终对应哪个验收节点。

---

### 03. 角色、所有权与决策权限

应明确谁负责实施、评审、集成、验收、发布和异常处理。

我建议至少区分以下责任：

**任务负责人**对任务交付负责；**模块负责人**对模块边界和长期维护负责；**集成负责人**对跨模块组合负责；**验收负责人**对证据与结论负责；**发布负责人**对开放条件与运行风险负责。

一个人可以承担多个角色，但角色责任不能消失。

尤其需要有人负责：

> “所有局部任务都说完成了，但整个功能还不能使用。”

这不是自动属于最后一个提交 PR 的人的问题，应在计划中提前指定集成责任。

对于低风险变化，可以按既定规则自动处理；对于权限边界、不可逆数据变化或真实外部操作，应规定更严格的审查与放行责任。**不需要每一个普通 PR 都让创始人逐项审批。**

---

## B. 任务、依赖与并行安排

### 04. 统一的任务卡与 PR 计划字段

这是实时执行计划的基本单元。

我建议每项进入实施的任务至少包含：

| 字段 | 应写清什么 |
|---|---|
| **编号、名称与工作包** | 能够稳定引用，知道它属于哪个交付结果 |
| **目标与范围** | 本任务做什么、不做什么 |
| **依据** | 需求、有效 ADR、SDD、接口与测试规格的具体版本 |
| **交付物** | 代码、配置、契约、文档、测量结果或验收证据 |
| **负责人和复核者** | 谁实施，谁评审，谁接收交付 |
| **开发前置条件** | 达到什么状态后才可以开始正式实施 |
| **合并前置条件** | 哪些依赖与检查满足后才允许合并 |
| **集成／发布前置条件** | 哪些真实能力或验收节点必须通过 |
| **可修改范围** | 允许修改的模块、公共契约及受限文件 |
| **并行与冲突约束** | 能和谁同时工作，不能同时占用什么 |
| **预计 PR 拆分** | 计划怎样分成可评审的变化，之后关联实际 PR |
| **风险与验收级别** | 是否需要专项评审、功能验收或发布验收 |
| **完成条件与证据** | 什么结果满足任务，证据保存在哪里 |
| **阻塞与交接信息** | 当前卡在哪里，下一步是什么，谁负责解除 |
| **资源与估算** | 环境、预算、容量、工作量范围和不确定性 |

**规划阶段先使用稳定任务编号，不必提前编造尚不存在的 PR 编号。**

真正创建 PR 后，再建立映射。任务拆分变化时更新映射，而不是让依赖全部绑定在一个可能废弃的 PR 上。

---

### 05. 带类型、条件和证据的依赖关系

只写：

> Task B depends on Task A。

通常不够。

我建议每条重要依赖至少记录：**依赖对象、依赖类型、满足条件、所需版本和判定证据。**

| 依赖类型 | 具体含义 | 示例 |
|---|---|---|
| **决策／规格依赖** | 需要先明确规则 | 授权撤销语义批准后，才能实现执行检查 |
| **开发依赖** | 缺少前置产物，正式实施无法继续 | 需要生成客户端后才能调用具体接口 |
| **合并依赖** | 可以提前开发，但不能提前合入 | 调用新接口的 PR，等待接口 PR 合并 |
| **集成依赖** | 局部可以实现，真实联调需要其他组件 | UI 可以先开发，端到端验证等待真实服务 |
| **环境／资源依赖** | 等待设备、账户、环境或独占资源 | 迁移演练需要指定数据库环境 |
| **验收依赖** | 下游必须等待某项能力被验证 | 开放真实发送前，恢复验收必须通过 |
| **部署／开放依赖** | 代码顺序不等于运行顺序 | 先部署兼容服务，再开放新客户端行为 |

GitLab 的合并请求依赖功能就专门处理“先合并谁”的约束，并区分 PR 自身就绪状态与合并顺序。它也明确指出：上游只是关闭而没有合并，不会自动满足下游依赖。citeturn649045view1

更好的依赖描述是：

> 调用方 PR 合并前，接口契约 v1 必须已经进入目标分支，相关兼容性检查通过，且依赖的构建产物已经可用。

而不是：

> 等后端完成。

跨仓库时尤其要注意：**上游代码合并，不等于下游需要的软件包已经发布，也不等于对应服务已经部署。**

---

### 06. 并行开发条件与资源冲突规则

我建议只有在以下条件满足时，才把任务标为可并行：

**输入契约足够明确，修改责任可区分，共享资源不会相互污染，最后存在明确的集成与验证安排。**

“修改不同文件”不等于没有冲突。

一个 PR 修改 API 的字段含义，另一个 PR 修改使用该字段的业务逻辑，即便没有 Git 文本冲突，也可能存在语义冲突。

文档应记录容易产生竞争的共享区域，例如公共 Schema、依赖锁文件、迁移目录、全局配置、同一个测试账户和同一套部署环境。

对于多个 Agent，我建议采用独立分支和工作目录，并进一步隔离数据库、端口、临时文件和凭证。

Git worktree 可以让一个仓库同时检出多个分支，但它仍共享部分仓库信息；**它本身不是运行时安全沙箱，也不会自动隔离数据库和外部账户。**citeturn844601view0

因此，文档应分别定义**代码工作区隔离**和**运行资源隔离**。

---

### 07. 调度、工作量、在制品限制与里程碑

这一章回答：

> **现在应该先做什么，允许多少工作同时进行？**

我建议排序时同时考虑依赖解锁价值、风险、业务优先级和资源可用性。

例如，一个契约任务会阻塞六个后续任务，就不能只因它代码少、展示效果不明显而一直延后。

计划应记录关键依赖链、估算范围、未知问题和资源限制。高风险假设可以先安排有明确结论的技术验证任务。

还应限制同时进行的任务数量，也就是 **WIP：在制品数量**。

对于 Agent 团队，编码 Agent 可以快速产生 PR，但评审、真实集成和验收也需要容量。我的建议是：**不能只限制模型并发，不限制待评审和待验收工作。**

里程碑应尽量用结果表达：

> 第一条真实邮件流程及规定的失败恢复完成验收。

而不是：

> 已完成二十个 PR。

---

### 08. 状态定义与进入、退出条件

不要用一个“完成”覆盖整个交付过程。

我建议至少分别记录：

**任务实施状态、PR 评审与合并状态、功能验收状态、部署与开放状态。**

例如：

> 任务实施完成；PR 已合并；功能组合验收尚未通过；生产能力仍关闭。

这是一个完全合理的中间状态。

每个阶段都要有进入和退出条件：

“可以开始”需要输入与环境就绪；“可以评审”需要实现、测试和说明准备好；“可以合并”需要依赖和保护检查满足；“工作包完成”需要组合验收满足。

阻塞最好作为附加状态记录原因、责任人和解除条件，而不是把所有问题都塞进“进行中”。

**任务依赖图中的循环等待应被识别并解决；开发中的修改—测试—修复循环，则是任务内部工作流，不要把二者混成一张无法调度的图。**

---

## C. 每个 PR 内部的工作方式

### 09. PR 拆分原则与分支策略

我建议一个 PR 尽量围绕一个可以理解、评审和验证的变化主题。

代码、相关测试和必要的规格更新应一起考虑，不能规定“所有测试等最后再补”。

Google 的评审指南建议相关测试通常与生产代码放在同一个变更中，并要求评审测试本身是否真的能够发现错误。citeturn583508view4

文档还应规定普通分支、依赖分支、合并方式和紧急修复路径。

对于“叠加 PR”，即后一个 PR 基于尚未合并的前一个 PR 开发，应明确基础分支、合并顺序，以及上游修改后下游如何更新并重新验证。

**小 PR 不意味着随意把一个不可分割的变化拆成几个会破坏主分支的碎片。**

每次合并后都应满足当时承诺的兼容性与可运行条件。未开放能力也不能借助一个界面开关，就忽视初始化、迁移或后台代码可能产生的影响。

---

### 10. 单个 PR 的标准执行流程

这是你明确问到的“每个 PR 内部怎么工作”。

我建议采用以下默认流程：

| 阶段 | 具体工作 | 进入下一阶段前应具备什么 |
|---|---|---|
| **1. 接单与基线检查** | 阅读任务、需求、设计、有效 ADR、依赖状态 | 范围明确，输入版本正确，没有未解决的硬阻塞 |
| **2. 准备工作区** | 建立分支、隔离环境、准备测试数据和权限 | 可以复现基线，知道已有失败，不污染其他任务 |
| **3. 制定小型实施计划** | 列出修改点、契约影响、测试与迁移影响 | 不越过任务范围，重大设计变化已进入决策流程 |
| **4. 建立验证** | 编写或补充能发现目标问题的测试 | 知道测试为什么失败，预期不是由错误实现反推 |
| **5. 实现与局部循环** | 小步实现、运行测试、分析失败、修复 | 实现与相关测试满足本 PR 的要求 |
| **6. 自检与整理** | 阅读完整 diff，检查无关修改、敏感信息和文档 | 变更可审查，证据完整，已知限制明确 |
| **7. 正式评审** | 复核需求、设计、正确性、测试与兼容性 | 必要意见得到处理，所需评审有效 |
| **8. 集成候选检查** | 在规定目标基线或合并候选上运行必要检查 | 合并依赖与自动化条件满足 |
| **9. 合并与合并后验证** | 合入、确认构建与必要回归、处理异常 | 主分支状态明确，证据对应实际版本 |
| **10. 交接与更新计划** | 更新任务、产物、下游条件和验收状态 | 下游知道什么已可用，什么仍未获准 |

对于适合的逻辑，可以采用测试驱动开发的“先失败测试—实现通过—重构”循环；这是开发方法，与上一轮讨论的测试规格文档不是同一个概念。citeturn844601view4

还要规定不同失败去哪里处理：

**普通代码错误**回到实现与测试；**规格冲突**进入需求或设计变更；**环境故障**进入环境处理；**超出权限**暂停相关操作并请求授权。

不要让 Agent 无限重试，也不要遇到任何失败都通过删除测试或降低标准解决。

---

### 11. PR 描述、评审与交接要求

一个优秀的 PR 描述，应让评审者知道：

**为什么改、改了什么、没改什么、依赖什么、风险是什么、如何验证，以及怎样撤回或继续修复。**

我建议模板包含任务与规格引用、变化摘要、实际依赖、测试结果、未测项、迁移与开放影响、所需专项评审，以及关联验收节点。

评审不能只检查格式。Google 的代码评审指南明确覆盖整体设计、功能、复杂度、并发问题、测试、命名和文档。citeturn583508view4

交接也不能只写：

> 做完了，交给下一个 Agent。

应包含实际提交版本、已完成内容、仍未解决的问题、测试证据、可用接口及下一步约束。

**接收者应能够核验交付物，不必相信交付者的自我评价。**

---

### 12. CI、合并队列与合并权限

CI，即持续集成检查，应承担可自动验证的规则，而不是只运行编译。

我建议按变化范围配置构建、测试、契约兼容、安全检查、依赖满足情况，以及证据完整性检查。

尤其要防止：

> PR-A 在旧主分支上通过，PR-B 也在旧主分支上通过，两个一起合并却失败。

GitHub 的 merge queue 会将变更与最新目标分支及队列中前面的 PR 组合，运行规定检查。使用 GitHub Actions 时，需要配置 `merge_group` 事件才能对相应合并组合执行检查。citeturn649045view0

但合并队列只能执行已配置的检查，不能替团队发现尚未定义的业务依赖，更不能替代完整功能验收。

还应规定谁能够绕过规则、在什么条件下允许、如何记录，以及随后必须补什么验证。普通实现 Agent 不应同时拥有修改保护规则和放行自身变更的权限。

---

## D. 哪些 PR 要“大验收”，怎样验收？

### 13. 风险分级与专项检查触发条件

**验收强度应该主要跟影响和风险走，而不是跟代码行数走。**

我建议至少明确哪些变化需要提升检查等级，例如：

授权与隔离、真实外部操作、共享数据模型、数据库迁移、调度与恢复、公共接口、模型或 Harness 行为，以及系统更新和特权组件。

一个只修改两行的权限判断，可能比一个数百行的纯展示组件更需要严格验证。

分级应由变更内容、涉及范围和上下游影响共同决定，不能只相信 PR 作者勾选的“低风险”。

所有 PR 都有基本门槛；高风险 PR 增加专项评审与证据；跨模块用户能力再进入组合验收。**不需要每个 PR 都跑全系统所有测试，但关键风险不能因为“只是小改动”被忽略。**

---

### 14. 分层验收，而不是只设一次最终大考

我建议设置下面几层。这里的编号是项目组织建议，不是通用标准。

| 层级 | 验收对象 | 主要判断 |
|---|---|---|
| **G0：实施准入** | 一个任务 | 输入、范围、权限和环境是否足以开工 |
| **G1：PR 合并检查** | 一个具体变更 | 局部正确、相关回归、兼容与依赖是否满足 |
| **G2：功能／工作包验收** | 多个 PR 组成的能力 | 完整场景、跨模块规则、异常与真实产物是否成立 |
| **G3：发布准入** | 一个确定的发布候选 | 迁移、运行、容量、安全、监控和恢复是否就绪 |
| **G4：开放后观察** | 已部署并按范围开放的版本 | 实际运行是否满足继续扩大的条件 |

Google SRE 的生产就绪评审不仅关注功能，还包括架构依赖、监控、应急响应、容量、变更管理和性能。citeturn844601view3

你说的“大验收”，通常对应 **G2 或 G3**。

**它不是“最后一个 PR 的作者顺便看一眼”，而是一个有独立负责人、输入版本和证据要求的节点。**

验收节点可以由工作流、测试任务或人工评审实现，不必为了形式而制造一个没有代码变化的“验收 PR”。

---

### 15. 每个验收节点的完整定义

我建议每个 G2、G3 节点包含：

| 字段 | 应该明确什么 |
|---|---|
| **对象与范围** | 验收哪个工作包或发布候选 |
| **触发条件** | 哪些任务、PR、环境与外部条件已就绪 |
| **版本基线** | 提交、构建、依赖、配置及适用模型／Harness 版本 |
| **验收规格** | 引用哪些测试与产品验收条件，不另写一套冲突标准 |
| **负责人和批准者** | 谁组织执行，谁复核，谁有权作出结论 |
| **环境与证据** | 哪里运行，真实与模拟边界是什么，必须留下什么 |
| **通过／失败条件** | 什么允许放行，哪些失败不可用总通过率抵消 |
| **失败处置** | 创建哪些修复任务，阻塞哪些下游动作 |
| **失效与重验条件** | 哪些变化会使原证据不再适用 |
| **通过后解锁什么** | 解锁集成、部署还是用户开放，必须具体 |

特别要强调版本：

> **验收通过的是“这个确定组合在这些条件下的结果”，不是永久给一个功能盖章。**

后续修改了接口、迁移脚本、权限策略或相关实现，应评估并重跑受影响的检查。不能拿旧候选的结果去批准新候选。

GitHub 的分支保护也提供撤销过期审批、要求最新可评审提交获得批准等机制，体现了“批准与具体变化绑定”的原则。citeturn583508view0

---

### 16. 发布、观察、回退与收尾

应明确合并、部署和用户开放分别由什么条件控制。

例如，代码已经部署但能力仍关闭，下一步可能是试点开放，而不是直接扩大到全部用户。

我建议每个发布计划写清开放范围、观察指标、暂停条件、停止新增工作方式，以及回退或向前修复路线。

渐进发布也需要证据和停止规则。Google SRE 将金丝雀发布定义为有限范围、有限时间的部署评估，用来判断是否继续扩大发布。citeturn583508view5

回退必须考虑数据和外部影响：

**撤回代码不等于撤回已经发送的邮件，也不等于迁移后的数据自动恢复。**

收尾还应包含移除临时开关、清理兼容代码、释放环境和预算，以及更新运行文档，避免工作包永远只完成“开发部分”。

---

## E. Agent 协作、异常与持续维护

### 17. 人与 Agent 的执行约定

针对你的团队，我建议任务卡额外指定：

执行 Agent 与 Harness、允许调用的工具、可读上下文、可写范围、运行预算、检查点、停止条件，以及交接格式。

共享上下文应优先包括任务规格、有效决策、公共契约和实际证据；不应默认让所有 Agent 共享所有凭证和全部用户数据。

尤其要把以下权限分开：

**修改实现、修改测试基线、修改 CI 与保护规则、产生验收结论、执行生产发布。**

GitHub 的 Actions 安全指导要求工作流凭证采用最小权限，并建议按具体作业增加必要权限，而不是默认授予广泛访问。citeturn844601view2

我的建议是：

普通范围内的编码、测试和提交可以自动执行；需要改变需求、降低验收门槛、修改安全边界或产生未授权外部影响时，进入指定审批流程。

**Agent 可以提交证据，不能仅凭“我已经测试通过”解锁依赖。**

---

### 18. 阻塞、返工、依赖变更与应急路径

这一章回答：

> **原计划不再成立时，团队怎样继续工作？**

需要定义上游 PR 被拒绝、关闭、撤回或重新设计时，下游怎样处理；契约变化时谁通知消费者；验收失败后谁拆修复任务；主分支失效时是否暂停普通合并。

我建议每次重要变更都检查它影响的下游集合，而不是只改当前任务。

例如：

> 授权契约变化 → 重新评估执行网关、UI 提示、恢复逻辑和相关验收证据。

不是所有下游都必须停止。可以继续与该变化无关的工作，但不能继续把已失效的假设当成已确认事实。

应急路径可以更快，但要留下原因、权限、影响范围和补验责任。**应急不意味着允许删除历史失败或永久绕过保护。**

---

### 19. 执行进度、瓶颈与工程反馈

我建议进度汇总围绕以下信息组织：

当前可启动任务、真正阻塞交付的依赖、等待评审与验收的工作、已通过的完整能力、仍未覆盖的风险，以及下一次能形成什么可验证结果。

不要主要用代码行数、PR 数量或 Agent 工作时长衡量进展。

更有用的指标包括任务完成周期、阻塞时长、评审等待、验收等待、返工比例、失败恢复时间和单位成功交付成本。

这些指标的用途是发现瓶颈，不是让 Agent 为了提高数量而拆出大量没有交付价值的 PR。

---

### 20. 规范落实、更新与例外管理

最后要说明哪些规则通过流程约定执行，哪些通过仓库与 CI 强制执行。

例如，风险判定需要专业判断；“缺少必需检查不能合并”则适合自动限制。

文档应明确维护人、变更流程、例外批准、有效期，以及例外到期后的处理。

**写了规则，不等于规则已经落实。**

我建议定期抽查：任务卡是否真实、依赖是否仍有效、通过记录是否指向当前版本、关闭任务是否真的交付，以及临时例外是否被永久遗忘。

# 四、用一个具体例子：哪些 PR 并行，哪些依赖，在哪里大验收？

下面沿用邮件功能。**编号和拆分仅作示例，不代表已经创建了这些任务或 PR。**

目标工作包是：

> 用户确认内容后，系统能够真实发送邮件，并在规定的异常情况下保留正确状态、避免盲目重发。

## 1. 示例任务与合并关系

| 任务／计划 PR | 主要交付 | 开发安排 | 合并依赖 |
|---|---|---|---|
| **A：接口与状态契约** | 公共类型、操作语义和契约测试 | 需求与关键设计明确后开始 | 无本组代码依赖 |
| **B：状态持久化** | 操作记录、事务、并发约束 | A 就绪后，与 C、D、E 并行 | A |
| **C：授权与行动入口** | 执行前检查、权限上下文 | A 就绪后，与 B、D、E 并行 | A |
| **D：供应商适配器** | 调用、错误映射和证据转换 | A 就绪后，与 B、C、E 并行 | A |
| **E：确认与状态界面** | 确认内容、显示真实状态 | 可依据 A 使用明确标注的测试替身开发 | A；未接真实链路不得算功能验收 |
| **F：发送编排** | 连接存储、授权和供应商调用 | 本例正式集成等待 B、C、D | B、C、D |
| **G：恢复与结果核对** | 中断恢复、未知结果处理 | 本例正式集成等待 F | F |

在本例中：

**B、C、D、E 可以并行。**

**F 的正式集成依赖 B、C、D；G 的正式集成依赖 F。**

更早编写 F、G 的测试或依据契约做实现是可以另行安排的，但必须记录采用的基线和未解决的真实集成依赖。

---

## 2. 哪些需要更严格的 PR 级检查？

我会对 C 的权限行为、B 的数据正确性，以及 F、G 的外部影响和恢复逻辑设置专项检查。

E 也不是“只是前端所以随便验收”：它必须证明没有把未知显示成成功，没有确认错误的内容版本，也没有绕过后端授权。

不过，**这些 PR 的专项检查仍然不能代替整个功能的组合验收。**

---

## 3. 大验收放在哪里？

建立独立节点 **G-MAIL-FUNCTION**。

它的输入是包含 A 到 G 的确定集成候选，并依据前面测试规格验证：正常发送、内容修改后确认失效、授权撤销、响应丢失、重复消息、执行器恢复，以及用户最终看到的状态与实际结果。

如果某项依赖尚未真实接入，就明确记录对应场景未验证，不以模拟结果替代。

通过后，进入发布准入节点，检查运行、监控、容量、权限配置和停止方案。

**所有 PR 已合并，只满足组合验收的部分前置条件，不自动代表工作包通过。**

---

## 4. 验收失败后怎么办？

假设 G 的恢复逻辑发现重复发送风险。

应建立修复任务，关联失败证据，阻止相关功能开放；不必因此阻止所有与邮件无关的普通开发。

修复 PR 合并后，对新候选重新执行受影响的验收，保留旧候选失败记录。

**不要把“大验收”做成最后一个超级 PR，也不要等全部产品完成才第一次做端到端检查。**

# 五、放到 GitHub，哪些东西应该由工具执行？

这份文档不应该只停留在文字层。

| 需要落实的事情 | 可采用的载体 |
|---|---|
| 工作包、任务和负责人 | Issues、项目看板和任务字段 |
| 任务之间的阻塞关系 | Issue dependencies |
| PR 的目的、依赖和证据说明 | PR 模板与结构化任务引用 |
| 模块评审责任 | CODEOWNERS 与相应保护规则 |
| 合并检查 | Required status checks、规则集和适用的合并队列 |
| 环境与发布限制 | Environments、部署保护与受控凭证 |
| 验收结果 | 指向确定构建的运行记录、报告和批准记录 |

GitHub 已支持用 issue dependencies 表达阻塞与被阻塞关系，但这属于任务关联；**不要据此推断某个任务关系已经自动变成 PR 的强制合并检查。**需要在项目中明确额外的执行机制。citeturn583508view2

`CODEOWNERS` 可以分配代码所有者并配合规则要求其批准。不过，同一规则列出多个所有者时，通常任一所有者的批准即可满足对应要求；需要两个独立专业角色都批准时，不能只靠在同一行写两个名字。citeturn583508view1

还有一个容易忽略的细节：GitHub 的部分状态检查规则允许 `skipped` 或 `neutral` 满足条件。因此，对关键验收，我建议增加明确的结果汇总检查，确认必需测试确实运行并取得合格证据，不能把“没有运行”误当作“通过”。citeturn583508view0

发布环境可以设置审批或其他保护规则，但功能可用范围与仓库、套餐有关，应按实际环境确认，不能在文档里假设所有仓库都有相同能力。citeturn844601view1

**工具负责执行部分规则；任务语义、风险判断和完整验收范围仍需要团队定义。**

# 六、怎样判断这份文档已经足够好？

我建议用下面这些问题进行最终审查：

| 问题 | 不合格信号 |
|---|---|
| **每项工作有明确交付物吗？** | 只有“做前端”“优化 Agent” |
| **依赖记录了具体条件吗？** | 只有“等上一个完成” |
| **开发、合并、验收、发布分开了吗？** | 一个状态同时代表四件事 |
| **并行条件真的成立吗？** | 只检查文件是否不同，没有检查契约和共享资源 |
| **每个 PR 有可执行的内部流程吗？** | 编码结束后才临时决定谁评审、测什么 |
| **完整功能有集成负责人吗？** | 每个人只对自己的 PR 负责 |
| **大验收绑定确定版本吗？** | 汇总各分支的通过结果，就宣称整体成功 |
| **失败会改变下游状态吗？** | 上游已撤回，下游仍继续按旧假设推进 |
| **权限与证据受保护吗？** | 实现 Agent 能自行降低门槛并批准自身 |
| **规范和仓库行为一致吗？** | 文档写不能合并，实际任何人都能绕过 |

开工前，不必把未来几年全部 PR 排好。我的建议是：**先确定整体工作包、关键依赖和验收结构，把近期工作细化到可以启动；后续根据实际发现滚动拆分。**

## 最后的结论

**你需要这套资料，而且它不只是“工作方式说明书”，更是一套工程执行与交付规则。**

它至少应把下面这条关系贯通：

> **规格依据 → 工作包与任务 → 有条件的依赖与并行 → PR 内部工作流 → 合并检查 → 功能组合验收 → 发布与观察 → 失败反馈和重新调度。**

**SDD 让工程师知道具体怎样实现；测试规格让团队知道怎样判断正确；这份文档则让所有人和 Agent 知道：现在谁该做什么、何时可以继续，以及什么时候才能有证据地宣布交付。**
