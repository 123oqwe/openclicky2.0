# Security

OpenClicky reads your screen, listens to your microphone, holds an API key, and types into
other applications. Those four capabilities are where the interesting bugs live. This page
says how to report one, what is in scope, and which gaps are already known so you do not
spend an afternoon on them.

## Reporting a vulnerability

There is no security email address and no security team. This is a small project.

**GitHub's private vulnerability reporting is turned off on this repository.** Verified:
`api.github.com/repos/123oqwe/openclicky2.0/private-vulnerability-reporting` returns
`enabled: false`. So there is no "Report a vulnerability" button to click today.

What to do instead:

1. Open an issue titled `security: <one line, no details>`.
2. In the body, say what kind of problem it is and that you have details you would rather
   not post publicly. Nothing else.
3. Wait to be given a private channel before you write the reproduction.

Do not put any of the following in a public issue: a working exploit, a real API key,
someone else's screenshot or audio, or a demo that harms a third party's service.

Once you have a private channel, include the affected commit or release tag, the steps to
reproduce, what an attacker gains, and whether you want to be credited.

There is no bounty. Acknowledgement and a fix timeline are best effort.

## In scope

Report anything that breaks one of these promises.

**Capture only when you act.** `ScreenSource::capture_all` requires a `CaptureGuard` and
`CaptureGate::authorize` is the only way to get one. A capture that happens without a user
action, or a gate opened on something that is not a user action, is a bug.

**The key stays put.** The API key belongs in the OS key store or in `secrets.enc` at 0600.
It must never reach `config.toml`, the database, a log line, an error message, or a commit.
`crates/core/src/security.rs` masks bearer tokens and key-shaped values; a path around it
is a bug.

**Typing goes where you aimed.** Text injection must not reach a window you did not target,
must not paste multi-line text into a terminal, and must not type something the secret check
in `crates/core/src/dictation.rs` should have refused.

**Tools run only when approved.** The approval gate, the private-network guard, and the
workspace boundary are all in scope. So is a way to make the app talk to a host the
configured policy forbids.

**Data goes to the endpoint you configured and nowhere else.** Any other outbound traffic is
a bug. `docs/07-compatible-endpoints.md` documents what may legitimately leave the machine.

**Prompt injection that reaches an action.** Text on your screen can try to steer the model.
The boundary is the approval prompt, not the model's good judgement. If a hostile screen can
cause an action without you approving it, that is in scope. If a hostile screen only produces
a wrong answer, it is a quality issue, not a security one.

**Release artifacts.** A file that does not match `SHA256SUMS`, or an installer that fetches
anything other than the release asset it names, is in scope.

## Out of scope, and why

**The macOS "unidentified developer" prompt.** The release artifacts are ad-hoc signed and
not notarized. `.github/workflows/release.yml` sets `APPLE_SIGNING_IDENTITY: "-"`, and
`notarytool` appears nowhere in this repository. macOS therefore blocks the first launch and
makes you allow it under System Settings → Privacy & Security. Windows is not Authenticode
signed either, so SmartScreen will be unhappy too. This is a known gap and a decision that is
still open, not a vulnerability. Reporting it will get this paragraph quoted back at you.

**You cannot verify what you downloaded.** `SHA256SUMS` is generated by the same workflow
that builds the artifacts and is served from the same host, unsigned. It catches a truncated
or corrupted download. It does not prove the release was not tampered with. Until there is a
signing key, treat it as a corruption check, not an authenticity check.

**A third-party endpoint.** If you point `base_url` at someone else's gateway, what happens
to your screenshots there is between you and them. See `PRIVACY.md`.

**The system keychain refusing the app's key.** Reproduced on the maintainer's Mac: `openclicky set-key`
writes the item, and reading it straight back reports no such item, so the app treats the
keychain as unusable and keeps the key in memory for the life of the process. `openclicky doctor`
and `set-key` now print that sentence instead of a generic refusal. It is an operating
system fact about an ad-hoc signed binary, not a hole and not something the app can
argue its way out of, so do not report it as a vulnerability. The supported answer is
the encrypted file: `openclicky set-key --remember-file`, or the button the settings page
offers, which puts the key in `secrets.enc` at mode 0600.

**Local root.** Anyone who can read your user account can read your database and your config.
Running OpenClicky as another user, or in a container, is not in scope.

**Platform paths less travelled.** macOS is what the maintainer runs. Windows and Linux
builds exist and their tests pass, but their permission and injection paths have had far less
contact with real machines. A bug there is a real bug; it may just take longer to confirm.

## Known open issues

**#98.** The private-network guard can be bypassed with a backslash in the URL authority, so
`allow_private_network = false` does not fully hold. Filed and unfixed. A report that
reproduces the same bypass adds nothing; a report that finds a second one does.

**#86.** The key store was not compiled into the binary at one point, so a saved key lived
only in memory. Check the issue before reporting a variant of it.

**#107.** Restoring the clipboard after a paste works for text only, so an image or a file on
your clipboard is cleared. Privacy bug, not a privilege escalation, already filed.

**#93.** Tool arguments shown in the approval prompt are truncated to 200 characters, so the
prompt can hide part of the path you are approving. Known and filed. Anything that makes this
worse belongs in that issue.

## What this page cannot promise

There has been no external audit. No signed releases, so no chain of custody. The repository
has one maintainer, which means a response can be slow and a fix can take a while. Everything
above describes the code as it is at the commit you are reading, not an assurance that the
code is free of the bugs this page lists as in scope.
